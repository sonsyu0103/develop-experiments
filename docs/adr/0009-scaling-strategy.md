# ADR 0009: スケール戦略 —— 何を今決め、何を後回しにするか

- ステータス: **採用 (実装前)**
- 日付: 2026-08-05

## 背景

「登録ユーザー 100 万人でも捌けるシステム」を目標に置いた。

[インフラ構成](../infrastructure.md) の初版では
「リードレプリカを置いていない」と書いたが、その根拠を
**レプリケーション遅延の副作用だけ**で説明していた。
これは「なぜ要らないか」の説明になっていない。

この ADR で、負荷を数字に分解し、
**何が何番目にボトルネックになるか**を決める。

## まず数字にする

100 万は登録ユーザー数であって、同時接続数ではない。
両者は 3 桁違うので、混同したまま設計すると必ず過剰になる。

前提を明示して見積もる。

| 項目 | 控えめ | 攻めた前提 |
| --- | --- | --- |
| 登録ユーザー | 100 万 | 100 万 |
| DAU | 10 万 (10%) | 30 万 (30%) |
| 1 人あたり PV / 日 | 20 | 50 |
| **PV / 日** | 200 万 | 1,500 万 |
| 平均 PV/秒 | 23 | 174 |
| **ピーク PV/秒** (平均の 8 倍) | 185 | 1,390 |
| **ピーク API RPS** (1 PV = 3 リクエスト) | **約 550** | **約 4,200** |

書き込みは桁が違う。

| 項目 | 控えめ | 攻めた前提 |
| --- | --- | --- |
| コメント投稿 / 日 | 10 万 | 60 万 |
| 平均 | 1.2 / 秒 | 7 / 秒 |
| **ピーク** | **約 10 / 秒** | **約 56 / 秒** |

### この数字から読み取れること

**1. 書き込みは驚くほど少ない。**
ピークでも毎秒 56 件。PostgreSQL の書き込みスループットとしては誤差の範囲であり、
SERIALIZABLE を使っても総量としては何の問題もない。

**Phase 2 の関心は「スループット」ではなく「集中」になる。**
毎秒 56 件が 100 スレッドに分散すれば競合はほぼ起きない。
炎上中の 1 スレッドに全部が集中すると、同じ 56 件でも直列化失敗が頻発する。
測るべきは平均 RPS ではなく、**単一スレッドへの集中度**になる。

**2. 閲覧数を同期 UPDATE にしていたら、それだけで破綻していた。**
ピーク 1,390 PV/秒がそのまま `UPDATE threads` になり、
しかも人気スレッドほど同じ行に集中する。
[ADR 0006](0006-view-count-and-popularity.md) の判断が、この数字で裏付けられる。
**書き込みの主役はコメント投稿 (56/秒) ではなく閲覧数 (1,390/秒) だった。**

**3. 読み取り 4,200 RPS は、単一 PostgreSQL の限界ではないが余裕もない。**
キーセットページネーションと部分インデックスが効いていれば
1 クエリはサブミリ秒で返る。8 vCPU 級のインスタンスで捌ける範囲にある。
ただし安全マージンは小さく、**レプリカが必要になる可能性は十分にある**。

## 決定 1: リードレプリカは「置かない」ではなく「置ける形にする」

初版の記述を撤回する。

100 万ユーザーを前提にする以上、
「レプリカは要らない」と言い切れる根拠はない。
一方で、最初から 2 台構成にして遅延の副作用を全経路で引き受けるのも早すぎる。

**判断すべきは「レプリカを置くか」ではなく
「後からレプリカを置けるか」になる。**

### 今の構造では置けない

現在、`postgres.NewPool` が生成する `*pgxpool.Pool` は 1 つで、
全リポジトリがこれを共有している。
レプリカを足すには、クエリごとに接続先を選ぶ必要があり、
リポジトリの構造そのものを変えることになる。

幸い、`sqlc` が生成する `Queries` は `DBTX` インターフェースを受け取る形なので、
**生成コード側は既に分離可能**になっている。足りないのは上のレイヤだけ。

### 決定

リポジトリを、**読み取り用と書き込み用の 2 つの `Queries` を持つ形**にする。

```go
type ThreadRepository struct {
    w *sqlcgen.Queries // プライマリ (書き込み + 一貫性が要る読み取り)
    r *sqlcgen.Queries // レプリカ (遅延を許容できる読み取り)
}
```

**当面は両方に同じプールを渡す。** 構成上は今と何も変わらない。
変わるのは「どのクエリが遅延を許容できるか」がコードに書かれることだけ。

レプリカを足す日が来たら、`cmd/api/main.go` の結線で `r` だけ差し替える。
この変更を後からやろうとすると、全クエリを 1 件ずつ
「これは遅延して大丈夫か」と再検討することになる。
**その判断は書いた本人がその場でやるのが一番安い。**

## 決定 2: 遅延を許容できない読み取りを先に列挙する

レプリカ読み取りで壊れるのは、**自分が書いた直後に自分で読む**経路になる。
他人の投稿が数百 ms 遅れて見えるのは掲示板として問題ないが、
「投稿したのに自分のコメントが出てこない」は不具合として報告される。

| 経路 | 接続先 | 理由 |
| --- | --- | --- |
| コメント投稿後のスレッド詳細 | **プライマリ** | 自分の投稿が見えないと壊れて見える |
| マイページ (自分の投稿一覧) | **プライマリ** | 同上 |
| ログイン直後の `/me` | **プライマリ** | セッション作成の直後 |
| セッションの検証 | **プライマリ** | ログアウトが即座に効かなくなる |
| スレッド一覧 (新着 / 人気) | レプリカ | 数百 ms 古くても問題ない |
| 他人のスレッド詳細 | レプリカ | 同上 |
| コメント一覧 (自分の投稿直後を除く) | レプリカ | 同上 |

### 「自分の投稿直後」をどう判定するか

素朴には「書き込み後 N 秒はプライマリを読む」で足りる (sticky)。
単純で、実装コストがほぼゼロ。**まずこれを採る。**

より正確にやるなら、PostgreSQL の WAL 位置を使える。

```
書き込み後: pg_current_wal_insert_lsn() を取得してセッションに持つ
読み取り時: レプリカの pg_last_wal_replay_lsn() と比較
            追いついていればレプリカ、遅れていればプライマリ
```

これは「read-your-own-writes をレプリカ構成で保証する」という、
**このリポジトリの主題 (一貫性と分離レベル) の延長線上にある題材**になる。
sticky 方式が実際に取りこぼすことを測ってから、必要なら実装する。

## 決定 3: 接続プーリングはレプリカより先に必要になる

**これが実際には最初に来るボトルネックになる。**

PostgreSQL は接続ごとに OS プロセスを 1 つ持つ。
接続数を増やすとメモリと context switch が線形に増え、
**アクティブ接続の最適値は CPU コア数の 2〜4 倍程度**にしかならない。

ECS でスケールアウトすると、この数は簡単に破れる。

| タスク数 | `MaxConns` | DB への接続数 |
| --- | --- | --- |
| 2 | 8 | 16 |
| 10 | 8 | 80 |
| 30 | 8 | **240** |

アプリ側のプール (`pgxpool`) は、
**1 タスク内の接続を再利用するだけで、タスクをまたいだ制御はできない**。
タスク数に比例して接続が増えるのを止められない。

**既定を 8 に下げても問題は先送りされるだけになる** (下の「実測」3-2)。
旧既定の 20 なら 30 タスクで 600 接続、8 でも 240 接続。
どちらも「コア数の 2〜4 倍」からは桁で外れており、
**プール上限の調整で解ける問題ではない**ことがはっきりする。

したがって **RDS Proxy (または PgBouncer) を [インフラ構成](../infrastructure.md) に追加する**。

### 罠: transaction pooling と prepared statement

これは踏んでから気づくと原因の特定が難しいので先に書いておく。

`pgx` は既定でプリペアドステートメントをキャッシュする
(`QueryExecModeCacheStatement`)。プリペアドステートメントはセッションに紐づくため、
トランザクション単位で接続を多重化するプーラとは前提が衝突する。

| プーラ | 挙動 |
| --- | --- |
| RDS Proxy | プリペアドステートメント使用時に接続が **pin** され、多重化が効かなくなる |
| PgBouncer (transaction mode) | 1.21 以降は `max_prepared_statements` で対応。それ以前は非対応 |

対処は、DSN で実行モードを落とすか (`default_query_exec_mode=simple_protocol`)、
プーラ側の対応設定を入れるかのどちらかになる。
**プーラを入れた瞬間に静かに性能が出なくなる**種類の問題なので、
導入時は pin 率かプール多重度を必ず確認する。

## ボトルネックが来る順序

以上をまとめると、手を打つ順序はこうなる。

| # | ボトルネック | 対策 | 今やること |
| --- | --- | --- | --- |
| 1 | DB 接続数 (タスク数に比例) | RDS Proxy / PgBouncer | 構成図に追加。実装は不要 |
| 2 | 閲覧数の書き込み集中 | バッファ + 定期フラッシュ | **[ADR 0006](0006-view-count-and-popularity.md) で対処済み** |
| 3 | セッション検索がプライマリに集中 | Redis へ移す | インターフェースの背後に置く ([ADR 0005](0005-authentication.md)) |
| 4 | 読み取り QPS | リードレプリカ | **読み書き経路を分けておく (決定 1)** |
| 5 | 画像の帯域 | 署名付き URL へ移行 | 移行条件を明記済み ([ADR 0007](0007-image-storage.md)) |
| 6 | 閲覧数フラッシュがタスク数に比例 | Redis で集約してから 1 経路で反映 | 次の手として記録済み ([ADR 0006](0006-view-count-and-popularity.md)) |

**リードレプリカは 4 番目**であり、最初に来る問題ではなかった。
ただし 4 番目に来ることは確かなので、決定 1 の準備をしておく。

## 後から変えにくいもの / 後で足せるもの

スケールのための判断は、**この 2 つを取り違えると高くつく**。

### 後で足せる (今やらない)

RDS Proxy、リードレプリカ、Redis、CloudFront、オートスケーリング、
署名付き URL への移行。
いずれも**インフラの追加**であり、アプリの構造を変えずに導入できる
—— 決定 1 の準備をしておく限りにおいて。

### 後から変えにくい (今決める)

| 項目 | 状態 |
| --- | --- |
| 読み書きの経路分離 | **決定 1 で今やる** |
| カーソルの表現 | **対応済み** ([ADR 0018](0018-opaque-cursor.md))。公開前に不透明トークンへ変更した |
| セッションストアの抽象化 | [ADR 0005](0005-authentication.md) で対処済み |
| ID の型 (`BIGINT` 連番) | **未決** ([ADR 0003](0003-open-questions.md) #11) |
| `comments` のパーティション数 (8) | **未決** ([ADR 0003](0003-open-questions.md) #12) |

下 2 つは、後から変えるとデータの再配置を伴う。
数字が出た段階で判断できるよう、未決事項として登録する。

## 「捌ける」ことは測らないと分からない

この ADR の見積もりは**すべて仮定の上に立っている**。
DAU 率も PV 数もピーク係数も、根拠は経験則でしかない。

したがって、この設計が 100 万ユーザーを捌けるという主張は、
現時点では**検証されていない**。

[README](../../README.md) の Phase 4 を、
その検証の場として位置づける。

| 測ること | 何が分かるか | 状態 |
| --- | --- | --- |
| 単一スレッドへの投稿集中度 vs 直列化失敗率 | 「炎上」が Phase 2 の実装で耐えられるか | 済 ([ADR 0019](0019-comment-concurrency.md)) |
| 閲覧数更新 あり / なし での 40001 発生率 | [ADR 0006](0006-view-count-and-popularity.md) の分離が効いているか | 済 ([ADR 0006](0006-view-count-and-popularity.md)) |
| 読み取り QPS の限界 (単一インスタンス) | レプリカが何 RPS から必要になるか | **済** (下記) |
| 接続数 vs スループット | RDS Proxy が何タスクから必要になるか | **済** (下記) |
| パーティション数 vs クエリ時間 | 8 で足りるか (未決 #12 の判断材料) | **済** (下記) |

**設計を先に膨らませるより、測れる形にすることを優先する。**

## 実測 (Phase 4 / `make scale-probe` / `make partition-probe`)

測定機は Apple M1 Pro (8 コア) 上の Docker Desktop。
**コンテナ側に見えている CPU は 4 で、全サービスがそれを分け合う。**
PostgreSQL 17、`shared_buffers` 128MB、`max_connections` 100。
データは 2,000 スレッド / 20 万コメント (`make bench-dataset`)。

### 1. 「負荷生成側が先に飽和する」は成り立たなかった

README の Phase 4 は、この項目を
「単一マシンの compose では負荷生成側が先に飽和する」ため未測定としていた。
**先に飽和するかどうかを測ったら、していなかった。**

負荷生成を go-api コンテナの中で走らせ (ホストからだと Docker の
ポート転送が先に律速になる)、まず DB を触らない `/healthz` で天井を出す。

| 並列 | `/healthz` RPS | `/threads?size=20` RPS |
| --- | --- | --- |
| 1 | 6,978 | 664 |
| 4 | 18,472 | 2,017 |
| 8 | 24,969 | **2,241** |
| 16 | 29,689 | 2,127 |
| 128 | **33,805** | 2,262 |

**`/threads` は校正の 7% で頭打ちになる。** 生成側の天井 (33,805 RPS) は
はるか上にあるので、2,200 RPS は測定器の限界ではなく API 側の限界になる。

「測れない」と書いてあった理由が、**測ってみたら成り立っていなかった**。
天井を測らずに「生成側が先に飽和するはず」と書いた時点で止まっていた。

### 2. 頭打ちの正体は PostgreSQL の CPU

条件ごとに `docker stats` を取った (100% = 1 コア)。

| 並列 | RPS | postgres | go-api (負荷生成を含む) |
| --- | --- | --- | --- |
| 1 | 664 | 81% | 36% |
| 4 | 2,017 | 235% | 63% |
| 8 | 2,241 | 259% | 64% |
| 128 | 2,262 | 262% | 63% |

並列 8 以降は RPS もレイテンシ以外も動かず、**postgres だけが 260% 前後で
張り付く**。go-api は 63% で頭打ちになっており (しかもこの数字には
負荷生成のぶんが混ざっている)、アプリ側には余力がある。

**レプリカの判断材料としてはこれが答えになる。** 読み取りを増やすときに
足りなくなるのは API のタスク数ではなく DB の CPU で、
「後からレプリカを置ける形にする」(決定 1) の前提は正しかった。

### 3. PostgreSQL 単体の天井と、接続数の最適点

HTTP と Go を全部剥がし、pgbench で同じ SQL を直接流した
(コンテナ内、Unix ソケット)。

| 接続 | 一覧クエリ TPS | 詳細 + コメント TPS | postgres CPU |
| --- | --- | --- | --- |
| 1 | 1,054 | 1,428 | 103% |
| 2 | 1,904 | 2,346 | 200% |
| 4 | 3,082 | 4,549 | 305% |
| 8 | **3,570** | **5,452** | 356% |
| 16 | 3,381 | 5,259 | 355% |
| 32 | 3,395 | 5,038 | 362% |
| 64 | 3,105 | 4,442 | 363% |

**スループットは接続数 = コア数の 2 倍でピークになり、そこから下がる。**
4 vCPU で 8 接続が最適点で、64 接続では 13% 落ちる (一覧)。
CPU は 360% で飽和したまま TPS だけが下がるので、
**増えたぶんは切り替えと待ちに消えている**ことになる。

これが「RDS Proxy が何タスクから必要になるか」の答えの形になる。
必要になるのは**タスク数**ではなく、
**全タスクの接続数の合計が DB のコア数の 2 倍を超えたとき**。

### 3-2. 決定: `DB_MAX_CONNS` の既定を 20 から 8 に下げる

上の最適点が API 経由でも同じ位置に出るかを確かめた。
`DB_MAX_CONNS` を振って go-api を作り直し、`/threads` を叩く
(`make scale-probe` の 5 番)。

| プール上限 | RPS (並列 16) | RPS (並列 64) | p95 (並列 64) | 実接続数 |
| --- | --- | --- | --- | --- |
| 4 | 1,982 | 1,970 | 40.7 ms | 5 |
| **8** | 2,109 | **2,157** | **36.4 ms** | 9 |
| 12 | 2,121 | 2,162 | 37.1 ms | 13 |
| 16 | 2,139 | 2,096 | 40.2 ms | 17 |
| 20 (旧既定) | 2,104 | 2,073 | 45.2 ms | 21 |
| 32 | 2,137 | 2,115 | 55.4 ms | 33 |
| 64 | 2,186 | 2,184 | **122.5 ms** | 65 |

**スループットは上限 8 で頭打ちになる。** 4 では 8% 落ちるが、
8 から 64 までは 2,100 前後で動かない ——
**増やしても速くならない。**

**変わるのは遅い側の応答だけになる。** 並列 64 での p95 は
上限 8 で 36 ms、上限 64 で 122 ms。3.4 倍に伸びている。

理由ははっきりしている。**上限を増やすと、待つ場所がアプリの待ち行列から
DB の中へ移る。** DB の中で待たれると全員が一緒に遅くなるが、
手前で絞れば待っている要求だけが待つ。
pgbench が示した最適点 (接続数 = コア数の 2 倍 = 8) と同じ位置になった。

したがって **既定を 8 にする。**

**8 が普遍的に正しいわけではない。** 適正値は DB のコア数に比例し、
アプリからはそれが見えない (アプリのコア数は別の数字になる)。
固定値である以上どの数字も推測だが、
**20 が「測らずに置いた推測」だったのに対し、8 は
「4 vCPU で測った値」であり、外し方が安全な側に倒れている** ——
小さすぎればアプリ側の待ち行列として見えるが、
大きすぎると尾を引くレイテンシとして静かに悪化する。

環境ごとに `DB_MAX_CONNS` で上書きする前提は変えない。
compose からも渡せるようにした (`DB_MAX_CONNS` / `DB_MIN_CONNS`)。

### 4. 見積もり 4,200 RPS との突き合わせ

ADR の見積もりは「読み取りピーク 約 4,200 RPS (攻めた前提)」で、
「8 vCPU 級のインスタンスで捌ける範囲にある」と書いた。

実測は **4 vCPU を API と DB で分け合って 2,262 RPS**。
DB 単体では一覧 3,570 TPS / 詳細 5,452 TPS 出ている。

**見積もりを覆す結果は出ていない。** ただし
「8 vCPU なら 2 倍出る」と読むのは行き過ぎで、
上の表のとおり CPU を増やしても接続数の最適点が動くだけの領域がある。
**言えるのは「4 vCPU で 2,200 RPS」までで、
4,200 RPS が出ることを確かめたわけではない。**

### 5. パーティション: 2,000 万行でも効き始めなかった

`comments` の HASH 8 分割は「どの規模から効き始めるかを Phase 4 で測る」
ために入れたもの (`db/migrations/000001_init_schema.up.sql`)。
`bench_part` スキーマに同じ列・同じ索引の表を
「分割なし」「HASH 8」「HASH 32」で作り、同一データで比べた。

**2,000 万行 / 20 万スレッドでの「1 スレッドのコメント一覧」** ——
本番の主経路であり、除外が最も効くはずの形:

| 測り方 | 分割なし | HASH 8 |
| --- | --- | --- |
| ウォーム後 (実行 + 計画) | **1.20 ms** | 1.69 ms |
| うち実行だけ | 0.210 ms | **0.194 ms** |
| プリペアドステートメント (n=120) | **0.042 ms** | **0.042 ms** |

**除外は正しく効いている。** 実行計画に `Subplans Removed: 7` が出て、
8 区画のうち 1 つしか走査していない。それでも速くならないのは、
**2,000 万行を 8 分割しても B-tree の段数が変わらない**ため。
索引探索の段数は行数の対数でしか減らないので、
1 段減らすには 100 倍以上の行数差が要る。

除外が効かないクエリでは、分割は一貫して負ける (200 万行、計画 + 実行):

| クエリ | 分割なし | HASH 8 | HASH 32 |
| --- | --- | --- | --- |
| 20 スレッドぶんの集計 | **1.29 ms** | 5.44 ms | 9.75 ms |
| 時刻で絞る全体集計 | **142.5 ms** | 202.3 ms | 211.5 ms |
| 1 行 INSERT | **0.86 ms** | 1.27 ms | 1.50 ms |

**32 分割はすべての項目で 8 分割より悪い。**
[未決 #12](0003-open-questions.md) は「8 のまま」で閉じた。

**問いの立て方が間違っていた。** 「どの規模から効き始めるか」は
「いずれ効き始める」ことを前提にしているが、この形のクエリでは
効き始める規模が (現実的な範囲に) 無い。
8 分割の価値は読み取り性能ではなく保守の側 ——
区画ごとの `VACUUM`、索引の作り直し、古い区画の切り離し —— にある。
**その用途なら維持する価値はあるが、性能を理由に正当化してはいけない。**

## 引き受けるコスト

- **読み書き分離の構造を、レプリカがない状態で維持することになる。**
  同じプールを 2 つのフィールドに入れる形は、
  知らずに読むと冗長に見える。なぜそうなっているかをコードのコメントに残す
- **クエリを追加するたびに「レプリカに逃がせるか」の判断が要る。**
  判断を忘れると、既定でプライマリに寄る (安全側に倒れる) ようにする
- **見積もりの前提が外れれば順序も変わる。**
  たとえば画像が想定より多用されれば、帯域 (5 番目) が一気に繰り上がる。
  この ADR の順序は測定結果で更新する
- **100 万ユーザーは目標であって要件ではない。**
  そこに到達しない可能性のほうが高い。
  この ADR が正当化するのは「**後から手を打てる形にしておくこと**」までであり、
  到達していない負荷のために今インフラを増やすことではない
