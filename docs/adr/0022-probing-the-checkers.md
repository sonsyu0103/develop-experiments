# ADR 0022: 検査そのものの検出力を、変異で測る

- ステータス: **採用・実装済み**
- 日付: 2026-08-24

## 背景

**検査は、壊れても出力が変わらない。**

テストなら「落ちた」で気づける。しかし検査 (`verify-*`) は、
何も検出できない状態でも「OK」と出て、CI は緑になる。
**縮んだことに気づく手がかりが 1 つも無い。**

これは新しい問題ではなく、このリポジトリで繰り返し踏んできた形になる。

| いつ | 何が起きたか |
| --- | --- |
| ADR 0004 | 緩和ルールの `deny` に相手モジュールを入れ忘れていた。プローブを置いて初めて分かった |
| ADR 0003 #8 | `image_test.go` が「CHECK 制約と揃っている」と書きながら、比較していたのは**テスト内のリテラル同士**だった。制約を変えても緑 |
| ADR 0005 決定 4 | スモークが認証まわりを丸ごと飛ばしたまま「74 件すべて成功」と表示していた |
| ADR 0020 | フロントに振る舞いの検査が 1 つも無く、変異プローブも**その領域を測れていなかった** |

対策として 2 つの仕組みを置いた。

    .github/scripts/arch-probe.sh      arch-lint の設定を検査する
    .github/scripts/mutation-probe.py  Go のテストを検査する

**ソースを読む静的検査には、それが無かった。**

    .github/scripts/verify-log-events.py
    .github/scripts/verify-constraint-checks.py

2026-08-24 のレビューで実際に測ったところ、**4 つ穴が空いていた。**

| # | 穴 | 壊したときの終了コード |
| --- | --- | --- |
| ① | フィールド名の正規表現が `[a-z_]+`。数字を含む名前は**どの検査にも当たらないまま素通り** | **0** (素通り) |
| ② | DDL を `PARTITIONED BY` より先まで読み、パーティション列が**レコードの列として宣言済み**に見えていた | 0 (現状 0 件のため潜在) |
| ③ | `slog` の型と DDL の型を**誰も突き合わせていなかった** | 0 (現状 0 件のため潜在) |
| ④ | 「テストがマイグレーションを読んでいるか」の判定に**コメントが数えられていた** | **0** (素通り) |

①と④は**実際に終了コード 0 のまま**だった。
どちらも「検査がある」ように見えていたので、レビューでも見落とされていた。

## 決定 1: 静的検査には、変異プローブを対で置く

`.github/scripts/checker-probe.py` を追加した。
宣言した変異を 1 つずつ当て、検査が落ちるかを実測する。

`arch-probe.sh` が arch-lint に、`mutation-probe.py` が Go のテストに
していることを、ソースを読む検査に対して行うだけになる。

**設定ではなくソースを壊す**点が `arch-probe.sh` と違う。
そのぶん陳腐化しやすいので、置換対象が**ちょうど 1 か所**に
当たることを毎回確認する —— 0 件を素通しすると、
**何も壊さずに「落ちた」を得る**ことになり、検出力の証拠が捏造される。

## 決定 2: 終了コードではなく、**期待する NG の文言**まで見る

`arch-probe.sh` は終了コードだけで判定している (出力の文言で判定すると
想定外の通知を取りこぼすため)。**こちらは逆にする。**

理由は、1 つの変異が複数の検査に当たるためになる。
たとえば `dt` というフィールドを出すと、

  - パーティション列との衝突 (見たいもの)
  - DDL に宣言が無い (ついでに鳴るもの)

の両方が鳴る。終了コードだけを見ると、**塞いだはずの穴を塞がないまま
「検出できた」と数える。**

これは机上の心配ではない。このスクリプトを書く途中で 1 度踏んだ ——
比較用の旧実装を `/tmp` に置いたところ、相対パスで解決している
参照が壊れ、**まったく無関係な理由で落ちていた**のを
「旧実装でも検出できる」と読み違えた。

## 決定 3: 壊したものは、**どう終わっても**戻す

`mutation-probe.py` の `Restorer` を踏襲する。
例外と Ctrl-C は `finally` が、SIGTERM / SIGHUP はシグナルハンドラが戻す
(Python は SIGTERM の既定ハンドラでそのまま終わるため、`finally` に到達しない)。

このスクリプトは**検査そのもの**を書き換えるので、
戻し損ねると**以降の CI がすべて嘘の結果を返す。**

同じ理由で、状態を変える他のプローブにも同じ規律を広げた。
`viewcount-probe.py` は HOT update の比較のために
`threads_alive_popular_idx` を落とすが、**落とした直後の失敗経路で
復元に到達しなかった** —— 索引が消えたまま残ると人気順が全表走査になり、
以降の測定がすべて別物になる。しかも「なぜか遅い」以外の手がかりが出ない。

## 決定 4: CI に載せる基準は「DB もネットワークも要らないこと」

`checker-probe.py` は両方とも要らないので `make check` と CI に載せた。
**実測 1 秒**で 13 変異を通す (Go Checks 全体は 179 秒)。

逆に、実環境が要るものは載せない (`make logs-verify`、`make smoke` の一部)。
**そこは「載せられないので、静的側に同じ検査を置く」で埋める。**

実例: ADR 0010 の 4-5 (ログに出してはいけない項目) は、
一覧が `infra/duckdb/verify.py` にしか無く、**CI で 1 度も検査されていなかった。**
他の規則は「あとで気づいて直す」が効くが、
**一度 S3 に出したものは事実上消せない。**
その規則がいちばん検査から遠かったことになる。
同じ一覧を `verify-log-events.py` に持ち、
**両者がずれたら落とす** (`ast` で読んで突き合わせる)。

## 引き受けるコスト

- **変異は実装が変われば陳腐化する。** 置換対象が 0 件になったら
  プローブ側が先に落ちるので、黙って無効化されることはない ——
  ただし直す手間は残る
- **プローブ用のアンカーが実質的な契約になる。**
  `slog.String("version", Version())` のような行を消すと、
  無関係な PR で `checker-probe` が赤くなる
- **CI が 1 ステップ増える。** 実測 1 秒なので今のところ無視できる

## やらなかったこと

### 検査のカバレッジを測る

Python 側にカバレッジを入れれば「通っていない分岐」は分かるが、
**通っている分岐が正しく落とすか**は分からない。
①と④はどちらも**分岐は通っていた** —— 通ったうえで何も検出していなかった。

### プローブを自動生成する

検査ごとに「何を壊せば鳴るべきか」は人が決めるしかない。
自動生成すると、**鳴らないことが正しい変異**と
**鳴るべきなのに鳴らない変異**を区別できなくなる。

### すべてのプローブを CI に載せる

`concurrency-probe` / `viewcount-probe` / `scale-probe` などは
数字が環境の性能に左右されるため、CI には載せない (ADR 0009 と同じ判断)。
**そのぶん、壊れても誰も気づかない。**
実際 `concurrency-probe.py` は `csrfGuard` の導入以降ずっと壊れており、
Phase 10 と Phase 11 を越えるまで誰も気づかなかった。

そこで、載せない代わりに**自分が測れていないことを自分で言う**ようにした ——
成功が 0 件のモードがあれば失敗として扱い、ステータスの内訳を出す。
以前は全投稿が 403 で弾かれても
「レス番号の一意性と連番は、全モードで保たれています」と表示して
終了コード 0 で終わっていた (実測)。
