# ADR 0012: スレッド検索は `pg_trgm` から始める

- ステータス: **採用 (実装済み / Phase 11)**
- 日付: 2026-08-05 (実装して分かったことを 2026-08-16 に追記)

## 背景

100 万ユーザー規模の掲示板 ([ADR 0009](0009-scaling-strategy.md)) で
検索がないのは実用に耐えない。

一方で、素朴に書いた検索は**最も高くつくクエリ**になる。

```sql
-- インデックスが使えない。全行を読む
SELECT * FROM threads WHERE title LIKE '%キーワード%';
```

B-tree インデックスは前方一致 (`'キーワード%'`) にしか効かない。
中間一致は毎回シーケンシャルスキャンになり、
[ADR 0009](0009-scaling-strategy.md) で「読み取り 4,200 RPS」と見積もった
負荷の上に、これが乗る。

## 日本語という制約

**PostgreSQL の標準の全文検索 (`tsvector`) は、日本語では機能しない。**

標準のパーサは空白で単語を区切る。日本語は分かち書きをしないため、
文全体が 1 つのトークンになってしまう。
`to_tsvector('japanese', ...)` という設定も標準には存在しない。

日本語を扱うには、形態素解析または N-gram を行う拡張が要る。
ここで**理想構成が効いてくる**。

| 拡張 | 日本語の精度 | 公式 postgres イメージ | **Amazon RDS** |
| --- | --- | --- | --- |
| `pg_trgm` | 中 (英数字向けの設計) | **含まれる** (contrib) | **使える** |
| `pg_bigm` | 高 (bigram) | 含まれない | **使えない** |
| `pgroonga` | 最も高い (MeCab + N-gram) | 含まれない | **使えない** |

`pgroonga` は日本語検索としては最良だが、
**RDS でも Aurora でもサポートされていない**。
[インフラ構成](../infrastructure.md) で RDS を前提にしている以上、
ローカルでだけ動く拡張を選ぶと、本番に持っていけない設計になる。

実際にデプロイしないとしても、
**「理想構成を実装の指針として使う」と決めた以上、この制約には従う**
([インフラ構成](../infrastructure.md) の位置づけ)。

## 検討した選択肢

### A. `LIKE '%keyword%'` のまま

- 利点: 実装ゼロ
- 欠点: 全表走査。スレッドが増えるほど線形に遅くなる

### B. `pg_trgm` + GIN インデックス (採用)

- 利点: **contrib なので公式イメージに含まれ、RDS でも使える**。
  拡張の追加は 1 行。中間一致にインデックスが効く
- 欠点: 3 文字単位のトライグラムに分解する設計であり、
  日本語の精度は形態素解析に劣る。
  検索語が 1〜2 文字だと選択性が低く、候補が増えて遅くなる

### C. `pgroonga`

- 利点: 日本語検索としては最良
- 欠点: **RDS で使えない。** カスタムイメージのビルドが要る。
  ローカルと本番で検索の実装が変わることになる

### D. OpenSearch (別サービス)

- 利点: 検索専用エンジン。日本語の解析器も揃っている
- 欠点: サービスが 1 つ増え、**DB との同期という新しい問題**を抱える。
  [ADR 0008](0008-contact-and-mail.md) で SQS を避けたのと同じ理由で、
  この規模では代償が大きい

## 決定

**B を採用する。**

```sql
-- db/init/00-extensions.sql に追加 (拡張の作成は superuser 権限の作業)
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```

> **これだけでは日本語に効かない。** データベースの `LC_CTYPE` が `C` だと、
> `pg_trgm` は日本語からトライグラムを 1 つも作らない
> (「実装して分かったこと 1」)。`compose.yaml` 側の設定が対になる。

```sql
-- マイグレーション側
CREATE INDEX threads_title_trgm_idx
    ON threads USING gin (title gin_trgm_ops)
    WHERE deleted_at IS NULL;
```

部分インデックスにしているのは、既存の `threads_alive_id_desc_idx` と同じ理由になる。

精度が足りないと判明したら D (OpenSearch) に移る。
C は本番に持っていけないため、選択肢から外す。

[ADR 0009](0009-scaling-strategy.md) の「測ってから入れる」と同じ判断基準で、
**Phase 4 の測定項目に「検索クエリのレスポンス分布」を加える**。

## 決定 2: 検索対象はスレッドのタイトルだけにする

コメント本文を対象に含めない。

[ADR 0009](0009-scaling-strategy.md) の見積もりでは、コメントは
**5 年で 1.8 億〜10 億行**になる。
ここに GIN インデックスを張ると、インデックス自体が本体に匹敵する大きさになり、
`comments` のハッシュパーティション 8 つそれぞれに作られる。

スレッドのタイトルは 200 文字上限で、行数もスレッド数に収まる。
まずここだけを対象にして、需要と負荷を測る。

## 決定 3: 検索結果は新着順。関連度順にしない

関連度 (`similarity()`) 順にすると、**カーソルがスコアになる**。

- スコアは検索語ごとに変わるため、カーソルに埋め込む値の意味が
  クエリごとに変わる
- 同スコアの行が大量に出るので、第 2 キーが必須になる
- [ADR 0006](0006-view-count-and-popularity.md) で人気順のカーソルを
  `(view_count, id)` の複合キーにしたが、
  検索順はそれをさらに一段複雑にする。
  カーソル自体は不透明トークンなので値を足すこと自体はできる
  ([ADR 0018](0018-opaque-cursor.md))。難しいのは形式ではなく意味のほうになる

検索結果を `id DESC` (新着順) にすれば、
**既存のキーセットページネーションがそのまま使える**。

関連度順が必要になったら、そのとき D (OpenSearch) の検討と合わせて考える。

## 決定 4: 最低文字数は設けない (実測して決めた)

下の「実装して分かったこと 2」のとおり、**1〜2 文字の検索語では
GIN インデックスが使えない**ことを実測した。それでも下限は設けない。

- 日本語の検索語は 2 文字が非常に多い (「東京」「検証」)。
  3 文字未満を拒否すると、**日本語の検索がまともに使えなくなる**
- 短い検索語が必ず遅いわけではない。並び順が `id DESC` + `LIMIT` なので、
  **ありふれた語ほど速い** (id を新しい順に辿って 20 件見つけた時点で止まる)。
  遅くなるのは「短く、かつ珍しい語」の組み合わせだけになる

代わりに、**Phase 4 で「短い x 珍しい」の分布を測る**。
そこで初めて (a) 最低文字数、(b) `statement_timeout`、
(c) OpenSearch (選択肢 D) への移行、のどれを採るかを決める。

## 罠

### 短い検索語でインデックスが効きにくい

`pg_trgm` は文字列を 3 文字のトライグラムに分解する
(前後にパディングを入れるため、2 文字の語でもトライグラムは作られる)。
ただし検索語が短いほど生成されるトライグラムが少なく、
**選択性が下がって多数の候補を再チェックすることになる**。

日本語の検索語は 2 文字が多いため、ここは実測が要る。
最低文字数を設けるかどうかは、測ってから決める。

> **この節は 2 か所が間違っていた** (「実装して分かったこと 2」で実測)。
>
> - パディングが入るのは**文字列を索引に載せるとき**で、
>   `LIKE '%語%'` の**パターン側には入らない**。前後に何が来るか
>   分からないためになる
> - したがって 2 文字以下では**トライグラムが 1 つも取り出せず**、
>   「選択性が下がる」ではなく**索引が使えない** (全件が候補になる)
>
> 結論は決定 4 にある。**最低文字数は設けない。**

### GIN インデックスの更新コスト

GIN は B-tree より更新が重い。
ただし**スレッドのタイトルは作成時にしか書かれない**ため、
この設計では問題にならない。

将来タイトルの編集機能を入れる場合は、この前提が崩れる。

### 検索語をそのまま `LIKE` に渡さない

`%` と `_` は `LIKE` のワイルドカードなので、
エスケープせずに渡すと**利用者が全件マッチを作れる**。
入力は必ずエスケープする。

## 引き受けるコスト

- **日本語の検索精度は形態素解析に劣る。**
  「東京」で「東京都」は引けるが、表記ゆれや語幹の一致は扱えない
- **拡張が 1 つ増える。** `db/init/00-extensions.sql` に追加するため、
  既存のボリュームを消さないと反映されない (初回起動時のみ実行されるため)。
  開発環境の作り直しが要る
- **インデックスが 1 つ増える。** `threads` への書き込みが少しだけ重くなる。
  スレッド作成はコメント投稿より桁で少ないため、影響は小さい
- **検索は「あれば使われる」機能で、負荷の予測が難しい。**
  他の API と違い、利用者が任意の文字列を投げてくる。
  遅いクエリのログ (`auto_explain`) を検索経路について特に注視する
- **データベースのロケール設定に縛られる。** 下の「実装して分かったこと 1」。
  `LC_CTYPE` を C に戻すと、この ADR の前提が音もなく消える

## 実装して分かったこと (Phase 11)

実測はすべて **50,000 スレッド / PostgreSQL 17 / `postgres:17-alpine`** で行った。
`EXPLAIN (ANALYZE, BUFFERS)`、`max_parallel_workers_per_gather = 0`。

### 1. **`LC_CTYPE=C` では、pg_trgm が日本語を 1 文字も索引しない**

**この ADR の前提が丸ごと崩れていた。**

```sql
-- 変更前 (LC_CTYPE=C)
SELECT show_trgm('検証');   -- {}          ← トライグラムが 0 個
-- 変更後 (LC_CTYPE=C.UTF-8)
SELECT show_trgm('検証');   -- {0x0b1253,osW,0x912f90}
```

`pg_trgm` は「語をなす文字」の並びからトライグラムを切り出す。
その文字種判定はデータベースの `LC_CTYPE` に従い、**C ロケールでは
PostgreSQL が「1 バイト = 1 文字」の速い経路に入るため、
日本語の文字は「文字」と判定されない。**

結果として、日本語のタイトルは索引に 1 エントリも載らない。
`CREATE INDEX` は成功し、`\d threads` にも出る。**エラーは出ない。**
出るのは「索引があるのに全件が候補になる」という実行計画だけになる。

| | 索引が返す候補 | 実行時間 | buffers |
| --- | --- | --- | --- |
| `LC_CTYPE=C` | **50,510** (実際の一致は 501) | 26.75 ms | 672 |
| `LC_CTYPE=C.UTF-8` | **501** | **0.82 ms** | 16 |

`compose.yaml` を分けて指定する形に直した。

```diff
-POSTGRES_INITDB_ARGS: "--encoding=UTF8 --locale=C"
+POSTGRES_INITDB_ARGS: "--encoding=UTF8 --lc-collate=C --lc-ctype=C.UTF-8"
```

**`LC_COLLATE` は C のまま**でよい。`compose.yaml` が C ロケールを選んだ
理由 (バイト順比較が速い / `LIKE 'prefix%'` が B-Tree で効く /
glibc 差でインデックスが壊れない) は**すべて照合順序 (`LC_COLLATE`) の話**で、
文字種判定 (`LC_CTYPE`) とは分けて指定できる。

> **RDS では確認していない。** `C.UTF-8` は新しめの glibc にしか無く、
> 使えない場合は `ja_JP.UTF-8` や `en_US.UTF-8` を `LC_CTYPE` に充てる。
> **`LC_COLLATE` を釣られて変えないこと** —— それをやると上の 3 つを失う。

**教訓は「ロケールは照合順序の設定だ」と思い込んでいたこと。**
`LC_CTYPE` は「どの文字が文字か」を決めており、
**拡張の挙動をここまで変える**とは想定していなかった。

### 2. 索引が使えるのは **3 文字から**。1〜2 文字では候補が全件になる

「短いと選択性が下がる」と書いていたが、実際は**選択性の問題ではなかった。**

`LIKE '%語%'` のパターンからは、両端にパディングを置けない
(前後に何が来るか分からないため)。**語の内側に完全に収まる
トライグラムだけ**が取り出せるので、2 文字以下では取り出せる
トライグラムが 0 個になり、GIN は全件を候補として返す。

50,000 行・一致 501 行での実測 (`LC_CTYPE=C.UTF-8`、索引を使わせた場合):

| 検索語 | 索引が返す候補 | 実行時間 |
| --- | --- | --- |
| `縁` (1 文字) | 50,000 | 26.96 ms |
| `旧話` (2 文字) | 50,000 | 26.34 ms |
| `旧記録` (3 文字) | **501** | **0.51 ms** |

**3 文字で 52 倍**。境界は連続的ではなく、崖になっている。
`show_trgm()` は 1 文字でもトライグラムを返す (文字列全体には
パディングを置けるため) ので、**関数の出力を見て「効く」と判断すると間違える。**

この結果を受けて決定 4 (最低文字数を設けない) を追加した。

### 3. 新着順 (決定 3) と GIN インデックスは競合する

`ORDER BY id DESC LIMIT 20` があるため、プランナは
**「id の索引を新しい順に辿って、20 件見つかったら止める」**計画を選べる。
ありふれた語ならこれが最速になる (実測 0.2 ms / buffers 8)。

問題は**「一致するのは古い行だけ」の語**で、この計画は
テーブルをほぼ端まで歩く。

| 計画 | 実行時間 | buffers |
| --- | --- | --- |
| プランナが選んだ `Index Scan Backward` (pkey) | 21.6 ms | 708 |
| 強制した GIN Bitmap | **0.82 ms** | 16 |

**プランナは統計から「1% は含む語だから、すぐ 20 件見つかる」と読む。**
一致が古い id に偏っているかどうかは統計に出ない。
決定 3 (新着順) を選んだ以上、この形は避けられない。
Phase 4 の測定項目に加える。

### 4. クエリを 2 本に割った (`ListThreads` と `SearchThreads`)

「検索語が NULL なら絞り込まない」を 1 本の SQL で書くと、
`WHERE ... AND ($1::text IS NULL OR title ILIKE ...)` になる。

**この `OR` は汎用計画 (generic plan) で索引を殺す。**
パラメータ値を見て計画を立てたときは分岐を畳めるが、
PostgreSQL は同じ prepared statement を繰り返し実行すると
汎用計画に切り替えることがあり、そうなると畳めない。
**「たまに遅い」がいちばん困る**ので、SELECT 句の重複を受け入れて割った。

### 5. 空白だけの検索語は「指定なし」にした (400 にしない)

`?q=` や `?q=%20` を 400 にすると、**検索欄を空のまま送信したフォームが
弾かれる。** 利用者からは「検索が壊れている」としか見えない。
カーソルに空文字を許しているのと同じ判断になる (ADR 0018)。

正規化 (前後の空白を落とす) は `model.ParseSearchQuery` に閉じてある。
`strings.TrimSpace` は `unicode.IsSpace` で判定するので、
**全角スペース (U+3000) もここで落ちる** —— 日本語入力では実際に紛れる。

### 6. `LIKE` のエスケープは永続化層に置いた

`%` `_` `\` を打ち消すのは PostgreSQL の `LIKE` の都合であって、
検索語そのものの性質ではない。ドメイン (`SearchQuery`) は素の文字列を持ち、
`ThreadRepository` が `ESCAPE '\'` と対になる形でエスケープする。

**順に置換していく実装にしないこと。** `%` を先に `\%` へ変えてから
`\` を `\\` へ変えると、自分で挿入した `\` を拾って
`\\%`「バックスラッシュに続く任意の文字列」に化ける。
`strings.NewReplacer` は入力を 1 回だけ走査するので、この形なら 1 段で済む。

> **ここは変異プローブに直された。**
> 最初は「`ReplaceAll` を 3 回呼ぶと二重にエスケープする」と書いていたが、
> **`\` を先に置換する順序なら 3 回呼んでも結果は同じ**だった
> (`\` の置換結果を `%` の置換は拾わない)。
> その変異を入れてもテストが緑のままだったので気づいた。
> **危ないのは回数ではなく順序**で、`\` を最後に置換したときだけ壊れる。

### 7. 拡張は初回起動時にしか作られない —— マイグレーションで撃ち分ける

`db/init/00-extensions.sql` は**コンテナの初回起動時にしか実行されない。**
Phase 11 より前に作ったボリュームには `pg_trgm` が無く、
`000010` は `type gin_trgm_ops does not exist` で落ちる ——
**エラーだけ見ても何をすればいいのか分からない。**

`000010` の先頭に `pg_extension` を確かめる `DO` ブロックを置き、
「`make clean && make up` でデータベースを作り直せ」と言わせている。

**拡張の作成をマイグレーションに移す案は採らなかった。**
`CREATE EXTENSION` は superuser 権限の運用作業で、
RDS ではアプリの接続ロールが権限を持たない構成もありうる。

### 8. 索引はテーブル本体より大きい

50,000 行での実測。

| | サイズ |
| --- | --- |
| `threads` (ヒープ) | 4,400 kB |
| `threads_title_trgm_idx` | **4,888 kB** |

**決定 2 (コメント本文を対象に含めない) の裏づけ**になった。
ADR 0009 の見積もりでコメントは 5 年で 1.8 億〜10 億行になる。
そこに同じ比率の索引を張ると、索引だけで本体に匹敵する大きさが
**ハッシュパーティション 8 つそれぞれに**乗る。
