# ADR 0011: モデレーション —— ロール・削除権限・通報

- ステータス: **採用 (実装前)**
- 日付: 2026-08-05

## 背景

[ADR 0005](0005-authentication.md) の権限モデルには**管理者が存在しない**。
その結果、次の状態になっていた。

| 状況 | 現状の権限モデルでの結末 |
| --- | --- |
| 匿名で荒らし投稿がされた | `author_id` が NULL なので **誰も削除できない** |
| ログインユーザーが不適切な画像を投稿した | 本人しか消せない。本人は消さない |
| なりすまし・誹謗中傷の投稿 | 対応手段がない |

画像投稿を許し ([ADR 0007](0007-image-storage.md))、
100 万ユーザー規模を想定する ([ADR 0009](0009-scaling-strategy.md)) 以上、
この状態では運用できない。

## 決定 1: ロールは `users` の列として持つ

```sql
ALTER TABLE users ADD COLUMN role TEXT NOT NULL DEFAULT 'user';
ALTER TABLE users ADD CONSTRAINT users_role_valid
    CHECK (role IN ('user', 'moderator', 'admin'));
```

別テーブル (`user_roles`) にしないのは、**1 ユーザーが持つロールは 1 つ**であり、
多対多にする理由がないため。権限の組み合わせを細かく制御する要求が出たら、
そのときに切り出す。

3 段階に分けるのは、**投稿を消せる権限と、権限を配れる権限を分離する**ため。

| | `user` | `moderator` | `admin` |
| --- | --- | --- | --- |
| 自分の投稿の削除 | ✅ | ✅ | ✅ |
| **他人・匿名の投稿の削除** | ❌ | ✅ | ✅ |
| 通報キューの閲覧 | ❌ | ✅ | ✅ |
| **ロールの変更** | ❌ | ❌ | ✅ |

モデレーターを増やしても、権限を配れる人間は増えない。

### 権限昇格を作り込まない

- **ユーザー登録時にリクエストから `role` を読まない。** 常に `'user'` 固定。
  「クライアントから送られた値を保存する」経路を 1 か所でも作ると、
  そこが権限昇格の入口になる
- ロール変更 API は `admin` のみ。変更は監査記録に残す (決定 3)

### 最初の管理者をどう作るか

**UI からは作れないようにする。** 「最初の 1 人」を作る機能は、
そのまま「誰でも管理者になれる」機能になりうる。

環境変数 `BOOTSTRAP_ADMIN_GOOGLE_SUB` に Google の `sub` を指定し、
その値に一致するユーザーがログインしたときだけ `admin` を付与する。

シークレット扱いの値ではないが、
[ADR 0005](0005-authentication.md) の他の設定と同じく
Secrets Manager から渡す ([インフラ構成](../infrastructure.md))。

## 決定 2: 削除はすべて論理削除。匿名投稿もモデレーターは消せる

既存の `SoftDelete` をそのまま使う。物理削除しない理由は 2 つある。

- **誤って消したときに戻せる。** モデレーションは判断を伴うので必ず誤操作が起きる
- コメントの参照整合性が保たれる (既存のスキーマ設計の理由と同じ)

匿名投稿 (`author_id IS NULL`) は、**本人には消せないがモデレーターには消せる**。
[ADR 0005](0005-authentication.md) の「匿名投稿は誰も削除できない」を
この ADR で上書きする。

## 決定 3: モデレーション操作は DB に記録する

```sql
CREATE TABLE moderation_actions (
    id          BIGINT      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    actor_id    BIGINT      NOT NULL REFERENCES users(id),
    action      TEXT        NOT NULL,   -- 'delete_thread' | 'delete_comment' | 'delete_image' | 'change_role'
    target_type TEXT        NOT NULL,   -- 'thread' | 'comment' | 'image' | 'user'
    target_id   TEXT        NOT NULL,   -- 型が混在するため TEXT
    reason      TEXT,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT moderation_action_valid CHECK (
        action IN ('delete_thread', 'delete_comment', 'delete_image', 'change_role')
    )
);

CREATE INDEX moderation_actions_actor_idx  ON moderation_actions (actor_id, created_at DESC);
CREATE INDEX moderation_actions_target_idx ON moderation_actions (target_type, target_id);
```

**ログ ([ADR 0010](0010-log-pipeline.md)) ではなく DB に書く。**

ADR 0010 で「ログは at-most-once であり欠落しうる。
課金・監査に使う数値をログの件数から数えない」と決めた。
モデレーション記録はまさに監査であり、
「誰が消したか分からない」状態は許容できない。

ログにも出すが、**正はこのテーブル**になる。

## 決定 4: 通報はログイン必須。閾値による自動削除はしない

```sql
CREATE TABLE reports (
    id           BIGINT      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    reporter_id  BIGINT      NOT NULL REFERENCES users(id),
    target_type  TEXT        NOT NULL,   -- 'thread' | 'comment'
    target_id    BIGINT      NOT NULL,
    reason       TEXT        NOT NULL,   -- 'spam' | 'abuse' | 'illegal' | 'other'
    note         TEXT,
    status       TEXT        NOT NULL DEFAULT 'open',  -- 'open' | 'resolved' | 'rejected'
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    resolved_at  TIMESTAMPTZ,
    resolved_by  BIGINT      REFERENCES users(id),

    CONSTRAINT reports_reason_valid CHECK (reason IN ('spam','abuse','illegal','other')),
    CONSTRAINT reports_status_valid CHECK (status IN ('open','resolved','rejected')),
    -- 同一ユーザーによる同一対象への重複通報を防ぐ
    CONSTRAINT reports_unique_per_user UNIQUE (reporter_id, target_type, target_id)
);

CREATE INDEX reports_open_idx ON reports (created_at) WHERE status = 'open';
```

### 匿名通報を許さない

通報を匿名で受け付けると、**通報そのものが荒らしの手段**になる。
無限に通報を投げてキューを埋められる。

投稿は匿名を許すが ([ADR 0005](0005-authentication.md))、
通報はログイン必須とする。非対称だが、
**投稿は表現、通報は他人への申し立て**であり、後者には責任の所在が要る。

### 通報数が閾値を超えても自動で消さない

「N 件通報されたら自動的に非表示」は実装が簡単で、しかも**危険**になる。

- 組織的に通報を集めれば、正常な投稿を消せる (通報爆撃)
- 少数派の意見が構造的に消えやすくなる

通報は**モデレーターのキューに積むだけ**にする。
判断は必ず人間が行い、その結果が `moderation_actions` に残る。

自動化するとしても、上限は「優先度を上げる」までとする。

## 決定 5: 削除された画像はストレージからも消す

論理削除では S3 のオブジェクトが残るため、
**不適切な画像は URL を直接叩けば見え続ける**。
CloudFront にキャッシュも残る。

[ADR 0007](0007-image-storage.md) の `images.status` に `'deleted'` を追加する。

```
モデレーターが画像を削除
   → images.status = 'deleted' に更新 (投稿本体は論理削除)
   → 回収バッチが S3 のオブジェクトを削除
   → CloudFront の該当パスを invalidate
```

回収バッチは既に `'pending'` の孤児を回収する役目を持っているので、
**対象に `'deleted'` を加えるだけ**で済む。定期処理は増えない。

CloudFront の invalidate を忘れると、削除後もキャッシュ期間中は配信され続ける。

## モジュール構成: `moderation` を独立させる

[ADR 0004](0004-modular-monolith.md) に従い `internal/moderation` を追加する。

通報とモデレーション記録は `thread` / `comment` / `image` の
いずれにも属さない**横断的な関心事**であり、
どれかに寄せると他の 2 つへの参照が必要になってモジュール境界が壊れる。

削除操作は、各モジュールが公開する最小のインターフェース
(`ThreadSoftDeleter` など) を `moderation` 側で定義して受ける。

### ただし、これで depguard が 15 ルールになる

モジュールは 6 つ (`thread` / `comment` / `user` / `image` / `contact` / `moderation`)。
1 モジュールにつき 2 ルール + レイヤ用 3 ルールで **15 ルール**。

[ADR 0004](0004-modular-monolith.md) が
「9 を超えて破綻するようなら `go-arch-lint` を再検討する」と書いた水準を、
明確に超える。

**[ADR 0003](0003-open-questions.md) の未決 #13 の判断が、
この ADR で先送りできなくなった。**

なお、そこで数え直したところ**問題はルール数ではなかった**。
`deny` エントリが約 106 になること、そして
**書き忘れが「許可」に倒れる**ことが本体になる。

> **その後の決定 ([ADR 0017](0017-arch-lint-and-depguard.md))**
> 実地検証の結果、検査は `depguard` から `go-arch-lint` に移した。
> `depguard` のルールは 0 になり、この節が心配していた 15 ルールは発生しない。
> `moderation` に必要なのは、2 枚の arch ファイルへの約 16 行ずつの宣言になる。
> なお未決 #13 は穴の所在を「拒否リストであること」としていたが、
> 実測では**どのルールにも一致しないファイルが無検査になること**だった。

## 引き受けるコスト

- **管理画面が要る。** 通報キュー、投稿の削除、ロール変更。
  Next.js 側の作業が増え、しかも**認証の 4 層キャッシュ問題
  ([ADR 0005](0005-authentication.md)) が最も厳しく効く画面**になる。
  管理者向けの内容が他人にキャッシュされたら事故では済まない
- ~~**depguard が 15 ルールになる**~~ ——
  [ADR 0017](0017-arch-lint-and-depguard.md) で検査を `go-arch-lint` に移したため、
  arch ファイル 2 枚に約 16 行ずつの宣言で済む
- **モデレーターの誤操作は戻せるが、その導線も要る。**
  論理削除なので復活は可能だが、「復活させる UI」がなければ
  DB を直接触ることになる
- **通報の一意制約が UX に影響する。**
  同じ対象に 2 回通報しようとするとエラーになる。
  「既に通報済みです」として正常に扱う必要がある
- **`target_id` を `TEXT` にしている。** `images.id` が UUID、
  `threads` / `comments` が `BIGINT` で型が混在するため。
  [ADR 0003](0003-open-questions.md) の #11 は
  **用途ごとに使い分ける (統一しない)** 決定になったので、
  この混在は解消されない。`TEXT` のままとする。
  型が違うものを 1 列に詰めている以上、
  **参照整合性は外部キーで保証できない**点に注意する
  (削除済みの対象を指す行が残りうる)
