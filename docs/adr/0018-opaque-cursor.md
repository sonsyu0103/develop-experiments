# ADR 0018: カーソルを不透明トークン (base64url + JSON) にする

- ステータス: **採用**
- 日付: 2026-08-09

## 背景

[ADR 0006](0006-view-count-and-popularity.md) は、人気順のカーソルが
`(view_count, id)` の複合キーになるため
**「カーソルを不透明なトークン (base64 エンコードした構造体) に変える」**
と決めた。[ADR 0009](0009-scaling-strategy.md) は「カーソルの表現」を
**後から変えにくい項目**の表に置き、公開前の今が最後の機会だと書いている。

この ADR は、その「不透明トークン」の**形式・検証・失効の扱い**を確定させる。
README の着手順 0 番がこれにあたる。

変更前の状態 (実際のコードで確認した):

| 場所 | 変更前 |
| --- | --- |
| `api/openapi.yaml` の `Cursor` | `type: integer` / `format: int64` / `minimum: 1` |
| `api/openapi.yaml` の `NextCursor` | `type: integer` (nullable) |
| `pagination.Page.Cursor` | `*int64` |
| SQL | `id < sqlc.narg('cursor_id')` |

つまり **`id` がそのまま API の契約に出ていた**。
並び順は id 降順の 1 つだけなので、現時点では破綻していない。

カーソルを読む実装は、現時点で
[`apps/next-app/app/page.tsx`](../../apps/next-app/app/page.tsx) (表示のみ) と
[`.github/scripts/smoke-test.py`](../../.github/scripts/smoke-test.py) の 2 つしかない。
**今なら直す先が 2 か所で済む。** Phase 3 で一覧のページ送りを実装した後だと、
ここに画面側の状態管理が加わる。

## 検討した選択肢

### A. `id` を数値のまま公開し続ける

- 利点: 実装コストがゼロ。カーソルを目で読めるのでデバッグが楽
- 欠点: 並び順を足した時点で API の型が変わる。
  ADR 0006 の人気順 (Phase 7) は着手順の最後のほうにあり、
  そのときには一覧・無限スクロール・検索結果がカーソルを持っている

### B. base64url + JSON の不透明トークン (採用)

- 利点: 中身を増やしても API 上の型は `string` のまま。
  人気順は `{"v":1,"s":"popular","vc":...,"id":...}` のように
  フィールドを足すだけで済み、
  仕様書も生成された型もクライアントも変わらない
  (`s` については後述の「並び順を足すときの規則」を参照)
- 欠点: 目視でデバッグできない。
  「復号に失敗する」という新しいエラー経路が増える

### C. B に HMAC 署名を付ける

- 利点: 改竄を検出できる
- 欠点: 署名鍵の管理とローテーションが増える。
  得られるものが**この API では小さい** —— カーソルを改竄して読めるのは
  「公開済みの一覧の別の位置」でしかなく、権限の昇格にならない。
  論理削除済みの行は SQL 側で `deleted_at IS NULL` により常に除外される

### D. サーバ側にカーソルの状態を保存し、参照 ID だけを返す

- 利点: 完全に不透明。トークンを短くできる
- 欠点: **状態を持つ。** TTL、掃除の定期処理、複数インスタンス間の共有が要る。
  [ADR 0009](0009-scaling-strategy.md) が守ろうとしている
  「API プロセスを状態なしに保つ」と正面から衝突する

## 決定

**B を採る。カーソルは `base64url` (パディングなし) で符号化した
JSON `{"v":1,"id":42}` とする。**

実装は [`internal/pagination`](../../apps/go-api/internal/pagination/pagination.go) に閉じている。
HTTP 層も永続化層もトークンの形式を知らない
(永続化層には `Page.CursorID()` が `*int64` を渡す)。

決め手になったのは、**直す先がまだ 2 か所しかない**という一点になる。
B と A の差は「いつ払うか」でしかなく、払う額は後になるほど増える。

### パディングを外す

`base64.RawURLEncoding` を使う。標準の `=` パディングはクエリ文字列で
`%3D` にエスケープされ、生の URL とログが読みにくくなるため。

### バージョンを埋める

`v` は形式のバージョン。互換性のない変更をしたらここを上げ、
古いトークンは復号を拒否する。
実害は「ページ送りの途中で先頭に戻る」だけで済む。

### 並び順を足すときの規則

**バージョンを上げるだけでは足りない。** `v` は形式のバージョンであって、
並び順の識別子ではない。仮に人気順を `{"v":1,"vc":...,"id":...}` として足すと、
`DecodeCursor` は `v == 1` を無条件で受理するため、

**新着順が発行したトークン (`vc` なし) を人気順のエンドポイントに渡すと、
`vc` がゼロ値の 0 に落ち、「閲覧数 0 の位置から」ページングが始まる。**
400 も出ず、黙って誤ったページが返る。

したがって規則を決めておく。

| 変えるもの | やること |
| --- | --- |
| 並び順を足す | トークンに並び順の識別子 `s` を足す。既定 (新着順) は空文字。ハンドラは要求された並び順と `s` の一致を検査し、違えば 400 |
| 形式そのものを変える (フィールドの意味が変わる等) | `v` を上げる。古い版は復号を拒否 |

`s` の検査は `pagination` ではなくハンドラ側に置く。
「どの並び順を要求されたか」を知っているのは HTTP 層だけであり、
`pagination` に持ち込むとソート種別の一覧を下位層が知ることになる。

### 署名しない

選択肢 C を採らない。**トークンの目的は秘匿ではなく、
内部表現を API の契約から切り離すことにある。**
`{"v":1,"id":42}` は復号すれば読めるが、それは
変更前に `?cursor=42` と書いていたのと同じ情報量でしかない。

### 壊れたトークンは 400 で落とす

復号できないカーソルを**黙って先頭ページ扱いにしない**。
そうするとクライアントは「ページ送りしたのに 1 ページ目が返る」状態になり、
無限スクロールが同じページを取り続ける無限ループに入る。
[ADR 0013](0013-http-defense.md) のコード体系に従い
`INVALID_ARGUMENT` (400) を返す。

ただし**理由は細分化しない** (base64 が壊れている / JSON が壊れている / 版が違う)。
トークンはクライアントが組み立てるものではないため、
どの理由でも対処は「先頭ページから取り直す」の一手しかない。

### 仕様書で強制するのは文字集合と長さまで

```yaml
schema:
  type: string
  pattern: '^[A-Za-z0-9_-]*$'
  maxLength: 256
```

`+` ではなく `*` にしてある。`?cursor=` (空文字) は
「省略」と同じく先頭ページとして扱う。
`+` にすると、クライアントが `?cursor=${nextCursor ?? ''}` と組み立てたときに
**初回ロードだけが 400 になる**。

[ADR 0002](0002-openapi-direction.md) の方針どおり、仕様書に書ける制約は
仕様書に置いて検証ミドルウェアに強制させる。
「復号できるか」だけがハンドラ側の判定になる。

## 罠

### `minimum: 1` の防御が消える

変更前は `id <= 0` を仕様書の `minimum: 1` が弾いていた。
`type: string` にした時点でこの検査は**消える**。
`DecodeCursor` に `c.ID <= 0` の拒否を移してある。
移し忘れると、`id <= 0` を埋めたトークンがそのまま SQL に届く。

### 検証の置き場所が 2 か所に分かれる

仕様書 (`pattern` / `maxLength`) が弾くものと、
ハンドラ (復号失敗) が弾くものがある。
`server_test.go` の「仕様書によるリクエスト検証」の表に
壊れたトークンを足しても**そこは通り抜ける**。
別のテストとして置いてある
(`TestListThreads_MalformedCursorIsBadRequest`)。

### 長さの検査は復号の前に置く

`maxLength` を仕様書だけに任せると、検証ミドルウェアを外した構成で
巨大な文字列の復号に付き合わされる。`pagination` 側にも上限を持たせている。

### 空文字の扱いを 2 か所で決めない

`pagination` が「空文字 = 先頭ページ」としていても、
仕様書の `pattern` が空文字を弾けば、その分岐には**永久に到達しない**。
ミドルウェアとハンドラのどちらが先に判断するかを意識しないと、
コードとテストが揃って「先頭ページになる」と主張したまま、
実際には 400 を返す状態になる。

### 符号化のエラーを握りつぶさない

`Encode` は現在の `Cursor` では失敗しない。それでもエラーを返しているのは、
この設計が「並び順を足すときにフィールドを増やす」前提だから。
握りつぶすと、将来 `Encode` が空文字を返し、
`"nextCursor": ""` がクライアントへ流れ、
それを送り返したクライアントが `pattern` 違反の 400 を食う。

### 「弾いていること」だけをテストしない

不正なトークンを拒否するテストだけだと、
**常に 400 を返す実装でも全部通る**。
正しく発行したトークンが 200 になることを別に確認している
(`TestListThreads_ValidCursorIsAccepted`)。

## 引き受けるコスト

- **カーソルを目で読めなくなる。**
  障害調査では `base64 -d` を挟むことになる
- **トークンの形式を変えると、ページ送りの途中で失効する。**
  実害は先頭に戻る程度だが、
  フロント側は 400 を握って先頭から取り直す実装が要る (Phase 3)
- **トークンが長くなった。** `42` → `eyJ2IjoxLCJpZCI6NDJ9` (20 文字)。
  URL 長としては問題にならない範囲
- **改竄は検出できない** (選択肢 C を採らなかったため)。
  変更前と同じ水準であり、後退はしていない

## 決定を覆す条件

- **カーソルに秘匿すべき値を入れる必要が出た場合** ——
  たとえば検索の絞り込み条件やユーザー ID を埋めるようになったら、
  選択肢 C (HMAC 署名) を足す。形式に `v` を持たせてあるので、
  署名付きを `v: 2` として並行させられる
- **トークンが URL 長を圧迫し始めた場合** ——
  JSON をやめて固定長のバイナリ表現にする。
  API 上の型は `string` のままなので、この変更はクライアントに波及しない
