# ADR 0001: RDBMS に PostgreSQL を採用する

- ステータス: 採用
- 日付: 2026-08-02

## 背景

掲示板 API の永続化層として RDBMS を選定する。
本プロジェクトの主題は「並行処理と排他制御」であり、
コメント投稿時の同時実行制御と、スレッド一覧のコメント数集計が中心的な関心事である。

候補は PostgreSQL と MySQL 8.0。

## 検討したが採用理由にしなかったもの

### パーティショニング

当初は「PostgreSQL のパーティショニングが MySQL より優れているから」を
主たる採用理由に据えることを検討した。事実として以下の差はある。

| 観点 | PostgreSQL | MySQL 8.0 |
| --- | --- | --- |
| パーティションテーブルへの外部キー | 使える (PG11+) | **一切使えない** |
| partition-wise join / aggregate | あり | なし |
| ATTACH / DETACH PARTITION | あり (PG14 で `CONCURRENTLY`) | なし |
| DEFAULT パーティション | あり | なし |

しかし、**これを採用理由にするのは誠実ではないと判断した。**

本プロジェクトのデータ量は多く見積もってもコメント数万件であり、
パーティショニングが効き始める規模 (単一テーブルで数千万〜億行) には到底届かない。
この規模ではインデックスだけで十分であり、
むしろプランニングコストの分だけ不利になる可能性が高い。

「必要のない技術を、必要だと誤認して選んだ」という判断は、
要件と技術のマッチングができていないことを意味する。

**したがってパーティショニングは「採用理由」ではなく「検証対象」として扱う。**
実装はするが、その位置づけは
「どの規模から効き始めるかをベンチマークで実測するため」であると明記する
(Phase 4 / `db/migrations/000001_init_schema.up.sql` のコメント参照)。

## 決定

PostgreSQL を採用する。理由は以下の 4 点。

### 1. SERIALIZABLE の実装方式が本プロジェクトの主題に直結する (最重要)

PostgreSQL の `SERIALIZABLE` は **SSI (Serializable Snapshot Isolation)** であり、
読み取りロックを取らずに直列化可能性を保証する楽観的方式である。
競合を検出したときだけトランザクションを中止する。

対して MySQL (InnoDB) の `SERIALIZABLE` は、
全ての `SELECT` を暗黙的に `LOCK IN SHARE MODE` に変換する悲観的なロックベースであり、
同時実行性が大きく落ちる。

さらに MySQL の既定分離レベル `REPEATABLE READ` はギャップロックを取るため、
「同一スレッドに複数ユーザーが同時にコメントする」という本アプリの
中心的なユースケースでデッドロックが発生しやすい。
PostgreSQL の既定 `READ COMMITTED` にギャップロックは存在しない。

並行制御が主題である以上、
**分離レベルの挙動そのものを比較・計測できる**ことに価値がある。
詳細は [`docs/postgres-ssi.md`](../postgres-ssi.md) に記す。

### 2. 集計に使える機能が揃っている

要件の「コメント数を高速集計」に直接効くもの:

- **`COUNT(*) FILTER (WHERE ...)`** — SQL 標準。MySQL には無く `SUM(CASE WHEN ...)` で代用が必要
- **部分インデックス** — `WHERE deleted_at IS NULL` に限定した索引。MySQL には存在しない。
  論理削除との相性が良く、索引サイズを抑えられる
- **マテリアライズドビュー** — MySQL には存在しない。将来コメント数を事前集計する場合の選択肢
- **主キーによる関数従属性の認識** — `GROUP BY t.id` だけで `t.title` を選択できる

### 3. 計測できること

技術選定に根拠を持たせるには、最終的に実測値が要る。

- **`pg_stat_statements`** — クエリ別の呼び出し回数・合計/平均実行時間。N+1 の検出に直結する
- **`EXPLAIN (ANALYZE, BUFFERS)`** — バッファヒット率を含む詳細な実行計画
- **`auto_explain`** — 閾値を超えたクエリの実行計画を自動でログ出力

これらは `compose.yaml` と `db/init/00-extensions.sql` で有効化済み。

### 4. 運用面

- **トランザクショナル DDL** — `ALTER TABLE` をロールバックできる。
  MySQL は DDL で暗黙コミットするため、マイグレーション失敗時に中途半端な状態が残る
- **`RETURNING` 句** — `INSERT ... RETURNING id` が 1 往復で完結する。
  MySQL は `LAST_INSERT_ID()` を別クエリで叩く必要がある

## 結果

### 良くなること

- 並行制御の比較実装 (悲観ロック版 / SSI 版) を同一 DB 上で計測できる
- 論理削除つきの集計クエリを、部分インデックスと `FILTER` で素直に書ける
- 実行計画とクエリ統計を根拠として README に残せる

### 引き受けるコスト

- SSI を使う場合、**直列化失敗 (SQLSTATE 40001) のリトライをアプリ側で実装する必要がある**。
  これは PostgreSQL 特有の負担であり、`internal/infrastructure/postgres/errors.go` の
  `IsRetryable` がその起点になる
- パーティションテーブルの一意制約にパーティションキーを含める制約を受ける
  (`comments` の主キーが `(thread_id, id)` になっている理由)
- MySQL に比べホスティングの選択肢がわずかに狭い (本プロジェクトでは問題にならない)
