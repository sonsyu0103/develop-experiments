# ADR 0008: 問い合わせは DB に保存し、メール送信は非同期にする

- ステータス: **採用・実装済み** (2026-08-18)。
  決定 1〜4 をすべて実装。ワーカーは API プロセス内の定期処理として動く
  ([ADR 0003](0003-open-questions.md) 未決 #9 の決定)
- 日付: 2026-08-05 (実装して分かったことを 2026-08-17 に追記。
  **決定 2 を 2026-08-18 に改訂** —— 「自動返信を送らない」から
  「検証済みのアドレスにだけ送る」へ)

## 背景

問い合わせフォームを作り、内容を運営宛にメールで送る。
これはこのシステムで**初めて外部サービスに依存する処理**になる。

外部依存は落ちる。落ちたときに何が起きるかで設計が決まる。

## 決定 1: 保存と送信を分ける (outbox パターン)

### 検討した選択肢

#### A. リクエスト中に同期でメールを送る

- 利点: 実装が最短。送信結果をそのままレスポンスにできる
- 欠点: **メールプロバイダの障害が、そのまま問い合わせの喪失になる。**
  ユーザーには 500 が返り、書いた内容は失われる。
  問い合わせフォームは「送れなかったことに気づけない」のが最悪の失敗になる。
  加えて、SMTP のハンドシェイクぶんレスポンスが遅くなる

#### B. DB に保存してから、別経路で送信する (採用)

- 利点: 保存が成功した時点で内容は失われない。
  送信はリトライできる。API のレスポンスが外部サービスの遅延に引きずられない
- 欠点: ワーカーが要る。「保存されたが未送信」という状態が生まれる

### 決定

**B を採用する。**

```
POST /contact
     │
     ├──▶ contact_messages に INSERT (status = 'pending')
     │
     └──▶ 202 Accepted を返す        ← ここで外部サービスを待たない

     ⋮

ワーカー (一定間隔)
     │
     ├──▶ pending を取り出す (FOR UPDATE SKIP LOCKED)
     ├──▶ メール送信
     └──▶ status = 'sent' / 'failed' + attempt_count++
```

`202 Accepted` を返すのは、`200 OK` が「送信完了」を含意するため。
この時点で完了しているのは受理までであり、そう返すのが正確になる。

### 複数インスタンスでの二重送信を防ぐ

ワーカーが複数インスタンスで同時に動くと、同じ行を両方が拾って
**同じ問い合わせが 2 通届く**。

```sql
SELECT * FROM contact_messages
WHERE status = 'pending' AND next_attempt_at <= now()
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT $1;
```

`FOR UPDATE SKIP LOCKED` は、他のトランザクションがロック中の行を
**待たずに飛ばす**。各インスタンスは互いに異なる行を取得する。

`SKIP LOCKED` がない場合、後続のワーカーはロック解放まで待ち、
解放後に (既に処理済みの) 行を読むことになる。
`NOWAIT` ではエラーになってしまい、これも使えない。

これは Phase 2 の悲観ロックと同じ `FOR UPDATE` の系列にある機能であり、
**「ジョブキューを DB で作るときの定石」として Phase 4 の題材にもなる**。

### 送信は at-least-once であって exactly-once ではない

メール送信が成功した直後、`status` を更新する前にプロセスが落ちると、
その行は再び `pending` として拾われ、**同じメールが 2 通送られる**。

これを防ぐには送信側に冪等キーが要るが、SMTP にはその仕組みがない。
問い合わせ通知が稀に重複するのは許容し、
**送信済みの取りこぼし (at-most-once) にはしない**方を選ぶ。
問い合わせが届かないほうが、2 通届くより悪い。

`attempt_count` に上限を設け、超えたら `failed` にして打ち切る。
無限にリトライすると、送信できないメールが延々とプロバイダを叩き続ける。

## 決定 2: 自動返信は「検証済みのアドレス」にだけ送る

- 日付: 2026-08-18 に改訂。初版 (2026-08-05) は「自動返信を送らない」だった

### 初版の決定と、その理由

「お問い合わせありがとうございます」を**入力されたアドレス**に返す機能は作らない。

そのアドレスは検証されていない。他人のアドレスを入力すれば、
**このシステムを踏み台にして任意のアドレスへメールを送れる**。
内容の一部 (問い合わせ本文) を含めれば、実質的な迷惑メール送信機になる。

**この禁止は今も生きている。** 変わったのは「送らない」の理由が
アドレスの側にあったこと ——「入力された値だから送れない」のであって、
「本人に控えを返すこと」自体が悪かったわけではない。

### 「検証する」には 2 つの意味がある

|  | 中身 | 踏み台への効き目 |
| --- | --- | --- |
| 形式・送達性 | 構文が正しい / ドメインが実在する | **無い** |
| 所有権 | 書いた人がそのアドレスを受け取れる | **これだけが効く** |

前者は `normalizeEmail` が既にやっている。ここをいくら厳しくしても、
「実在するアドレス」であることと「入力した人の持ち物」であることは
無関係なので、踏み台の性質は 1 mm も変わらない。
むしろ実在確認を通すと、**送りつける先の精度が上がるだけ**になる。

### 所有権の確認には循環がある

所有権を確認する手段はメールを送ることしかない。
つまり **「未検証のアドレスへ一切送らない」は原理的に達成できない** ——
確認メール自体が未検証のアドレス宛の送信になる。

double opt-in を入れて到達できるのは、次の状態でしかない。

| | 送らない (初版) | double opt-in |
| --- | --- | --- |
| 任意の本文を他人へ配送 | 起きない | **消える** (確認メールは固定文面) |
| 同じ相手へ繰り返し送る | 起きない | **残る** (メール爆撃) |

「踏み台が消える」のではなく、**迷惑メール送信機がメール爆撃器に
格下げされる**だけになる。後者を抑えるには、IP 単位とは別に
**アドレス単位のクールダウン**が要る。

### 検証済みのアドレスは、既に 1 つ持っている

[ADR 0005](0005-authentication.md) 決定 3 は
**`email_verified` が false の ID トークンを受け付けない**と決めており、
`UpsertUser` はログインのたびに `users.email` を書き直している。

**IdP が確認し、鮮度も保たれているアドレス**が既に手元にある。
新しい機構をひとつも足さずに、控えを返せる相手がいる。

### 決定

**ログイン済みの問い合わせにだけ、`users.email` 宛に控えを送る。**

- 送り先は **`user_id` から引き直した `users.email`**。
  **フォームの入力欄の値ではない** —— 入力欄は `users.email` を
  初期値として埋めるだけで、利用者は書き換えられる。
  「ログイン済みだから入力値を信じる」にすると踏み台がそのまま生きる
- 匿名の問い合わせには**送らない。** double opt-in は入れない
- 差出人・件名はこちら側で組み立てる (決定 3 と同じ)

### 匿名に double opt-in を入れなかった理由

足すもの: 確認用のテーブル 1 枚、トークン (ハッシュで保存)、検証の経路 1 本、
送信種別の分岐、アドレス単位のクールダウン。加えて、

- **リンクのクリックだけで確定させられない。**
  メールクライアントのリンクプリフェッチで勝手に消費される
- **トークンが URL に載る** ので、ログの扱い
  ([ADR 0010](0010-log-pipeline.md)) と当てる必要がある
- **決定 1 と噛み合わない。** 「保存できた時点で失われない」を守るなら
  検証を受付の条件にできず、「受理は済んだ、控えが要るならリンクを踏んで」
  という後追いの形にしかならない

これで得るのが「ありがとうございます」の 1 通になる。
**受理が伝わっていないわけではない** —— `202` を受けた画面が既に伝えている。
割に合わないので入れない。**効かなくなってから** (= 控えが無いことで
実際に困る声が出てから) 考える。

### 送るのは best-effort

控えの送信は**リトライしない。** 運営への通知を確定 (`MarkSent`) した
**後**に 1 回だけ試し、失敗したら記録だけ残す。

- リトライするには行に「控えを送ったか」を持たせることになり、
  列が増えるうえ **`status = 'sent'` が何を意味するのかが 1 行で
  言えなくなる**
- 確定の**前**に送ると、控えの SMTP の往復ぶんだけ
  「運営には届いたが行は pending」の窓が広がる。そこで落ちれば
  **運営への通知がもう 1 通届く**

決定 1 が守ると決めたのは運営への通知だけで、控えはその外側にある。

### 「入力値へは送らない」を型で持つ

送り先の取り違えは**約束では守れない**。`Message.Email` (入力値) も
`users.email` も同じ `string` なので、入れ替えてもコンパイルは通る。

`model.VerifiedEmail` を作り、`MailSender.SendAutoReply` の宛先は
この型しか受け取らないようにした。**生成できるのは `users.email` を
読むアダプタ 1 か所だけ**なので、入力値を宛先へ渡す経路は書けない。

`normalizeLine` が「ヘッダに入れない」約束と入力検査を二重にしているのと
同じ考え方を、値の出どころに適用した形になる。

### 運営宛の通知には 2 つのアドレスを並べる

```
メールアドレス (入力値・未検証): typed-in@example.com
メールアドレス (検証済み・控えの送付先): account@example.net
```

**食い違っていること自体が情報**になる ——
他人のアドレスを入力した問い合わせが、対応する人の目に見える。
返信してよいのは後者だけになる。

## 決定 3: メールヘッダにユーザー入力を入れない

差出人・宛先・件名はすべてこちら側で組み立てる。
ユーザー入力は**本文にのみ**入れる。

> **宛先だけは 2 通りある** (決定 2 の改訂)。運営の固定アドレスか、
> `users.email` から作った `VerifiedEmail` のどちらか。
> **どちらも利用者が入力した文字列ではない。**
> 控えの件名にも入力を差し込まない —— 「本人宛だから安全」にすると、
> ヘッダに入力が入る経路が 1 つでき、それが後から他の宛先へ流用される。

`Reply-To` に入力されたアドレスを設定すると返信が楽になるが、
ヘッダ値に改行 (`\r\n`) を注入されると、
任意のヘッダを追加できる (**メールヘッダインジェクション**)。
`Bcc` を足せば、これも踏み台になる。

どうしても `Reply-To` を使う場合は、
アドレスの厳密な検証と制御文字の除去を通したうえで設定する。
初期実装では設定しない。

## 決定 4: 匿名でも問い合わせできる

問い合わせは「ログインできない」という内容も含みうるため、
ログインを必須にすると詰む。

ログイン済みの場合はメールアドレスと表示名を初期値として埋め、
`user_id` を記録する。匿名の場合は NULL。

### スパム対策

外部に開いた書き込み口なので、放置すると必ず荒らされる。

| 対策 | 内容 |
| --- | --- |
| レート制限 | IP 単位。一定時間あたりの投稿数を制限する |
| 長さ制限 | 本文・氏名・件名それぞれに上限。DB の CHECK 制約でも縛る |
| honeypot | 画面上非表示のフィールドを 1 つ置き、埋まっていたら破棄する |

CAPTCHA は入れない。外部サービス依存とプライバシーの話が別途発生し、
この規模では honeypot + レート制限で足りる。
効かなくなってから入れる。

#### レート制限をどこで数えるか

**アプリのメモリ上で数えると、複数インスタンスでは効かない。**
ECS のタスクが N 個あれば、実質 N 倍まで通ってしまう。
[ADR 0006](0006-view-count-and-popularity.md) の閲覧数バッファが
「タスク数に比例してフラッシュが増える」のと同じ構造の問題になる。
違いは、閲覧数は多少ずれてよいが、**レート制限はずれると意味を失う**点にある。

問い合わせに限れば、**`contact_messages` を数えるだけで足りる**。

```sql
SELECT count(*) FROM contact_messages
WHERE client_ip = $1 AND created_at > now() - interval '1 hour';
```

そもそも書き込み量が少ない (1 日数十件を想定) ため、
専用のカウンタストアを用意する必要がない。
そのため `contact_messages` に `client_ip INET` を持たせる。

**この方法は問い合わせだから成立する。**
コメント投稿や画像アップロードに同じレート制限をかける場合、
毎リクエストで集計クエリを走らせることになり、そのままでは使えない。
その段階になったら WAF のレート制限ルール (構成図に配置済み) か、
Redis での集計を使う。

## スキーマ

```sql
CREATE TABLE contact_messages (
    id              BIGINT      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id         BIGINT      REFERENCES users(id),   -- 匿名は NULL
    name            TEXT        NOT NULL,
    email           TEXT        NOT NULL,
    subject         TEXT        NOT NULL,
    body            TEXT        NOT NULL,
    client_ip       INET,                               -- レート制限の集計に使う
    status          TEXT        NOT NULL DEFAULT 'pending',
    attempt_count   INT         NOT NULL DEFAULT 0,
    last_error      TEXT,
    next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    sent_at         TIMESTAMPTZ,

    CONSTRAINT contact_status_valid CHECK (status IN ('pending', 'sent', 'failed')),
    CONSTRAINT contact_name_length    CHECK (char_length(name)    BETWEEN 1 AND 100),
    CONSTRAINT contact_subject_length CHECK (char_length(subject) BETWEEN 1 AND 200),
    CONSTRAINT contact_body_length    CHECK (char_length(body)    BETWEEN 1 AND 5000)
);

-- ワーカーが拾う行だけを索引に載せる (threads_alive_id_desc_idx と同じ考え方)
CREATE INDEX contact_pending_idx
    ON contact_messages (next_attempt_at, id)
    WHERE status = 'pending';

-- レート制限の集計用
CREATE INDEX contact_rate_limit_idx ON contact_messages (client_ip, created_at);
```

`client_ip` は個人データにあたるため、無期限には保持しない。
送信済みの古い行から `client_ip` を NULL にする運用を、
ログの保持期間 ([ADR 0010](0010-log-pipeline.md) 決定 6) と揃える。

リトライ間隔は指数バックオフとし、`next_attempt_at` に次回時刻を書く。
Phase 2 の直列化失敗リトライと同じ考え方だが、
あちらはプロセス内、こちらは DB に状態を持つ点が違う。

## 引き受けるコスト

- **「保存されたが送られていない」状態が存在する。**
  ワーカーが止まっていることに気づく仕組みがないと、
  問い合わせが静かに溜まり続ける。`pending` の最古の行の経過時間を
  メトリクスとして出す
- **メールが重複しうる** (at-least-once)。運用として受け入れる
- **SES の初期状態はサンドボックス。** 検証済みアドレス以外に送れない。
  理想構成としては解除申請が前提になる点を構成図に注記する。
  **控え (決定 2) はこの制約をまともに受ける** —— 宛先が利用者ごとに
  変わるため、サンドボックスでは全滅する。best-effort なので
  問い合わせ自体は届くが、`contact_auto_reply_failed` が鳴り続ける
- **控えの失敗ログに宛先が混じりうる。** 自分では載せていないが、
  `RCPT TO` の応答文にはアドレスが入ることがある
  (`550 ... <a@example.com> rejected`)。消す側に倒すと
  送れない理由が運用から見えなくなるので、載りうることを引き受ける
- **控えが届かないことは、行のどこにも残らない** (best-effort)。
  ログにしか出ないので、集計は `infra/athena/queries/contact-auto-reply.sql`
  に置いた。**`failed` の件数ではなく `sent` の最終時刻を見る** ——
  ワーカーが止まると失敗すら出なくなる (下記 9 と同じ構造)
- **ワーカーのライフサイクルが増える。**
  現在 API プロセスは HTTP サーバだけを持っている。
  ここに閲覧数のフラッシュ ([ADR 0006](0006-view-count-and-popularity.md))、
  画像の孤児回収 ([ADR 0007](0007-image-storage.md))、
  期限切れセッションの削除 ([ADR 0005](0005-authentication.md))、
  期限切れ冪等キーの削除 ([ADR 0015](0015-idempotency.md))、
  メール送信の 5 つの定期処理が加わる。
  **個別に goroutine を撒くのではなく、起動・停止を一元管理する
  仕組みを先に用意する**。graceful shutdown で全部を待てないと、
  終了時に閲覧数がロストする

## 実装して分かったこと

`000012` / `internal/contact` / `internal/infrastructure/mail` を実装した時点の記録。

### 1. 決定 1 の図のとおりに実装すると、SMTP の往復ぶん行ロックが残る

この ADR の図は「pending を取り出す (`FOR UPDATE SKIP LOCKED`) → メール送信
→ status 更新」を 1 つの流れとして書いている。素直に読むと、
**3 つが 1 つのトランザクションに入る。**

そうすると、外部サービスの応答を待つあいだ行ロックを保持し続け、
接続プールも 1 本占有する。SMTP の往復は数百 ms から数秒で、
相手が無応答なら締め切りまで伸びる。

そこで**確保だけを 1 文で終わらせて即コミットする**形に変えた。

```sql
UPDATE contact_messages
SET attempt_count   = attempt_count + 1,
    next_attempt_at = now() + $1::interval   -- リース
WHERE id IN (
    SELECT id FROM contact_messages
    WHERE status = 'pending' AND next_attempt_at <= now()
    ORDER BY next_attempt_at, id
    FOR UPDATE SKIP LOCKED
    LIMIT $2
)
RETURNING ...;
```

`SKIP LOCKED` は残っている —— 消えたのは「送信中もロックを持ち続ける」
ほうだけになる。送信中の行を他のインスタンスから隠すのは、
**ロックではなく `next_attempt_at` の先送り (リース)** が担う。

画像の回収 ([ADR 0007](0007-image-storage.md)) が
「確保 → S3 削除 → DB 反映」と 3 段階に割っているのと同じ形になった。
**外部サービスを呼ぶ定期処理は、どれもこの形に落ちる**らしい。

**at-least-once であることは変わらない。** 送信の直後、status を書く前に
落ちれば、リース切れの後にもう一度送られる。決定 1 が引き受けた性質のまま、
起こる条件が「クラッシュしたとき」に狭まっただけになる。

### 2. スキーマに長さ制約の穴が 1 つ空いていた

決定 4 の表は「本文・氏名・件名それぞれに上限」と書いており、
下のスキーマもその 3 つに `CHECK` を置いている。
**`email` だけ野放しだった。**

上限の無い列が 1 つでも残ると、そこが長さ制限の抜け道になる ——
5000 文字のアドレスを書けば、結局 1 件あたりの容量は同じことになる。
`contact_email_length CHECK (char_length(email) BETWEEN 3 AND 254)` を足した
(254 は RFC 5321 のアドレス長の上限)。

**上限は 3 か所で同じ値を持つ** (この ADR のスキーマ / ドメインの定数 /
仕様書の `maxLength`)。揃っていることは `message_test.go` が
実際にファイルを読んで検査する —— ADR 0011 の enum 検査と同じ形になる。

### 3. `ADR 0016` の索引表から外部キーの索引が抜けていた

[ADR 0016](0016-schema-and-indexes.md) の索引表は、`contact_messages` に
2 本 (`(next_attempt_at, id) WHERE pending` と `(client_ip, created_at)`) を
挙げている。これはこの ADR のスキーマからの転記で、
**`user_id` の索引が入っていない。**

同じ ADR 0016 が「外部キーには必ず索引を貼る (区分 A)」と決めており、
PostgreSQL は外部キーを張っても参照する側に索引を作らない。
`reports.resolved_by` で一度踏んだのと同じ形なので、
`contact_user_idx` を部分索引 (`WHERE user_id IS NOT NULL`) で足した。

消し込み用の `contact_ip_scrub_idx (created_at) WHERE client_ip IS NOT NULL`
も足している。述語に条件を含めると、**消し込みが進むほど索引が小さくなる**
(`images_reclaimable_idx` と同じ形)。

### 4. 決定 3 は「ヘッダに入れない」だけでは足りない

決定 3 はヘッダへの注入を封じているが、**本文にも 2 つ穴がある。**

| 穴 | 起きること |
| --- | --- |
| 1 行 998 オクテットの上限 (RFC 5322) | 改行なしで 5000 文字書かれると超える |
| 行頭の `.` (RFC 5321 のドット詰め) | `.` だけの行がメッセージの終端として解釈され、そこで本文が切れる |

本文を **base64 (`Content-Transfer-Encoding: base64`)** にすると両方消える。
76 文字で折り返すので 1 が消え、`.` が行頭に出ないので 2 も消える。

2 は Go の `smtp.Client.Data()` (textproto の `DotWriter`) がドット詰めを
行うため、素通しでも壊れない。**それでも base64 にしたのは、正しさが
送信ライブラリの実装依存にならないようにするため**になる。

### 5. 受付を「設定が無ければ 503」にしなかった

認証 ([ADR 0005](0005-authentication.md) 決定 4) と画像
([ADR 0007](0007-image-storage.md)) は「設定が無ければその経路だけ 503」で
揃えてある。問い合わせだけ**その形にしていない。**

メールの設定が無くても `POST /contact` は 202 を返し、
送信ワーカーだけが登録されない。**503 で断ると、その間に来た問い合わせが
そのまま失われる**ためになる —— 決定 1 が「保存が成功した時点で内容は
失われない」と決めた以上、受付を止める理由が無い。

画像やログインは、失敗した利用者がもう一度試しに来る。
**問い合わせは来てくれない。**

### 6. IPv4 射影された IPv6 でレート制限を回避できた

`client_ip` を `INET` にしたのは「`192.168.0.1` と `192.168.000.001` が
別の値にならないため」だった (決定 4)。同じ問題がもう 1 つあり、
**`::ffff:192.0.2.1` と `192.0.2.1` は `netip.Addr` としては別の値**になる。

そのまま保存すると、v6 で射影された表現に切り替えるだけで
別人として数えられる。保存の入口で `Unmap()` して 1 つに寄せた。
**レート制限はずれると意味を失う**ので、ここは近似で済ませられない。

### 7. `RESOURCE_EXHAUSTED` を実装に落とした

[ADR 0013](0013-http-defense.md) 決定 3 の表が
「429 = `RESOURCE_EXHAUSTED`、出典は ADR 0008」と既に決めていた。
仕様書の `enum` と `apperr` の番兵エラーを 1 対 1 で足している
(決定 3 の「追加は `api/openapi.yaml` から」に従う)。

**応答に上限も窓も載せていない。** 「何件までなら通るか」は
攻撃側にだけ有用な情報になる。`Retry-After` も付けない ——
移動窓なので正確な待ち時間を出すには集計クエリがもう 1 本要り、
**弾いた要求のために DB を叩く**ことになる。

### 8. honeypot の代償はブラウザの自動入力

決定 4 は honeypot を「画面上非表示のフィールドを 1 つ置き、
埋まっていたら破棄する」とだけ書いている。埋まった要求は
**エラーにせず 202 を返す** —— 400 にすると「この項目が引き金だ」と
ボット側に教えることになり、次の版では空で送られてくる。

その結果、**自動入力に埋められた人間の問い合わせも黙って消える。**
フォーム側で `autocomplete="off"` / `tabIndex={-1}` / `aria-hidden` を
付けて確率を下げているが、0 にはできない。honeypot を選ぶ以上、
ここは引き受けるコストになる。

### 9. 観測は「値が閾値を超えたこと」だけでは足りない

「引き受けるコスト」に挙げた「`pending` の最古の行の経過時間を
メトリクスとして出す」は、送信ワーカーの中で出している
(`contact_pending_age`)。

**ワーカーごと止まればこのログも出なくなる。** 監視側では
「値が閾値を超えたこと」ではなく、**「一定時間このイベントが
出ていないこと」も見る必要がある** —— 検知したい状態そのものが、
検知の手段を止める形になっている。

## レビューで見つかったこと (2026-08-17)

PR #35 のレビュー 1 往復で出た指摘と、それを直す過程で見つけた実バグ。

### 10. `IN (SELECT ... LIMIT n)` では件数を絞れなかった (実バグ)

確保のクエリを
`WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED LIMIT $2)` と書いていた。
**LIMIT が効かず、`pending` の全件を確保していた。**

```
Update on contact_messages (rows=4)
  -> Nested Loop Semi Join (rows=4)
       -> Seq Scan on contact_messages (rows=4)
       -> Subquery Scan (rows=1, loops=4)   ← 外側の行ごとに再実行
            -> Limit (rows=1, loops=4)
```

プランナが半結合に展開すると副問い合わせは外側の行ごとに評価され、
LIMIT は「1 回の評価あたり」にしか効かない。

実害は 2 つある。

- バッチサイズ (既定 20) が意味を失う。溜まっていれば 1 周回で全件を
  送ろうとし、SMTP の往復ぶんシャットダウンの待ち合わせが伸びる
- 全件を同時にリースするので、途中で落ちるとリース切れまで大量の行が止まる

`WITH claimed AS (SELECT ... FOR UPDATE SKIP LOCKED LIMIT $2)` +
`UPDATE ... FROM claimed` に変えた。**`FOR UPDATE` を含む CTE は
インライン展開されない** (ロックという副作用を持つため) ので、
1 回だけ評価されることが規定の挙動として保証される。
消し込み (`ScrubContactClientIPs`) も同じ形に揃えた ——
あちらは実測時に Hash Semi Join (`loops=1`) で LIMIT が効いていたが、
**それは統計次第で変わる**ので、プランの選択に委ねない。

> **これは live テストを直したから見つかった。** 初版のテストは確保を
> 2 回続けて呼ぶだけで、ロック中の行が 1 つも無い状態を測っていた
> (下記 11)。ロックを保持した状態を作るようテストを書き直したところ、
> **隣のテストが「4 件確保できた (want 2)」で落ちた。**

### 11. SKIP LOCKED の live テストが SKIP LOCKED を通っていなかった

「同時に確保しても同じ行が配られない」と書いたテストが、
確保を**逐次に** 2 回呼んでいた。2 回目の時点で 1 回目は既にコミット済みで、
ロックされた行が 1 つも無い ——
**クエリから `SKIP LOCKED` を消しても緑のまま**だった。

別のトランザクションで `SELECT ... FOR UPDATE` を保持したまま確保し、
締め切り付きの context で呼ぶ形に直した。`SKIP LOCKED` が無ければ
ロック解放まで待たされ、締め切りで落ちる。

### 12. `QUIT` の失敗を送信の失敗にしていた

`w.Close()` (DATA の終端) が成功した時点でメールは届いている。
その後の `client.Quit()` のエラーをそのまま返していたため、
**221 が返らないサーバが相手だと、同じ問い合わせが上限まで届いたうえで
`failed` として打ち切られる** (8 通届いて ERROR が鳴る)。
記録 (`mail_quit_failed`) だけ残して成功として扱う。

### 13. `X-Forwarded-For` を無条件に信じていた

gin の既定はすべての送信元を信頼するプロキシとみなす。
`SetTrustedProxies` を呼んでいなかったので、`ClientIP()` は
**XFF の最も左 = 送信者が自由に書ける値**を返していた。

決定 4 のレート制限は、ヘッダ 1 本で回避できた。
**逆に他人の IP を名乗って 5 件送れば、その IP を 1 時間締め出せた。**

「偽装されうる値」であること自体は IP でレート制限する以上ついて回るが、
それは**信頼できるプロキシが XFF を付け替える前提**での話になる。
境界を宣言していない状態では、プロキシが 1 つも無くても偽装できた。

`TRUSTED_PROXIES` を足し、**既定は空 (誰も信じない)** にした。
閲覧数の重複抑制 ([ADR 0006](0006-view-count-and-popularity.md)) も
同じ値を使うので、そちらの精度もこの設定で決まる。

### 14. honeypot に `maxLength` を置くと honeypot が漏れる

`website` に `maxLength: 200` を書いていた。仕様検証ミドルウェアは
ハンドラより手前で弾き、**応答に `website` というフィールド名が載る。**
決定 4 が「400 にすると引き金を教えることになる」として避けたことを、
スキーマ側で成立させていた。制約を外した
(要求全体の大きさは本文サイズの上限が抑える)。

### 15. 受理時刻の表記で honeypot を判別できた

成功時は `saved.CreatedAt` をそのまま返しており、pgx は `timestamptz` を
**プロセスのローカル時刻**として復元する。honeypot 経路は
`time.Now().UTC()` なので、TZ が UTC でない環境では
`+09:00` と `Z` で表記が分かれる ——
**ID を返さないことで消したはずの手掛かりが、時刻の形で戻っていた。**
UTC に揃えた。

## 決定 2 を改訂して分かったこと (2026-08-18)

### 16. 列を足さずに済んだ —— 宛先は送信の直前に引く

素直に考えると `contact_messages` に `reply_to_email` を足して
受付時に写し取る形になるが、**そうしなかった。**

[ADR 0014](0014-author-resolution.md) が「`thread` は `user` を
import できないが、**JOIN を書ける場所はアダプタだけ**」と決めている。
同じ形で、確保のクエリ (`ClaimPendingContacts`) に
`LEFT JOIN users` を足せば済む。

| | 列を足す | 送信時に引く (採用) |
| --- | --- | --- |
| マイグレーション | 要る | 要らない |
| 退会した利用者 | **送ってしまう** (写した時点では在籍) | `deleted_at` で外れる |
| アドレスの鮮度 | 受付時点で固定 | 最新 (リトライ中に変わっても追う) |
| 同じ値の重複 | 2 か所に載る | 1 か所 |

「受付時点のアドレスに固定すべきでは」という筋はあるが、
リトライの上限は 91 分しかなく、その間にアカウントのアドレスが
差し替わる状況は既にアカウント自体が乗っ取られている。
**そこを防ぐのは控えの宛先の仕事ではない。**

### 17. `UPDATE ... FROM` の RETURNING では、sqlc が LEFT JOIN を追わない

最初は確保の UPDATE にそのまま結合を足した。

```sql
UPDATE contact_messages
SET ...
FROM claimed
     LEFT JOIN users ON users.id = claimed.user_id AND users.deleted_at IS NULL
WHERE contact_messages.id = claimed.id
RETURNING ..., users.email AS verified_email;
```

SQL としては正しいが、**sqlc が `VerifiedEmail string` を生成した**
(NULL 不可)。平の SELECT なら `*string` になる —— 同じファイルの
`threads.sql` は `author_display_name` を `*string` で出している。
外部結合の NULL 許容を追わないのは `UPDATE ... RETURNING` の経路だけらしい。

**匿名の問い合わせを 1 件確保した時点で、確保ごと落ちる。**
しかも落ちるのは「匿名の行が混ざったとき」なので、
ログイン済みの 1 件だけで試すと通る。

確保の UPDATE を CTE に押し込み、**結合を外側の SELECT に出した**。

```sql
WITH claimed AS (...), updated AS (
    UPDATE contact_messages SET ... FROM claimed WHERE ... RETURNING ...
)
SELECT updated.*, u.email AS verified_email
FROM updated
LEFT JOIN users u ON u.id = updated.user_id AND u.deleted_at IS NULL;
```

副産物として、**確保の UPDATE 文が結合を 1 つも持たなくなった。**
`LEFT` を `INNER` と書き間違える余地 (= 匿名の問い合わせだけが
永久に `pending` として残る) が、そもそも書ける場所から消えている。

### 18. live テストは 3 種類の行を同時に確保しないと意味が無い

上の 2 つ (INNER への化け / NULL の読み取り) は、
**どちらもログイン済みの 1 件だけを見ていると通ってしまう。**
`deleted_at IS NULL` を `WHERE` に書いた場合も同じ。

そのため `ClaimResolvesVerifiedEmail_Live` は
**ログイン済み・退会済み・匿名の 3 件を同時に積んで、3 件とも
確保されること**を最初に検査している。件数が 1 つでも欠けたら、
どれかの穴が開いている。

### 19. 控えに入力されたアドレスを書き写さない

控えの本文に「ご入力のアドレス: ...」を載せると親切に見えるが、
**入力欄には他人のアドレスが書かれていることがある。**
控えが届くのは登録アドレスの持ち主なので、
これは**他人のアドレスを本人以外に見せる経路**になる。

代わりに「フォームに入力されたアドレスへは送っていない」とだけ書く。
何が食い違っているかは運営宛のほうにだけ出す。

## 実配送を確認して分かったこと (2026-08-18)

Mailpit (compose) に対して、ログイン済み・匿名・退会済みの 3 経路を
実際に流した記録。**ここまでは偽 SMTP サーバに対する検査しかなかった。**

### 20. Athena のテーブル定義に contact 系の列が 1 つも無かった

控えの失敗を数えようとして気づいた。Phase 8 で `contact_*` のイベントを
出し始めたとき、[ADR 0010](0010-log-pipeline.md) の DDL
(`infra/athena/table.sql`) を更新していなかった。

同じファイルの「罠 2」が警告しているとおり、**Athena はスキーマオンリードで
エラーにならず静かに NULL になる。** `contact_id` も `client_ip` も
`count` / `limit` も、宣言が無いので**本番では最初から見えていなかった。**

「集計クエリを足す」以前に、**集計できる状態ですらなかった**ことになる。
6 列を足した。`count` と `limit` は予約語なので、クエリ側では
二重引用符が要る (DDL のバッククォートでは通る)。

> **手元の `make logs-verify` はこれを検出できたはず**だった
> (`verify.py` が「着地した列のうち DDL に無いもの」を見る)。
> 実環境が要るターゲットなので CI に載っておらず、
> 問い合わせの実装以降に回した形跡が無い。

### 21. 「セッション行を直接作る」は、そのままでは通らない

[ADR 0005](0005-authentication.md) の検証記録にある方法を踏襲したが、
**`sessions.id` に生のトークンを入れても認証されない。**
保存されているのはトークンの **SHA-256** で、`SessionToken.Hash()` が
その変換を担っている (ADR 0005 決定 1)。

素で入れた場合、`POST /contact` は **401 にならず 202 を返す** ——
問い合わせは匿名として受理されるため。`user_id` が NULL になって初めて
「セッションが効いていない」と分かる。

**最初の実配送は、これで控えが 1 通も出なかった。** ログには
`contact_auto_reply_sent` も `_failed` も出ず、
「送っていない」ことだけが分かる形になっていた ——
設計どおりではあるが、**原因の切り分けには `user_id` を見る必要がある。**

### 22. 実物で確認できたこと

`sha256` を通したセッションで流し直した結果。

| 経路 | 運営宛 | 控え |
| --- | --- | --- |
| ログイン済み | 届く | **`users.email` に届く** |
| 匿名 | 届く | 送られない |
| 退会済み | 届く | 送られない |

控えの生ヘッダで確かめたもの:

```
Return-Path: <contact@bbs.example.com>
Received: ... for <registered@example.net>;      ← 封筒の宛先
From: contact@bbs.example.com
To: registered@example.net
Auto-Submitted: auto-replied
Content-Transfer-Encoding: base64
```

- **入力欄に書いた `someone-else@example.com` は、控えのどこにも現れない**
  (ヘッダ・本文とも)
- `Cc` / `Bcc` は無く、運営のアドレスも混ざらない
- 本文の日本語が base64 の往復で壊れていない

運営宛には 2 つのアドレスが並び、**食い違いが目に見える**:

```
メールアドレス (入力値・未検証): someone-else@example.com
メールアドレス (検証済み・返信先): registered@example.net
  控え: このアドレス宛に送付を試みます (best-effort。届いたかは contact_id でログを参照)
```

> **退会済みの経路は、通ったところが想定と違った。** セッションの照合が
> 先に退会を弾くので、`user_id` が NULL のまま受理される ——
> 決定 2 が用意した `LEFT JOIN ... deleted_at IS NULL` ではなく、
> 匿名と同じ道を通っている。あちらは live テストのほうで測っている
> (受付後に退会した場合がそれに当たる)。

### 23. 集計クエリが、どこでも一度も実行されていなかった (レビュー指摘)

初版は `from_iso8601_timestamp` と 2 引数の `if()` で書いていた。
**どちらも Trino 専用**で、手元の DuckDB では構文エラーになる。

`infra/athena/queries/` は compose で `/queries` にマウントされ、
`make logs-query Q=/queries/xxx.sql` で回せる ——
**同じディレクトリの他 4 本は全部通り、これだけが落ちた。**
Athena でも実行していないので、**書いたきり一度も動いていない SQL**
だったことになる。

日付の切り出しは `substr(time, 1, 10)` にした。`CAST(time AS TIMESTAMP)` は
DuckDB では通るが、**Trino では `T` 区切りと末尾の `Z` の扱いが変わる** ——
手元で確かめられないものを、本番の唯一の集計手段に置かない。
`time` は RFC3339 なので先頭 10 文字がそのまま日付になり、
文字列比較でも時系列順に並ぶ。

**5 本すべてを DuckDB 1.4.1 (Dockerfile の固定版) で実行して確認した。**

### 24. 「一定時間 sent が出ていない」だけでは分母が無い

上の 9 と同じ話をクエリに書いたが、**書いた条件がそのままでは使えなかった**
(レビュー指摘)。控えのイベントだけを集めると、
**問い合わせが 1 件も来なかった日**と**ワーカーが止まった日**が
同じ見え方になる。この規模では前者が平常なので、アラートは鳴りっぱなしになる。

`contact_received` を同じ集計に入れて分母にした。
見るべきは **received > 0 なのに sent も failed も出ていない日**。
控えは匿名には送らないので、received と sent が一致しないこと自体は正常になる。

### 25. 手作業の列の洗い出しは、やはり漏れた

20 で足した 6 列は**手で数えたもの**で、レビューでさらに 3 列
(`oldest_age_ms` / `smtp_host` / `starttls`) の漏れが出た。
とくに `oldest_age_ms` は `contact_pending_age` が載せる唯一のフィールドで、
**送信ワーカーの詰まりを示す本命の信号**になる。

数え方を変えても漏れるので、**検査に落とした** ——
`.github/scripts/verify-log-events.py` が、ソース中の全 slog フィールドと
`infra/athena/table.sql` の列宣言の差分を取り、CI で落とす。
