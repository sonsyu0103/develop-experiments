# ADR 0007: 画像はアップロード時に再エンコードし、API を経由させる

- ステータス: **採用 (実装前)**
- 日付: 2026-08-05

## 背景

画像を 3 か所で扱う。

| 用途 | 添付先 | 想定サイズ |
| --- | --- | --- |
| コメント添付 | `comments` | 大きめ (本文の一部) |
| プロフィール画像 | `users` | 小さい (正方形) |
| スレッドアイコン | `threads` | 小さい (正方形) |

[ADR 0005](0005-authentication.md) の権限モデルに従い、
**画像を投稿できるのはログイン済みユーザーだけ**とする。
匿名で任意のバイト列をストレージに置けると、
容量の消費と違法コンテンツの設置が追跡不能な形で可能になるため。

## 決定 1: アップロードは API を経由させる (署名付き URL を使わない)

### 検討した選択肢

#### A. S3 の署名付き URL でブラウザから直接アップロードさせる

- 利点: API サーバが画像の帯域とメモリを持たない。スケールする
- 欠点: **API がバイト列を見ないまま受け入れることになる。**
  署名に `Content-Type` を含めても、それは自己申告であって中身の保証にならない。
  検証するには結局アップロード後にオブジェクトを読み直すか、
  別のトリガ (Lambda など) を立てる必要があり、
  検証の責任がコンポーネントをまたいで分散する。
  また「アップロード完了」を API が知らないため、2 フェーズの整合が要る

#### B. API が multipart/form-data で受け取り、ストレージへ書く (採用)

- 利点: 検証が API 1 か所に閉じる。DB とストレージの整合を 1 リクエストで扱える
- 欠点: API サーバが帯域とメモリを消費する

### 決定

**B を採用する。**

画像の検証はセキュリティの要であり、これを分散させる代償のほうが、
帯域を持つ代償より大きい。この規模で API の帯域が先に問題になることはない。

**移行条件を明記しておく。** 以下のいずれかに達したら A を再検討する。

- 画像アップロードが API の帯域またはメモリの支配的な要因になったとき
- 1 ファイルの上限を数十 MB 以上に引き上げる必要が出たとき

## 決定 2: 受け取った画像は必ず再エンコードする

**アップロードされたバイト列をそのまま保存しない。**
デコードして、リサイズし、こちらの指定した形式でエンコードし直したものだけを保存する。

これ 1 つで、画像アップロードの典型的な攻撃面がまとめて閉じる。

| 攻撃 / 問題 | 再エンコードで消える理由 |
| --- | --- |
| MIME 偽装 (`.png` を名乗る実行ファイル) | デコードできない時点で弾かれる |
| EXIF に含まれる位置情報 | 再エンコード後のメタデータは自前で書く |
| SVG に埋め込んだスクリプト | そもそも許可形式に入れない |
| ポリグロット (画像かつ HTML など) | 出力はこちらが生成したバイト列になる |

### 検証の順序

**デコードする前に寸法を読む。**

```
1. Content-Length / 実バイト数の上限チェック      (既定 5 MiB)
2. マジックナンバーで形式を判定 (拡張子と Content-Type は信用しない)
3. ヘッダだけをデコードして width × height を取得   ← image.DecodeConfig
4. ピクセル数の上限チェック                        (既定 5000 万画素)
5. ここで初めて全体をデコード
6. リサイズ + 再エンコード
```

**4 を 5 より前に置くことが要点になる。**
「圧縮後は数十 KB だが展開すると数十 GB」という画像
(decompression bomb) は、サイズ上限だけでは防げない。
`image.DecodeConfig` はヘッダのみを読むため、
展開せずに寸法を知ることができる。

### 許可する形式

入力: JPEG / PNG / WebP
出力: WebP (非対応環境向けのフォールバックが必要になれば JPEG を併置)

**SVG は許可しない。** ベクタ形式はスクリプトと外部参照を含められるため、
「画像」として扱うと XSS と SSRF の経路になる。
再エンコードによる無害化も、ラスタ化してしまえば
ベクタである意味がなくなるので成立しない。

## 決定 3: DB を先に書き、後から確定させる

ストレージと DB は別のシステムなので、片方だけ成功する状態が必ず起きうる。
どちらの順序でも孤児は生まれるが、**追跡できる孤児**にする。

```
1. images に status = 'pending' で INSERT   ← ここで object_key を決める
2. ストレージへ PUT
3. images を status = 'committed' に UPDATE
4. 添付先 (comments / users / threads) から参照させる
```

2 または 3 で落ちた場合、`pending` の行が残る。
**一定時間以上 `pending` のままの行を回収するバッチ**で、
ストレージ側のオブジェクトと DB 行の両方を削除する。

> **[ADR 0016](0016-schema-and-indexes.md) で一部を上書きした。**
> DB 行まで削除してよいのは `pending` の孤児だけになる。
> モデレーターが削除した画像 (`status = 'deleted'`) は
> コメントやスレッドから参照されているため、
> 行を消すと外部キー違反になり、かつ
> 「画像は削除されました」と「元から画像なし」を区別できなくなる。
> **`deleted` は S3 のオブジェクトだけを消し、DB 行は残す。**

逆順 (ストレージが先) にすると、DB に記録のないオブジェクトが残り、
これは全件リストと突き合わせないと見つけられない。

### オブジェクトキーにユーザー入力を使わない

キーは UUID で生成する。
アップロード時のファイル名は、表示用途で必要なら別カラムに持つ。

ファイル名をそのままキーにすると、パストラバーサル、
他ユーザーのオブジェクトの上書き、キーの衝突がすべて可能になる。

## 決定 4: 配信は公開読み取り (バケットは直接公開しない)

掲示板の画像は誰でも見られてよいため、
表示のたびに署名付き URL を発行する必要はない。

理想構成では CloudFront を前段に置き、
バケットへのアクセスは OAC (Origin Access Control) 経由に限定する。
**バケット自体はパブリックにしない** —— バケットを直接公開すると、
CloudFront を迂回して原本を叩けるようになり、
キャッシュもレート制限も効かない経路が残る。

ローカルは MinIO (S3 互換) を compose に追加する。
アプリ側は S3 互換のインターフェースだけを見るため、
エンドポイントの差し替えで両方に対応できる。

## 決定 5: API は絶対 URL を返す (オブジェクトキーではなく)

```json
"image": {
  "url": "https://cdn.example.com/images/018f2c....webp",
  "width": 1200,
  "height": 800
}
```

### 検討した選択肢

#### A. オブジェクトキーだけを返し、フロントで URL を組み立てる

- 利点: レスポンスが小さい。フロントがサイズ違いやフォーマット違いを自由に組める
- 欠点: **フロントが CDN のベース URL を知る必要がある。**
  Next.js では Server Component と Client Component の両方から参照できる形
  (`NEXT_PUBLIC_` 付きの環境変数) にする必要があり、
  組み立てロジックが 2 か所に散る。
  ローカル (MinIO) と本番 (CloudFront) でホストが違うことも、
  フロント側の関心事になってしまう

#### B. API が絶対 URL を返す (採用)

- 利点: **フロントは受け取った文字列を `src` に入れるだけ**になる。
  環境ごとの差を API が吸収する。ドメインを変えても API 側の変更で済む
- 欠点: レスポンスが冗長。サイズ違いを返すならフィールドが増える

### 決定の理由

**決定 1 の「移行条件」があることが決め手になる。**

将来、署名付き URL に移行した場合:

| | 絶対 URL を返していた場合 | キーを返していた場合 |
| --- | --- | --- |
| フロントの改修 | **不要** (URL の中身が変わるだけ) | 署名を要求する仕組みを作る必要がある |

移行の可能性を明記した以上、
**移行時にクライアントを改修せずに済む形**を選ぶ。

### 注意: 署名付き URL に移行したら、レスポンスのキャッシュ時間に上限が付く

現在は公開読み取りなので URL は不変であり、
API のレスポンスをいくらキャッシュしても問題ない。

署名付き URL に移行すると、URL に有効期限が付く。
**API レスポンスのキャッシュ時間が署名の有効期限を超えると、
期限切れの URL を配ることになる。**
移行時にはキャッシュ設定の見直しが必須になる。

## スキーマ

```sql
CREATE TABLE images (
    id           UUID        PRIMARY KEY,
    owner_id     BIGINT      NOT NULL REFERENCES users(id),
    kind         TEXT        NOT NULL,   -- 'comment_attachment' | 'avatar' | 'thread_icon'
    object_key   TEXT        NOT NULL UNIQUE,
    content_type TEXT        NOT NULL,
    width        INT         NOT NULL,
    height       INT         NOT NULL,
    byte_size    BIGINT      NOT NULL,
    status       TEXT        NOT NULL,   -- 'pending' | 'committed' | 'deleted'
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    committed_at TIMESTAMPTZ,

    CONSTRAINT images_status_valid CHECK (status IN ('pending', 'committed', 'deleted')),
    CONSTRAINT images_kind_valid   CHECK (kind IN ('comment_attachment', 'avatar', 'thread_icon'))
);

-- 回収バッチが拾う行。放置された pending と、削除された画像の両方を対象にする
CREATE INDEX images_reclaimable_idx
    ON images (created_at)
    WHERE status IN ('pending', 'deleted');
```

`'deleted'` は [ADR 0011](0011-moderation.md) で追加した。
投稿を論理削除してもストレージ上のオブジェクトは残るため、
**URL を直接叩けば不適切な画像が見え続ける**。
回収バッチの対象に加えることで、定期処理を増やさずに実削除まで到達させる。

添付先には `image_id UUID NULL REFERENCES images(id)` を持たせる。

- `comments.image_id` — **コメント 1 件に画像 1 枚**。
  複数枚にすると中間テーブルが要り、パーティション済みテーブルとの
  結合がもう 1 段増える。必要になってから拡張する
- `users.avatar_image_id` — NULL なら Google のプロフィール画像 (`users.avatar_url`) を使う
- `threads.icon_image_id`

`comments` はハッシュパーティション済みだが、
親テーブルへの `ALTER TABLE ... ADD COLUMN` は全パーティションに伝播する。

## モジュール構成

[ADR 0004](0004-modular-monolith.md) に従い `internal/image` を追加する。
**2 枚の arch ファイルにコンポーネントと依存を宣言する**
([ADR 0017](0017-arch-lint-and-depguard.md))。

ストレージは `domain/repository` のインターフェースとして定義し、
実装を `infrastructure/objectstorage` に置く。
`image` モジュールは S3 SDK の型を一切知らない。

## 引き受けるコスト

- **API が CPU とメモリを使う。** 再エンコードは画像 1 枚ごとに
  デコード後のピクセルぶんのメモリを確保する。
  同時アップロード数に上限を設けないと、メモリで落ちる
- **オリジナルが残らない。** 再エンコードで画質は必ず劣化する。
  「アップロードした画像がそのまま欲しい」という要求には応えられない
- **依存が増える。** WebP のエンコードは標準ライブラリにない。
  外部ライブラリのバージョンを固定して入れる
  (`Makefile` 冒頭の方針に従う)
- **回収バッチが必要になる。** 実装しないと `pending` 行と
  孤児オブジェクトが単調増加する。「後で書く」にすると書かれない
- **アップロード帯域の上限を決め打ちしている。**
  移行条件 (決定 1) を README かこの ADR で追跡し続けないと、
  問題が起きてから設計を見直すことになる
