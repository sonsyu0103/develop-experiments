# ADR 0025: 言語とフレームワークの選択 —— AI と組んで書くことを前提にする

- ステータス: **採用 (実装済み)**。ただし**この記録は後から書いた** (2026-08-27)。
  下の「なぜ後から書いたか」を参照
- 日付: 2026-08-27

## 背景

このリポジトリは Go (Gin) + PostgreSQL + Next.js で書かれている。
[ADR 0001](0001-why-postgresql.md) が PostgreSQL を選んだ理由を残している一方で、
**言語とフロントの選択には記録が無かった。**

面接でも読み手からも最初に聞かれるのはここなので、記録する。

## 検討したが採用理由にしなかったもの

[ADR 0001](0001-why-postgresql.md) がパーティショニングに対してやったのと同じで、
**「もっともらしいが、この規模では効かない理由」を先に落としておく。**

### 「Go は速い」

事実ではあるが、**この規模では言語の速度は律速にならない。**

[ADR 0009](0009-scaling-strategy.md) で見積もったピークは API 550〜4,200 RPS、
書き込みは毎秒 10〜56 件。ここで効くのは
「同一行への書き込み集中をどう捌くか」([ADR 0006](0006-view-count-and-popularity.md))
であって、言語のスループットではない。

**実際、Phase 4 の実測でボトルネックはすべて DB 側に出ている。**
言語の速度を採用理由に据えると、測る前に答えを決めたことになる。

### 「Rust なら安全」

所有権とライフタイムによる保証は本物で、並行処理が主題である以上、
**題材としてはむしろ噛み合っていた。**

採らなかったのは**学習コストと開発速度**による。
このリポジトリは 3 か月で Phase 0〜13 を通すことを前提にしており、
「言語の習得」に時間を割くと、**主題である並行制御の実測に届かない。**

つまり Rust を落としたのは技術的な優劣ではなく、**期間の制約**になる。
そこを曖昧にしない。

### 「TypeScript でフロントとバックエンドを統一する」

言語が 1 つで済む利点は認める。型定義を共有でき、
コンテキストスイッチも減る。

だが**バックエンドの機能として弱い**と判断した。
このリポジトリが扱う題材 —— goroutine による並行処理、`race detector`、
`go test -bench` による実測、単一バイナリでの配布 —— は、
Node で同じ密度にはならない。

**「言語を揃える」ことのために、主題を測る道具を手放すことになる。**

## 決定 1: バックエンドは Go

理由は 3 つ。**1 が最も重い。**

### 1. AI と組んで書くことを前提にすると、静的型が検証の足場になる

このリポジトリは**AI との共同作業を前提に設計している。**
その前提では、言語の選択基準が変わる。

生成されたコードが正しいかを、**人間が読む前に機械が弾ける**ことが効く:

- 型の不一致はコンパイルで落ちる
- `go vet` / `golangci-lint` が実行前に検出する
- `race detector` が並行処理の誤りを実行時に捕まえる

動的型だと、**同じ誤りがテストを書くまで表に出ない。**
生成量が増えるほど、この差は開く。

「AI が書けるか」ではなく「**AI が書いたものを、こちらが安く検証できるか**」で選んだ。

### 2. 主題が並行制御であり、道具が標準にある

`goroutine` / `channel` / `sync` が言語に組み込まれ、
`-race` と `go test -bench` が標準ツールにある。

[ADR 0019](0019-comment-concurrency.md) の 4 方式比較
(`make concurrency-probe`) や、
[ADR 0009](0009-scaling-strategy.md) のスケール実測 (`make scale-probe`) は、
**追加のツールを入れずに書けている。**

### 3. 「スキーマから型を生成する」が成立する

`sqlc` が SQL から、`oapi-codegen` が OpenAPI から Go のコードを生成する。
[ADR 0002](0002-openapi-direction.md) の「仕様書を単一の正とする」は、
**この 2 つが揃って初めて機械的に守れる。**

CI の `verify-generated` が生成物のドリフトを検出できるのも、
生成が決定的だからになる。

## 決定 2: フロントは Next.js (React)

### 理由: 最も使われているフレームワークは、AI が最も正確に書ける

決定 1 と同じ判断軸になる。

React は採用実績が最も多く、**学習データも最も厚い。**
AI に書かせたときの精度と、こちらが検証にかける手間が、そのぶん軽くなる。

Next.js を選んだのは、App Router と React Server Components によって
**取得をサーバ側に寄せられる**ため。
実際このリポジトリでは、一覧・詳細の取得を Server Components が行い
(`API_URL` を実行時に読む)、
ブラウザ側の呼び出しは投稿・削除など**状態を変える操作に限っている**
([ADR 0021](0021-frontend-screens.md))。

### **Vue との差は小さいと考えている**

正直に書いておく。**フレームワークとしての優劣で選んでいない。**

Vue でも同じものは作れるし、設計判断もほとんど変わらないと考えている。
差が出るのは「AI が書いたコードの精度」と「読み手の多さ」であって、
**フレームワークの表現力ではない。**

ここを「React のほうが優れているから」と書くと、
[ADR 0001](0001-why-postgresql.md) がパーティショニングについて退けたのと同じ
**「必要のない優位性を、必要だと誤認して選んだ」**形になる。

## 引き受けるコスト

| | |
| --- | --- |
| **言語が 2 つになる** | 型定義を共有できない。だから [OpenAPI を単一の正](0002-openapi-direction.md) にして、両側へ生成する形にした |
| **Go の記述量** | エラー処理が明示的なぶん行数は増える。ただし**生成コードの検証**という主目的とは矛盾しない |
| **Rust を選ばなかったことによる学習機会の逸失** | 期間の制約による判断であり、技術的な優劣ではない |

## なぜ後から書いたか

**実装が終わってから記録している。** これは ADR として理想的ではない。

書かなかった理由は、当時「言語の選択は主題ではない」と考えていたため。
主題は並行制御と実測であって、その器は何でもよいと思っていた。

**これは誤りだった。** 読み手が最初に問うのは器の選択であり、
そこに理由が無いと、**その先の判断もすべて「なんとなく」に見える。**

[ADR 0009](0009-scaling-strategy.md) が
「なぜリードレプリカを置かないか」を数字で説明したのと同じ密度で、
**選ばなかったものにも理由が要る。**
ADR 0001 が「検討したが採用理由にしなかったもの」を先に書いているのは、
まさにこの形になる。
