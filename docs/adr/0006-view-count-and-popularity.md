# ADR 0006: 閲覧数の計上を主トランザクションから分離する

- ステータス: **採用 (実装前)**
- 日付: 2026-08-05

「人気のスレッド一覧」の指標を**閲覧数**と定めた。
これは機能追加であると同時に、このリポジトリの主題である並行制御に
直接ぶつかる設計判断になる。

## 背景

素朴に書くと、スレッド詳細の取得はこうなる。

```sql
UPDATE threads SET view_count = view_count + 1 WHERE id = $1;
```

これを毎リクエスト実行すると、3 つの問題が同時に起きる。

### 問題 1: 人気スレッドほど競合する (ホットロウ)

PostgreSQL の `UPDATE` は対象行に排他行ロックを取り、
同じ行を更新する他のトランザクションはコミットまで待つ。
分離レベルを下げても回避できない。

閲覧数は「アクセスが集中している行ほど更新も集中する」という性質を持つ。
つまり**人気スレッドが構造的にボトルネックになる**。
一覧で上位に出るスレッドほど遅くなる、という最悪の相関になる。

### 問題 2: Phase 2 の SERIALIZABLE を殺す

これが決定的な理由になる。

Phase 2 では、コメント投稿を SERIALIZABLE で実装し、
直列化失敗 (SQLSTATE 40001) をリトライで吸収する。
コメント投稿は親スレッドの存在確認のために `threads` を読む。

ここに閲覧数の `UPDATE threads` が混ざると、
`threads` に対する読み書きの衝突 (rw-conflict) が大量に生まれる。
PostgreSQL の SSI は保守的で、危険な構造を検出した時点で
**実際には直列化可能な実行でも中断する**。

結果として、**閲覧というまったく無関係な操作が、
コメント投稿の直列化失敗率を押し上げる**。
リトライ回数が増え、Phase 2 で測ろうとしているスループットが、
測定対象と無関係な要因で汚染される。

同じトランザクション内に閲覧数更新を入れた場合はさらに悪く、
リトライのたびに閲覧数が二重計上されうる
(リトライは副作用を巻き戻すが、リトライ後に再度加算されるため
「何回加算されたか」がリトライ回数に依存する)。

### 問題 3: 人気順のインデックスが HOT update を殺す

人気順に並べるには `view_count` にインデックスが要る。
しかし PostgreSQL の HOT (Heap Only Tuple) update は、
**更新対象の列がどのインデックスにも含まれていないとき**にだけ効く。

| | `view_count` にインデックスなし | あり |
| --- | --- | --- |
| 1 回の閲覧で更新されるもの | ヒープの新タプルのみ | ヒープ + インデックスエントリ |
| デッドタプルの回収 | ページ内で完結しやすい | 通常の VACUUM 待ち |

つまり「人気順で並べたい」という要求そのものが、
「毎回カウントアップする」という実装の代償を引き上げる。
この 2 つは同時には安く成立しない。

## 検討した選択肢

### A. 素朴に同期 `UPDATE` する

- 利点: 実装が最短。値が常に正確
- 欠点: 問題 1〜3 をすべて踏む

### B. 閲覧イベントを追記専用テーブルに INSERT し、後で集計する

- 利点: `INSERT` は行ロックを取り合わないので競合しない
- 欠点: 閲覧数と同じ行数のテーブルが増え続ける。
  掲示板の閲覧回数は投稿数より桁が多い。
  保持期間とパーティション運用という別の問題を抱え込む

### C. シャーディングカウンタ (`thread_id` × N 行に分散)

- 利点: 競合が 1/N になる。値のロストがない
- 欠点: **人気順ソートに使えない。**
  現在値を得るには N 行の `SUM` が必要で、
  「全スレッドを閲覧数順に並べて上位 20 件」を索引だけで解けない。
  結局、順位付け用の集計列を別に持つことになり、
  そちらの更新タイミングという同じ問題が戻ってくる

### D. アプリ内でバッファし、定期的にまとめて反映する (採用)

- 利点: DB への `UPDATE` 回数がフラッシュ間隔で決まり、
  閲覧数とは無関係になる。問題 1〜3 がすべて緩和される
- 欠点: 値が最新ではない。プロセスが異常終了するとバッファがロストする

### E. Redis でカウントする

- 利点: 高速。プロセスをまたいで集約できる
- 欠点: 依存サービスが 1 つ増え、その永続化方針という判断が別途要る。
  結局「Redis から PostgreSQL へどう反映するか」という
  D と同じ問題が、コンポーネントを 1 つ挟んだ形で残る

## 決定

**D を採用する。** 加えて、以下を不変条件として定める。

> **閲覧数の更新は、コメント投稿・スレッド作成の
> トランザクションに絶対に混ぜない。**
> 別の接続・別のトランザクション・`READ COMMITTED` で行う。

これは性能上の最適化ではなく、Phase 2 の測定を成立させるための前提である。

### 計上の流れ

```
GET /threads/{id}
     │
     ├──▶ スレッド取得 (読み取りのみ。閲覧数は触らない)
     │
     └──▶ メモリ上のカウンタに +1        ← ここは DB に触らない
              │
              │  一定間隔 (既定 5 秒) または一定量に達したら
              ▼
        フラッシュ (別トランザクション / READ COMMITTED)
              │
              ▼
        UPDATE threads SET view_count = view_count + $2 WHERE id = $1
        (バッファ内のスレッドを id 昇順でまとめて更新)
```

#### `id` 昇順で更新する理由

フラッシュは複数行を 1 トランザクションで更新する。
複数のインスタンスが異なる順序で同じ行集合を更新すると、
**デッドロックが起きる**。行の取得順序を `id` 昇順に固定することで、
ロックの獲得順序が全インスタンスで一致し、循環待ちが構造的に発生しなくなる。

### 副産物: キーセットページネーションが成立する

これは D を選んだ結果として得られる、無視できない利点になる。

閲覧数を毎回更新すると、`view_count` はページ送りの最中に変動する。
キーセットページネーションは「カーソル以降を辿る」方式なので、
**並び順のキーが動くと行の重複と取りこぼしが起きる**。
これは [`pagination.go`](../../apps/go-api/internal/pagination/pagination.go) が
OFFSET を採らなかった理由そのものであり、同じ問題が別の入口から戻ってくる形になる。

フラッシュ間隔を設けると、`view_count` は**間隔の間は動かない**。
ページ送りが数百 ms で終わる以上、実用上は安定した並びを辿れる。

### 人気順のカーソルは複合キーになる

```sql
-- 新着順 (現在)
WHERE deleted_at IS NULL AND id < $1
ORDER BY id DESC

-- 人気順
WHERE deleted_at IS NULL AND (view_count, id) < ($1, $2)
ORDER BY view_count DESC, id DESC
```

行値比較 (`(a, b) < (x, y)`) を使う。
`AND`/`OR` に展開した条件と違い、これは索引をそのまま辿れる。

```sql
CREATE INDEX threads_alive_popular_idx
    ON threads (view_count DESC, id DESC)
    WHERE deleted_at IS NULL;
```

`id` を第 2 キーに入れているのは、閲覧数が同値のスレッドが必ず存在するため。
同値の並びが不定だとページ境界で行が重複・欠落する。

#### `pagination.Page` の変更が必要

現在の `Page.Cursor` は `*int64` で、`id` をそのまま公開している。
人気順ではカーソルが `(view_count, id)` の組になるため、この型では表せない。

**カーソルを不透明なトークン (base64 エンコードした構造体) に変える。**
内部表現を API に晒さない形にしておけば、
今後ソート順を追加してもカーソルの型は変わらない。

これは既存の新着順 API の互換性を壊す変更になる。
まだ公開前なので、この段階で直しておく。

> **実装済み (2026-08-09)。** トークンの形式・検証・失効の扱いは
> [ADR 0018](0018-opaque-cursor.md) で確定させた。
> `Page.Cursor` は `*pagination.Cursor` になり、
> 人気順で `view_count` を足しても API の型は変わらない。

### 重複カウントは簡易な抑制に留める

同一ユーザーの連打をすべて弾こうとすると、
閲覧履歴を全件持つことになり選択肢 B の欠点に合流する。

バッファ内に「(セッション or IP, thread_id) → 最終計上時刻」を持ち、
**一定時間内の再訪はカウントしない**。これはメモリ上の近似であり、
インスタンスをまたいだ厳密性は保証しない。
閲覧数は表示用の指標であり、課金や順位確定に使わないため、この精度で足りる。

## 引き受けるコスト

- **値がロストする。** プロセスが異常終了するとバッファ内の増分が消える。
  graceful shutdown ではフラッシュしてから終了するが、
  SIGKILL やクラッシュは救えない。**閲覧数は正確な値ではない**と割り切る
- **値が最新ではない。** 最大でフラッシュ間隔ぶん遅れる。
  「今の閲覧数」を即座に返す API は作れない
- **水平スケールでフラッシュ頻度がインスタンス数に比例する。**
  N インスタンスなら同じ行への `UPDATE` が N 倍の頻度で来る。
  それでも同期更新に比べれば桁で少ないが、
  インスタンスを増やし続ければいずれ問題 1 に再会する。
  そのときは E (Redis で集約してから 1 経路で反映) が次の手になる
- **`view_count` は「真の閲覧数」ではないと明示する必要がある。**
  README と API 仕様の両方に書く。後から精度を上げる要求が来たときに、
  設計を選び直す前提が残る
- **テストが時間依存になる。** フラッシュ間隔を待つテストは遅く不安定になるため、
  時刻とフラッシュ契機を注入可能にして、テストからは明示的に発火させる

## Phase 4 のベンチマーク題材

この ADR は、そのまま [README](../../README.md) の Phase 4 の計測項目になる。

| 比較 | 測るもの |
| --- | --- |
| A (同期 UPDATE) vs D (バッファ) | スレッド詳細取得のスループットとレイテンシ分布 |
| 閲覧数更新 **あり / なし** で Phase 2 のコメント投稿 | **直列化失敗 (40001) の発生率** |
| `view_count` インデックス **あり / なし** で同期 UPDATE | HOT update 率とデッドタプルの増加速度 |

2 行目が本命になる。「無関係に見える機能追加が、
別の機能の並行制御を壊す」ことを数字で示せる。
これは Phase 2 と Phase 4 を繋ぐ結節点であり、
閲覧数を人気の指標に選んだことの最大の収穫になる。
