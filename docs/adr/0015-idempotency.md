# ADR 0015: 冪等性 —— クライアント側のリトライを扱う

- ステータス: **採用 (実装前)**
- 日付: 2026-08-05

## 背景

Phase 2 では直列化失敗 (SQLSTATE 40001) をリトライで吸収する。
これは**サーバ内部のリトライ**であり、トランザクションが巻き戻るため冪等になる。

**問題はクライアント側のリトライになる。**

| 起きること | 結果 |
| --- | --- |
| レスポンス待ちでタイムアウト → 再送 | **サーバでは成功していて、コメントが 2 件できる** |
| モバイルの回線切り替え | 同上 |
| ダブルクリック | 同上 |
| 送信直後のリロード | 同上 |

リトライを主題に据えながらクライアント側のリトライを放置するのは、
非対称を見落としていることになる。

## 決定 1: 層を分けて、両方やる

| 層 | 対策 | 防げるもの |
| --- | --- | --- |
| クライアント | 送信中はボタンを無効化する | ダブルクリック |
| **サーバ** | **`Idempotency-Key` ヘッダ** | タイムアウト後の再送、回線切り替え、複数タブ、リロード |

クライアント側だけでは**サーバが無防備のまま**になる。
最も起きやすい「タイムアウトしたが実は成功していた」は、
ボタン制御では原理的に防げない。

## 決定 2: 対象を 2 経路に限定する

全エンドポイントに入れるのは重い。実害の大きさで絞る。

| 経路 | `Idempotency-Key` | 理由 |
| --- | --- | --- |
| **コメント投稿** | **入れる** | Phase 2 の主題と直結する |
| **画像アップロード** | **入れる** | 下記 |
| スレッド作成 | 入れない | 頻度が低く、重複に気づきやすい |
| 問い合わせ | 入れない | [ADR 0008](0008-contact-and-mail.md) で既に at-least-once を許容している |
| 通報 | 入れない | 一意制約で重複が弾かれる ([ADR 0011](0011-moderation.md)) |

### 画像アップロードで特に必要な理由

二重送信すると **S3 にオブジェクトが 2 つ残る**。

[ADR 0007](0007-image-storage.md) の回収バッチが拾うのは
`pending` と `deleted` だけなので、
**両方が `committed` になった重複は誰も削除しない**。
ストレージ費用として蓄積し続ける。

## 決定 3: 冪等性の記録は主トランザクションに入れる

[ADR 0006](0006-view-count-and-popularity.md) では
「閲覧数の更新を主トランザクションに絶対に混ぜない」と決めた。
**冪等性の記録は逆で、同じトランザクションに入れなければならない。**

| | 閲覧数 | 冪等キー |
| --- | --- | --- |
| 主処理との関係 | **無関係** (混ぜると直列化失敗を誘発する) | **原子的でなければならない** |
| 片方だけ成功したら | 数値が少しずれるだけ | **キーは記録されたが投稿されていない、が起きる** |

別トランザクションにすると、
「キーを記録した直後に処理が失敗」したとき、
リトライしても「処理済み」と誤判定されて投稿が永久に失われる。

### 直列化失敗でリトライしたとき

主トランザクションが巻き戻れば冪等キーの記録も巻き戻り、
リトライで再度 `INSERT` される。**これが正しい挙動**になる。

キーの `INSERT` は主キーへの単一行挿入なので、
同じキーが同時に来た場合以外は競合しない。
Phase 2 の直列化失敗率への影響は無視できる。

## スキーマ

```sql
CREATE TABLE idempotency_keys (
    user_id         BIGINT      NOT NULL REFERENCES users(id),
    key             TEXT        NOT NULL,
    endpoint        TEXT        NOT NULL,
    request_hash    TEXT        NOT NULL,   -- 同じキーで別の内容を送られた検出用
    response_status INT,
    response_body   JSONB,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    completed_at    TIMESTAMPTZ,

    PRIMARY KEY (user_id, key)
);

CREATE INDEX idempotency_keys_created_idx ON idempotency_keys (created_at);
```

**主キーを `(user_id, key)` にする。**
キーはクライアントが生成するため、グローバルに一意である保証がない。
ユーザーで名前空間を分けないと、他人のキーと衝突して
**他人の投稿結果が返る**という最悪の事故になりうる。

## 処理の流れ

```
1. INSERT ... ON CONFLICT DO NOTHING で先着を決める
     │
     ├─ 挿入できた   → 処理を実行 → response を記録 → コミット → 201 を返す
     │
     └─ 挿入できない → 既存行を読む
                        ├─ request_hash が違う → 422 (同じキーで別の内容)
                        └─ 一致する           → 記録した response をそのまま返す
```

### 同時に来た場合は待つ

`INSERT ... ON CONFLICT DO NOTHING` は、
競合する行が**未コミット**のとき、そのトランザクションの終了を待つ。

待った結果コミットされていれば、既存行を読んで記録済みのレスポンスを返せる。
**待ち時間はコネクションを占有する**ため、
文の実行タイムアウトを設けて、超えたら 409 を返す。

### `request_hash` を持つ理由

これがないと、**同じキーを使い回して別の内容を投稿しようとしたとき、
黙って前回の結果が返る**。クライアントのバグが見えなくなる。

不一致を 422 で明示的に失敗させる。

## 決定 4: 匿名投稿は対象外にする

コメント投稿は匿名でも可能だが ([ADR 0005](0005-authentication.md))、
匿名には**キーの名前空間を分ける手段がない**。

IP で分ける案はあるが、NAT の背後では複数人が同じ IP になり、
逆に他人のキーと衝突する。

**匿名の二重送信はクライアント側の防止のみで扱う。**
「ログインすると二重投稿されなくなる」という非対称は、
制約として API 仕様に明記する。

## 定期処理が 5 つになる

古いキーは削除しないと単調増加する。**保持は 24 時間**とする
(クライアントがリトライを諦めるまでの時間として十分)。

[ADR 0003](0003-open-questions.md) の未決 #9 で数えた定期処理に、
これで 5 つ目が加わる。

| # | 処理 | 出典 |
| --- | --- | --- |
| 1 | 閲覧数のフラッシュ | [ADR 0006](0006-view-count-and-popularity.md) |
| 2 | 画像の孤児回収 | [ADR 0007](0007-image-storage.md) |
| 3 | 問い合わせメールの送信 | [ADR 0008](0008-contact-and-mail.md) |
| 4 | 期限切れセッションの削除 | [ADR 0005](0005-authentication.md) |
| 5 | **期限切れ冪等キーの削除** | この ADR |

**5 つすべてを graceful shutdown で待てる仕組みが要る**という
[ADR 0008](0008-contact-and-mail.md) の指摘が、さらに重くなる。

## 引き受けるコスト

- **レスポンスを DB に保存する。** `response_body` を `JSONB` で持つため、
  大きなレスポンスを返す経路では容量を消費する。
  対象を 2 経路に絞っているのはこのためでもある
- **クライアントがキーを生成する責任を持つ。**
  生成を忘れるとヘッダなしのリクエストになる。
  **ヘッダがない場合は冪等性なしで処理する**(必須にはしない) ——
  必須にすると、既存クライアントが即座に壊れる
- **「処理中に同じキーが来た」の挙動が待ちになる。**
  タイムアウトの設定を誤ると、コネクションが詰まる
- **匿名とログイン済みで挙動が変わる。** 上記の非対称は
  利用者からは見えないが、不具合報告の切り分けを難しくする
