# ADR 0019: コメント投稿の並行制御 —— レス番号を題材に据える

- ステータス: **採用**
- 日付: 2026-08-11

## 背景

Phase 2 はこのリポジトリの主題である。
[ADR 0003](0003-open-questions.md) の「Phase 2 に残した作業」はこう書いている。

- SERIALIZABLE 分離レベルでのトランザクション実装
- 直列化失敗 (SQLSTATE 40001) の指数バックオフつきリトライ
- 悲観ロック版 (`SELECT ... FOR UPDATE`) との比較実装
- 両者のスループット比較ベンチマーク

**しかし、現在のコメント投稿には競合する余地がない。**

```sql
INSERT INTO comments (thread_id, author_name, body, author_id)
SELECT ... WHERE EXISTS (SELECT 1 FROM threads WHERE id = $1 AND deleted_at IS NULL)
```

1 文で閉じているため原子的であり、しかも `threads` を書き換えるのは
スレッドの論理削除だけである。これを `SERIALIZABLE` で包んでも、
**40001 は実運用ではまず発生しない。**

つまり、このまま上の 4 項目を実装すると:

| 作ったもの | 実際に起きること |
| --- | --- |
| SERIALIZABLE のトランザクション | 競合しないので READ COMMITTED と同じ結果 |
| 40001 のリトライ | 発火しない。**経路が一度も通らない** |
| 悲観ロック版との比較 | どちらも待たないので差が出ない |
| スループット比較 | リトライ 0 回どうしの比較になる |

「並行制御を実装した」とは言えるが、**動いていることを実証できない。**
このリポジトリは実測してから選ぶ流儀で来ている
(`db/query/threads.sql` の相関サブクエリ比較、
[ADR 0017](0017-arch-lint-and-depguard.md) の 16 件のプローブ)。
発火しない経路を「実装済み」として残すのは、その流儀に反する。

**したがって、先に「本物の競合」を持つ題材を決める必要がある。**

## 決定 1: レス番号 (スレッド内連番) を導入する

`comments` に `seq` を足す。掲示板の `>>1` `>>2` にあたる、
**スレッドの中で 1 から振られる番号**である。

```sql
ALTER TABLE comments ADD COLUMN seq INTEGER;
-- backfill 後
ALTER TABLE comments ALTER COLUMN seq SET NOT NULL;
CREATE UNIQUE INDEX comments_thread_seq_key ON comments (thread_id, seq);
```

### なぜこれが題材として成立するか

**採番は「読んでから書く」ことになる。**

```sql
SELECT COALESCE(MAX(seq), 0) + 1 FROM comments WHERE thread_id = $1;
INSERT INTO comments (thread_id, seq, ...) VALUES ($1, $2, ...);
```

同時に 2 人が投稿すると、両者が同じ `MAX(seq)` を読んで同じ番号を書こうとする。
**これは 1 文にまとめても解決しない** —— 集約はスナップショットから計算されるため、
`INSERT ... SELECT MAX(seq)+1` でも同じ値が 2 回計算される。
文の原子性は、読んだ値の鮮度を保証しない。

`threads` の存在確認 (現行の `WHERE EXISTS`) が 1 文で片付くのは、
**読んだ結果が他トランザクションの書き込みで無効化されないから**である。
採番はそうならない。この差が Phase 2 の題材になる。

### 正しさが DB 側で検証できる

これがレス番号を選んだ 2 番目の理由になる。

```sql
CREATE UNIQUE INDEX comments_thread_seq_key ON comments (thread_id, seq);
```

**壊れたら DB が拒否する。** テストが「通った」ことではなく、
一意制約違反が 0 件であることを根拠にできる。

このリポジトリでは、`make mutation-probe` を入れた日だけで
**「守っているつもりのテストが、壊しても落ちなかった」が 2 件見つかっている。**
検証を DB の制約に寄せられる題材は、それだけで価値がある。

パーティションキー `thread_id` を先頭に含むため、
**この一意制約はパーティションテーブルにそのまま張れる**
([ADR 0016](0016-schema-and-indexes.md) 問題 2 の制約に抵触しない)。
`comments (id)` を UNIQUE にできなかったのとは事情が違う。

### 掲示板として自然な機能である

並行制御のためだけに作った人工的な列ではない。
`>>12` のような参照は掲示板の基本的な語彙であり、
**この機能が無いほうが不自然**である。

主題のために要件を捏造すると、
「並行制御を見せたいから無意味な列を足した」という
[ADR 0001](0001-why-postgresql.md) がパーティショニングで避けたのと
同じ誤りになる。レス番号はそれに当たらない。

## 検討した他の題材

### A. コメント数の上限 (`docs/postgres-ssi.md` の例)

[SSI の解説](../postgres-ssi.md) が書き込みスキューの例に使っている
「1 スレッド 1000 件まで」をそのまま実装する案。

- 利点: 既存ドキュメントとの一致が最も強い。教科書的な書き込みスキュー
- 欠点: **上限付近の状態を作らないと競合が観測できない。**
  ベンチマークのたびに「あと 1 件で上限」というデータを用意することになる。
  上限を小さくすれば作りやすいが、それは測定のためだけの設定であり、
  機能としては意味を持たない

### B. `threads.updated_at` を投稿時に更新する

- 利点: 実装が最も小さい
- 欠点: これは書き込みスキューではなく**ホットロウ競合**である。
  同じ形の問題を [ADR 0006](0006-view-count-and-popularity.md) が
  閲覧数について扱い、「主トランザクションに絶対に混ぜない」と決めている。
  ここで持ち込むと、その決定と正面から矛盾する

### C. 追加要件なし (存在確認 + INSERT を 2 文に割るだけ)

- 利点: スキーマも API も変えない
- 欠点: 冒頭に書いたとおり、40001 が発生する条件が
  「投稿と同時にスレッドが論理削除される」だけになる。**測定が空振りする**

**A・B・C はいずれも採らない。** レス番号 (決定 1) を採る。

## 決定 2: 4 つの実装を並べ、切り替え可能にする

比較実装は 2 つ (SSI / 悲観) と書かれていたが、**4 つにする。**

| モード | 分離レベル | 採番の方法 | 結果 |
| --- | --- | --- | --- |
| `naive` | READ COMMITTED | `SELECT MAX+1` → `INSERT` | **投稿が失われる** |
| `ssi` | **SERIALIZABLE** | 同上 + 40001 リトライ | 正しい |
| `pessimistic` | READ COMMITTED | `threads` を `FOR UPDATE` してから採番 | 正しい |
| **`unique` (既定)** | READ COMMITTED | 1 文で採番し、一意制約違反 (23505) をリトライ | 正しい |

**既定が `ssi` でないのは実測の結果**である。下の「実測」節を参照。

### `naive` を実装する理由

**防御なしで何が起きるかを実証するため。**
[`interactor_nplus1.go`](../../apps/go-api/internal/thread/usecase/interactor_nplus1.go)
と同じ位置づけになる —— 本番経路ではないが、
「なぜ本番経路がこの形なのか」を実測で示すために存在する。

「並行制御を入れたら正しくなった」は、
**入れる前が本当に壊れていたことを示さない限り主張にならない。**

#### `naive` の壊れ方は「重複」ではなく「失敗」になる

当初は「レス番号が重複する」と書いていたが、**そうはならない。**
`UNIQUE (thread_id, seq)` があるため、DB が 2 件目を拒否する。

実際に起きるのは、SQLSTATE 23505 がリトライされずに上がってきて、
**投稿が 500 で失われる**ことである (実測で 32 件中 18 件)。

これは弱い結果ではなく、むしろ要点になる。

> **データを守っているのはアプリの並行制御ではなく、DB の制約である。**
> 並行制御が担っているのは「制約に弾かれないようにする」ことであり、
> 正しさの最後の砦ではない。

制約を外して重複を再現する実験は行わない。
「一意制約を外したら重複した」は自明であり、
そのために本番と違うスキーマを用意する価値がない。

`naive` は `ENV=development` のときだけ選択できる。
本番相当の設定で選ぼうとすると起動時にエラーにする ——
既定を安全側に倒す既存の方針
(`config.AuthConfig.SecureCookie` と同じ) に揃える。

### `unique` を実装し、そして既定にする理由

**実務でいちばん安い正解がこれだからである。**

```sql
INSERT INTO comments (thread_id, seq, ...)
SELECT $1, COALESCE(MAX(seq), 0) + 1, ...
FROM comments WHERE thread_id = $1
```

READ COMMITTED のまま 1 往復で済み、
競合したときは一意制約違反 (SQLSTATE 23505) が返る。
リトライすると `MAX(seq)` を読み直すため、次は通る。

**SSI が唯一の答えであるかのように書くのは誠実ではない。**
このリポジトリが PostgreSQL を選んだ理由は
「SSI のほうが速いから」ではなく「両方を同一 DB で比較できるから」であり
([ADR 0001](0001-why-postgresql.md))、その比較対象に
現実的な選択肢を入れないと比較の意味が薄れる。

引き換えに、`unique` は**競合時に無駄な `INSERT` を投げてから弾かれる**。
リトライ 1 回あたりのコストは 4 モードで最も高い。
それでも実測では最も速かった (下の「実測」節)。

### 切り替えは環境変数で行う

```
COMMENT_POST_MODE=unique | ssi | pessimistic | naive
```

ベンチマーク (Phase 4) で同一バイナリのまま切り替えられるようにする。
モードごとにビルドを分けると、比較に「ビルド差」という交絡が入る。

## 実測

`make concurrency-probe` で、**同じスレッドへ同時に投稿**したときの挙動を測った。
環境は開発用 compose (PostgreSQL 17 / 接続プール上限 20)。

### 32 並列

| モード | 成功 | 409 | 失敗 | 平均試行 | 最大試行 | 所要 |
| --- | --- | --- | --- | --- | --- | --- |
| `naive` | 14 | 0 | **18** | 1.00 | 1 | 119 ms |
| `ssi` (試行上限 5) | 23 | **9** | 0 | — | 5 | 212 ms |
| `ssi` (試行上限 12) | 32 | 0 | 0 | 2.66 | 7 | 215 ms |
| `pessimistic` | 32 | 0 | 0 | 1.00 | 1 | 159 ms |
| **`unique`** | 32 | 0 | 0 | 1.75 | 5 | **113 ms** |

**レス番号の重複は全モードで 0 件**だった (`UNIQUE (thread_id, seq)` が防いでいる)。
成功したぶんのレス番号は、どのモードでも `1..成功数` の連番になっている。

### 分かったこと 1: SSI がこのワークロードに最も向かない

3 つの正しいモードの中で `ssi` が最も遅く、リトライも最も多い。
**これは実装の不備ではなく、構造的な帰結**である。

> 投稿者は全員が `MAX(seq)` —— **同じスレッドのコメント全体** —— を読み、
> 全員がそこに書き込む。rw 依存は事実上すべての組み合わせで成立する。

[SSI の解説](../postgres-ssi.md) の 5 節はこう書いていた。

> - 競合が**少ない**なら SSI が有利
> - 競合が**多い**なら悲観ロックが有利

レス番号の採番は**競合率が構造的に 100% になる**問題であり、
楽観的方式が最も向かない側に位置している。
[ADR 0001](0001-why-postgresql.md) が
「SSI のほうが速いから PostgreSQL を選んだのではない」と書いていたことが、
ここで具体的な数字になった。

### 分かったこと 2: リトライ上限 5 は足りなかった

初版の `MaxAttempts: 5` は根拠のない値だった。
**8 並列の時点で `ssi` の最大試行が 5 に張り付いており**、
32 並列では 32 件中 9 件が 409 になっていた。

12 に上げると 32 並列でも全件が通り、実際に使われた試行回数は最大 7 だった。
**上限は「余裕を持って超えない値」でなければ、
競合が増えた日に静かに 409 が増える。**

### 分かったこと 3: `pessimistic` はリトライが 1 回も起きない

`FOR UPDATE` で待つため、平均試行が正確に 1.00 になる。
`unique` より 1.4 倍遅いが、**やり直しによる無駄な仕事が一切ない**。
待ち時間のばらつきが小さいことも含め、
「予測しやすさ」を優先するなら合理的な選択肢になる。

### 決定への反映

**既定を `ssi` から `unique` へ変更した。**

このリポジトリは「実測してから選ぶ」で来ている
(`db/query/threads.sql` の相関サブクエリ比較、
[ADR 0017](0017-arch-lint-and-depguard.md) の 16 件のプローブ)。
**主題が SSI であることは、SSI を本番経路に据える理由にならない。**

引き換えに、**`ssi` の経路は本番では一度も通らなくなる。**
`naive` と同じ「維持するが使わないコード」が 1 つ増えることを引き受ける。
Phase 4 のベンチマークと `make concurrency-probe` が唯一の実行経路になる。

## 決定 3: リトライは永続化層に置く

トランザクションの境界は永続化層 (`internal/infrastructure/postgres`) にある。
リトライは**トランザクション全体をやり直す**ものなので、同じ層に置く。

```
usecase.PostComment
   └── repository.Create        ← インターフェースは変えない
         └── postgres: RunInTx(SERIALIZABLE) { 採番 → INSERT }
               └── 40001 なら最初からやり直す
```

ユースケース層はリトライを知らない。
[ADR 0004](0004-modular-monolith.md) の層構成と `go-arch-lint` の許可リストを
変えずに済み、**ユースケースのテストがリトライに影響されない**。

### リトライの条件

| 項目 | 値 | 理由 |
| --- | --- | --- |
| 最大試行回数 | **12** (初回 + 再試行 11) | **実測で決めた** (下の「実測」節)。上限が無いと障害時に DB を押し潰す |
| バックオフ基準 | 2 ms | 競合相手のコミットは数ミリ秒で終わる。待つべき時間は短い |
| 増え方 | 2 の冪 + **full jitter** | 固定増分だと再試行が同じ位相で揃う |
| 上限 | 64 ms | ここに達する頃には競合率が異常。待つより諦める |
| 中断 | `ctx` のキャンセルを尊重 | クライアントが切った後も再試行しない |

> **最大試行回数の初版は 5 だった。** 根拠のない数字であり、
> 実測すると 8 並列の時点で上限に張り付いていた。12 に直している。

**トランザクション内で外部 API を呼ばない。**
リトライで二重実行されるため ([SSI の解説](../postgres-ssi.md) 4 節)。
現在の投稿経路に外部呼び出しは無いが、
[ADR 0007](0007-image-storage.md) の画像添付が入ると条件が変わる。

### リトライ可能の判定を広げる

`postgres.IsRetryable` は現在 40001 と 40P01 を見ている。
`unique` モードのために **23505 を条件付きで足す**。

**無条件に足してはいけない。** 一意制約違反はほとんどの場合
「同じものを二重に作ろうとした」であり、リトライしても永久に失敗する。
`comments_thread_seq_key` に対する違反だけをリトライ可能として扱う。

## 決定 4: 直列化失敗のログは、集計できる場所に 1 行残す

[ADR 0010](0010-log-pipeline.md) の 4-3 は
「リトライして成功した直列化失敗は ERROR ではない」と定め、
各試行を `DEBUG`、上限到達を `ERROR` としている。

一方で同じ ADR の 4-6 は、`serialization_failure` を Athena で集計する例を挙げている。

```sql
SELECT thread_id, count(*) AS failures, max(attempt) AS max_retry
FROM go_api_logs WHERE msg = 'serialization_failure' GROUP BY thread_id
```

**この 2 つは両立しない。**
4-3 は「DEBUG は本番で出さない」とも書いており、
`serialization_failure` が DEBUG である以上、
**本番の S3 にこの行は 1 件も届かない。**
上のクエリは常に 0 行を返す。

> 集約して初めて見えた不整合であり、
> [ADR 0016](0016-schema-and-indexes.md) が
> スキーマで同じことをやったのと同じ種類の発見になる。

### 決定

**各試行は `DEBUG` のまま、結果を `INFO` の業務イベント 1 行にまとめる。**

| 状況 | 出るもの |
| --- | --- |
| 各試行の失敗 | `DEBUG` `serialization_failure` (`thread_id`, `attempt`, `sqlstate`, `mode`) —— 開発のみ |
| 投稿の成功 | **`INFO` `comment_created` (`thread_id`, `seq`, `attempts`, `mode`)** |
| 上限到達で失敗 | **`ERROR` `serialization_retry_exhausted` (`thread_id`, `attempts`, `sqlstate`, `mode`)** |

`sqlstate` を載せるのは、直列化失敗 (40001) と採番の衝突 (23505) が
**同じイベント名で出る**ためである。モードによって競合の現れ方が違うので、
これが無いと `ssi` と `unique` のログを見分けられない。
イベント名を分けなかったのは、
[ADR 0010](0010-log-pipeline.md) の 4-6 が既に
`serialization_failure` という語彙を確立しているため。

`attempts` が 1 より大きい行が「リトライして成功した投稿」になる。
本番で出るのは INFO 以上なので、Athena の集計はこちらを起点にする。

```sql
-- 直列化失敗が集中しているスレッド上位 10 件 (本番で機能する形)
SELECT thread_id, sum(attempts - 1) AS retries, max(attempts) AS max_attempts
FROM go_api_logs
WHERE dt = '2026-08-11' AND msg = 'comment_created' AND attempts > 1
GROUP BY thread_id ORDER BY retries DESC LIMIT 10;
```

上限到達分は `serialization_retry_exhausted` を足して数える。
**ADR 0010 の 4-6 のクエリ例は、この ADR で置き換える。**

`mode` を載せるのは、Phase 4 のベンチマークで
モード別に集計するときに、ログ側だけで切り分けられるようにするためである。

## 決定 5: 削除しても番号は詰めない

コメントは論理削除 (`deleted_at`) なので行は残る。
採番は `deleted_at` を無視して `MAX(seq)` を取る。

| | この設計 | 詰める設計 |
| --- | --- | --- |
| 5 番を削除したあと | 次は 6 番。**5 番は欠番** | 5 番が別のコメントに再利用される |
| `>>5` の参照 | 「削除されました」を指す | **別の投稿を指す** |

**番号を再利用すると、過去の `>>5` が別の投稿を指すようになる。**
掲示板で欠番が出るのは自然な挙動であり、
参照の一貫性のほうが優先される。

これは [ADR 0011](0011-moderation.md) のモデレーション削除でも同じである。

## 決定 6: マイグレーション番号を着手順に合わせ直す

[ADR 0016](0016-schema-and-indexes.md) の「マイグレーションの分割」は
`000004` を Phase 10 後半 (通報)、`000005` を Phase 2 (冪等キー) に割り当てていた。

しかし [README](../../README.md) の着手順では **Phase 2 が 2 番、Phase 10 後半は 4 番**である。
番号が着手順と逆になっており、ADR 0016 自身の
「使わないテーブルを先に作らない」という原則に反する。

**ADR 0016 の表をこの ADR で更新する。**
同じ理由で `000003` / `000004` の割り当てを直したのと同じ扱いになる。

## 引き受けるコスト

- **投稿経路が 1 往復からトランザクションになる。**
  `BEGIN` / `COMMIT` を含めて往復が増える。
  競合が無いときの投稿は現行より確実に遅くなる。
  これは Phase 4 で `naive` との差として測る
- **`comments` の索引が 1 本 (実体は 8 本) 増える。**
  [ADR 0016](0016-schema-and-indexes.md) が数えた 24 本に 8 本足して 32 本になる
- **`seq` は既存行に backfill が要る。**
  `NOT NULL` を後から付けるため全行スキャンと `ACCESS EXCLUSIVE` ロックが発生する
  ([ADR 0016](0016-schema-and-indexes.md) の「既存テーブルへの `ALTER` は安全」の
  裏側にあたるケース)。実データがほぼ無い現時点だから許容できる。
  本番規模で同じことをするなら、`NOT NULL` を諦めるか
  `NOT VALID` の CHECK 制約から始める必要がある
- **本番で使わないモードが 3 つ (`naive` / `ssi` / `pessimistic`) 残る。**
  テストと保守の対象が増える。`interactor_nplus1.go` と同じ負債を、
  同じ理由 (実測のため) で引き受ける。
  **とくに `ssi` は主題そのものでありながら本番経路から外れた**ため、
  壊れても本番では気づけない。`make concurrency-probe` を
  Phase 4 まで生かしておく必要がある
- **`seq` は API に出る。** 一度出したフィールドは消しにくい。
  レス番号を将来やめる判断はほぼできなくなる
