## 解決済み

### ✅ 1. フロントエンドに `app/` が 2 つあった

`apps/next-app/src/` を削除し、`app/` に一本化した。

`src/app/threads/page.tsx` は Next.js の解決規則 (`app/` と `src/app/` が
両方あると `src/` 側が無視される) によりデッドコードであり、
かつ 3 箇所が壊れていた (`'use client'` 欠落、レスポンス形の誤り、
フィールド名の誤り)。
手書きの型定義 `src/types/api.d.ts` も API と一致していなかったため削除した。

`schema.d.ts` が仕様書から自動生成される以上、手書きの型を残す理由がない。

### ✅ 2. `api/openapi/swagger.yaml` が別系統で残っていた

削除した。同じ場所 (`api/openapi.yaml`) に、
**手書きの唯一の正**としての仕様書を置き直した ([ADR 0002](0002-openapi-direction.md))。

### ✅ 3. ESLint が実質的に動いていなかった

正式に導入した。

- `eslint` + `eslint-config-next` を devDependencies に追加
- フラット設定 `apps/next-app/eslint.config.mjs` を作成
- Next.js 16 で `next lint` は削除されたため、`eslint .` を直接呼ぶ形に変更
- 生成物 (`schema.d.ts`) は検査対象から除外
- `no-explicit-any` をエラーに引き上げ (型が生成されている以上 any は不要)

**ESLint は 9 系に固定している。**
`eslint-config-next` の peerDependencies は `>=9.0.0` だが、
同梱の `eslint-plugin-react@^7.37` が ESLint 10 で削除された
`context.getFilename()` を呼ぶため、10 系では起動時にクラッシュする。

### ✅ 4. Next.js が 13.4.7 で止まっていた

以下に更新した。

| | 変更前 | 変更後 |
| --- | --- | --- |
| next | `latest` (実体 13.4.7) | `^16.2.12` |
| react / react-dom | `latest` (実体 18.2.0) | `^19.2.8` |
| typescript | `latest` | `^5.9.3` |
| eslint | (なし) | `^9.39.5` |

`"latest"` 指定をすべて明示的なレンジに置き換えた。
`"latest"` は「バージョン指定」ではなく dist-tag であり、
lock を作り直した瞬間に別バージョンが降ってくるため再現性がない。

TypeScript は 7 系ではなく 5.9 系に留めた。
`eslint-config-next` が検証している組み合わせから外れるリスクを避けるため。

Next 16 のビルド時に `tsconfig.json` が自動更新され、
`jsx` が `react-jsx` (automatic runtime) になった。
これに伴い不要になった `import React` を削除している。

yaml を正とする方式に切り替えた。詳細は [ADR 0002](0002-openapi-direction.md)。

### ✅ 6. 認証

**入れる。** Google の OIDC を Go API 側で処理し、
サーバ側セッションを HttpOnly Cookie で持つ。
詳細は [ADR 0005](0005-authentication.md)。

**匿名投稿は残す。** `author_id` を NULL 許容で追加し、

——特に閲覧数 ([ADR 0006](0006-view-count-and-popularity.md)) ——

結果として Phase 2 / Phase 4 の題材が増えている。

### ✅ 11. ID の型

**用途ごとに使い分ける。全部を統一しない。**

| テーブル | 決定 | 理由 |
| --- | --- | --- |
| `threads` / `comments` | **`BIGINT` 連番のまま** | キーセットページネーションが素直に動いている。`comments` は 5 年で億単位になるため 8 → 16 バイトが効く。パーティションキー (`thread_id`) のハッシュ計算も重くなる |
| `users` | 内部 ID は `BIGINT`。**公開用に `public_id UUID` を別に持つ** | マイページの URL が連番だと全ユーザーを列挙できる |
| `images` | `UUID` | [ADR 0007](0007-image-storage.md)。キーが推測できると他人の画像を辿れる |
| `sessions` | ランダム | [ADR 0005](0005-authentication.md) |

掲示板でスレッド番号が連番なのはむしろ自然であり、
避けたいのは**ユーザーの列挙**だけなので、そこだけ分ける。

#### UUID v7 を選んだ根拠

RFC 9562 (2024 年) で標準化された版で、
**先頭 48 ビットが Unix ミリ秒のタイムスタンプ**、残りがランダムになっている。

| | UUID v4 | **UUID v7** | BIGINT 連番 |
| --- | --- | --- | --- |
| B-tree への挿入位置 | ランダム (ページ分割が多発) | **末尾に追記** | 末尾に追記 |
| キーセットの前提 (単調増加) | 満たさない | **満たす** | 満たす |
| サイズ | 16 バイト | 16 バイト | **8 バイト** |
| 総数の推測 | 不可 | **不可** | 可能 |
| 生成時刻の露出 | なし | **あり** (先頭が時刻) | なし |

v4 ではなく v7 を選ぶのは、**インデックスの挿入位置が末尾に寄る**ため。
v4 は完全ランダムなのでページ分割が多発する。

`public_id` はソートに使わないため単調増加である必要はないが、
インデックスの効率は v7 のほうが素直になる。

#### 公開用識別子はハンドル名ではなく UUID v7 にする

`/users/hoshino` のような可読な識別子は共有しやすいが、
**別の設計判断を一式呼び込む**。

- 変更を許すか (許すと URL が変わる)
- 一意性の判定 (大文字小文字、Unicode 正規化)
- 予約語の除外 (`admin`, `api`, `me` など)
- 紛らわしい名前によるなりすまし

まず `public_id UUID` (v7) で公開経路を作り、
**必要になってからハンドル名を足す**。
ハンドル名 → `public_id` の解決を追加するだけで済む。

逆順 (ハンドル名から始めて後で UUID を足す) にすると、
既に配布された URL の互換性が問題になる。

**PostgreSQL 17 には `uuidv7()` がない** (18 で追加) ため、
生成は Go 側 (`google/uuid` の `NewV7`) で行う。

### 12. `comments` のパーティション数 (8) は足りるか

[ADR 0009](0009-scaling-strategy.md) の見積もり (登録 100 万ユーザー、
DAU 10〜30%) では、コメントは年間 3,650 万〜2 億件になる。
5 年で 1 パーティションあたり 2,000 万〜1.2 億行。

行数そのものは PostgreSQL が扱える範囲だが、
**ハッシュパーティションの数を後から変えるには全データの再配置が要る**
(モジュラスが変われば行の所属先が変わるため)。
新構成のテーブルへ移行するか、論理レプリケーションを使うことになる。

README に記載のとおり、パーティションは
「どの規模から効き始めるかを Phase 4 で実測する」ために入れたものなので、
判断材料は測定で得られる。ただし**変更コストが高い側の判断**である点は
認識しておく。

- [ ] 実測後、8 のままにするか増やすか

### 13. depguard のルール数が ADR 0004 の想定を超える

[ADR 0004](0004-modular-monolith.md) は
「現在 7 ルールで、モジュールが 3 つになれば 9 になる。
**この数え方が破綻するようなら `go-arch-lint` を再検討する**」と書いている。

今回の設計でモジュールは 5 つになる。

| モジュール | 出典 |
| --- | --- |
| `thread` / `comment` | 既存 |
| `user` | [ADR 0005](0005-authentication.md) |
| `image` | [ADR 0007](0007-image-storage.md) |
| `contact` | [ADR 0008](0008-contact-and-mail.md) |

[ADR 0011](0011-moderation.md) で `moderation` が加わり、**6 モジュール**になった。
ルールは 1 モジュールにつき 2 つ (本体用 + 緩和用)、
レイヤ用の 3 つと合わせて **15 ルール**になる。

#### 問題はルール数ではない

数えるべきは `deny` のエントリ数になる。

| | ルール | `deny` エントリ |
| --- | --- | --- |
| 本体用 × 6 | 6 | 他 5 モジュール + `httpapi` + `infrastructure` + `pgx` + `gin` = **54** |
| 緩和用 × 6 | 6 | 他 5 モジュール + `httpapi` = **36** |
| `domain-layer` | 1 | 6 モジュールの `usecase` = 6 |
| `httpapi-layer` | 1 | 6 モジュールの `domain` + `infrastructure` + `pgx` = 8 |
| `httpapi-test` | 1 | 2 |
| **計** | **15** | **約 106** |

現在 (2 モジュール) の `.golangci.yml` は 205 行。
`desc` を同じ密度で書けば、**YAML は 700 行前後**になる。

さらに悪いのは、モジュールを 1 つ足すたびに
**既存の全モジュールの `deny` にも追記が要る**点になる。
編集コストが O(n²) で増える。

#### 本当の問題: 書き忘れが「許可」に倒れる

[ADR 0004](0004-modular-monolith.md) 自身が、この失敗を記録している。

> E は、緩和用ルールを 1 つにまとめていた初版では**検出できていなかった**。
> 「相手モジュールは閉じたまま」と書きながら deny に入れ忘れており、
> プローブを置いて初めて気づいた。
> **設定だけを読んで正しさを判断していたら見逃していた欠陥である。**

**2 モジュール・20 エントリの時点で既に入れ忘れが起きている。**
6 モジュール・106 エントリで起きないと考える理由がない。

`deny` (拒否リスト) 方式の本質的な弱点はここにある。

| 方式 | 書き忘れたとき |
| --- | --- |
| **拒否リスト** (`depguard`) | **通ってしまう** —— 境界が静かに壊れる |
| **許可リスト** (`go-arch-lint`) | 落ちる —— 気づく |

**フェイルセーフの方向が逆**になっている。

このプロジェクトは CORS で
「ワイルドカードを使わず許可リスト方式」を選んでいる
([`middleware.go`](../../apps/go-api/internal/httpapi/middleware.go))。
モジュール境界だけ拒否リストなのは、思想として一貫していない。

#### 選択肢

**A. `depguard` を維持し、境界の検証をテストで自動化する**

ADR 0004 が手動で置いて削除したプローブ 7 件を、
CI で回るテストとして残す。「落ちるはずのものが通る」ことを検出できる。

- 利点: ツールが増えない。ADR 0004 の実際の弱点 (手動検証) を直接埋める
- 欠点: YAML 700 行は残る。テスト自体を書き忘れたら守れない

**B. モジュール間の検査を `go-arch-lint` に移す**

`go-arch-lint` は**許可リスト**でコンポーネントの依存を宣言できる。
書かなかった依存は自動的に禁止される。

実際の依存は対称ではなく階層構造になっている。

```
moderation → thread, comment, image
image      → user
comment    → thread, user
thread     → user
contact    → user
```

これを宣言的に書けば、モジュール追加は**自分の行を足すだけ**で済む。

- 利点: O(n) で書ける。書き忘れが禁止側に倒れる。階層をそのまま表現できる
- 欠点: ツールとバージョン固定が 1 つ増える (Makefile の方針)。
  移行するなら中途半端に混在させず、モジュール間の検査は全部移す必要がある

**C. `.golangci.yml` を生成物にする**

モジュール一覧から対称な列挙を機械生成する。
このリポジトリは既に `verify-generated` で生成物の一致を CI 検査している。

- 利点: 列挙の手間と入れ忘れが消える。sqlc / oapi-codegen と同じ思想
- 欠点: lint の設定を生成するのは一般的でなく、読み手が戸惑う。デバッグしにくい

**D. モジュールを減らす**

`contact` は他のどのモジュールとも結合しない。
ただし減らしても 5 モジュール = 13 ルールで、O(n²) の構造は変わらない。

#### 方針 (決定済み・検証待ち)

**B を軸に、A を併せて行う。** ただし**決定の前に実地検証を挟む**。

- `depguard` には**レイヤとライブラリの検査だけを残す**。
  `**/internal/*/domain/**` のような総称で書ける範囲であり、
  モジュールが増えてもルールは増えない
  (ADR 0004 が「総称で書けるのはレイヤ方向だけ」と書いた、まさにその部分)
- **モジュール間の対称な禁止だけを `go-arch-lint` に移す。**
  ここが O(n²) の原因であり、許可リストなら O(n) になる
- A のプローブ自動化は、どちらのツールを選んでも価値がある

**移行するなら Phase 5 (3 モジュール目の追加) の時点が最も安い。**
6 モジュール分を手で書いてから捨てるのは、106 エントリを無駄に書くことになる。

ADR 0004 は**プローブ 7 件で実際に検証してから**書かれている。
同じ水準を保つため、`go-arch-lint` を小さく試して
「落ちること」と「通ること」を確認してから ADR 0013 として決定を記録する。
設定を読んだだけで判断しない。

**方針は B で決定した。** 残っているのは検証と、その結果の記録になる。

- [x] B で進める (2026-08-05 決定)
- [ ] Phase 5 の前に `go-arch-lint` を試し、
      落ちること / 通ることをプローブで確認する
- [ ] `depguard` に残す範囲 (レイヤ + ライブラリ) の線引きを確定する
- [ ] 結果を ADR 0013 として記録し、[ADR 0004](0004-modular-monolith.md) の
      決定 B を部分的に置き換える

#### 検証で確かめること

ツールの継続性そのものも検証項目に含める。
`go-arch-lint` は `golangci-lint` ほど広く使われておらず、
**採用前にメンテ状況とバージョン固定の可否を確認する**。

不安が残る場合は **A (`depguard` 維持 + プローブの自動化) に退避する。**
YAML 700 行は残るが、「入れ忘れが CI で落ちる」状態にはなるため、
現状より確実に良くなる。この退避先があることを前提に B を選んでいる。

([ADR 0005](0005-authentication.md))。

### 15. デモ環境を置くか (3 か月後に判断)

[インフラ構成](../infrastructure.md) は理想構成であり、デプロイしない。
一方で「動くものを見せられない」という制約が残る。

AWS で最小構成を組むと **ALB と RDS が支配的で月 $40〜50** になり、
無料枠も 12 か月で切れる。

無料枠が効く構成なら、ほぼ費用をかけずに置ける。

| 役割 | 候補 |
| --- | --- |
| PostgreSQL | Neon (スケールトゥゼロ) |
| Go API | Cloud Run (スケールトゥゼロ) |
| Next.js | Vercel |
| 画像 | Cloudflare R2 (S3 互換・エグレス無料) |
| メール | Resend など |

**移行コストは低い。** ストレージ・メール送信・OIDC のいずれも
インターフェースの背後に置く設計になっているため
([ADR 0007](0007-image-storage.md) / [ADR 0008](0008-contact-and-mail.md) /
[ADR 0005](0005-authentication.md))、実装の差し替えで足りる。

**理想構成 (AWS) と実際のデモ構成が違うこと自体は、
「なぜ妥協したか」を説明できる材料になる**ため、
無理に AWS に寄せる必要はない。

判断に伴って決まること:

- CD (現在 CI のみで、デプロイのパイプラインがない)
- Google OAuth のリダイレクト URI を本番ドメインで登録する
- 公開する以上、利用規約とプライバシーポリシーが要る

## 決定済みの API 仕様

| 項目 | 決定 |
| --- | --- |
| ページネーション | キーセット (cursor) 方式。`?cursor=&size=`、既定 20 件、上限 100 件 |
| エラー形式 | `{"error": {"code": "...", "message": "..."}}` |
| CORS | 許可リスト方式。既定は `http://localhost:3000` |
| スレッド作成 | `POST /threads` を実装済み |

## Phase 2 に残した作業

コメント投稿 (`POST /threads/{threadId}/comments`) は
**基本的な実装のみ**を済ませてある。以下は Phase 2 の作業として残っている。

- SERIALIZABLE 分離レベルでのトランザクション実装
- 直列化失敗 (SQLSTATE 40001) の指数バックオフつきリトライ
  (`postgres.IsRetryable` が起点)
- 悲観ロック版 (`SELECT ... FOR UPDATE`) との比較実装
- 両者のスループット比較ベンチマーク
