### ✅ 7. コメント削除 API

**公開する。** 項目 6 で `author_id` が入るため、
「`author_id` が現在のセッションのユーザーと一致するときだけ削除できる」
が表現できるようになった。

匿名投稿 (`author_id` が NULL) は本人には削除できない。
[ADR 0005](0005-authentication.md) の権限モデルを参照。

`LockThreadForUpdate` (Phase 2) と `FetchThreadListNPlusOne` (Phase 4) は
引き続き未使用のまま残す。用途はコードとロードマップに明記されている。

> **実装した (Phase 10 後半)。**
> `DELETE /threads/{threadId}` と
> `DELETE /threads/{threadId}/comments/{commentId}` を公開した。
>
> 「誰も削除できない」は [ADR 0011](0011-moderation.md) 決定 2 が
> 上書きしている —— **匿名投稿はモデレーターが消せる。**
> 本人に消せないことは変わらない (投稿者を特定する情報が無いため)。
>
> 実装して分かったこと:
>
> - **`403` と `404` の撃ち分けに 2 本目のクエリが要った。**
>   更新行数だけでは「対象が無い」と「自分のものではない」が区別できず、
>   自分の投稿が消せないときに理由を伝えられない。
>   判定と更新を CTE 1 本に畳む形も書けるが、
>   **sqlc が CTE と更新対象テーブルのスコープを混ぜてしまい生成に失敗する**
>   (PostgreSQL は通る)。失敗経路でだけもう 1 往復する形にした
> - **匿名投稿を弾くのに `IS NOT NULL` は要らなかった。**
>   `author_id = $2` は `author_id` が NULL のとき NULL になり、真にならない。
>   三値論理がそのまま「本人であることを示せない」を表している ——
>   ただし**フェイクでは再現できない**ので、実 DB の検査が要る
> - **`405` を見ていた検査が 2 か所壊れた。** どちらも
>   「仕様書に無いメソッド」の例として `DELETE /threads/{id}` を使っていた。
>   定義した瞬間に 401 を見るようになる。
>   測っているものが「405 を返す経路がある」ではなく
>   「定義されていないメソッドが弾かれる」であることを、
>   検査の側に書いておく必要がある

### ✅ 11. ID の型

**用途ごとに使い分ける。全部を統一しない。**

| テーブル | 決定 | 理由 |
| --- | --- | --- |
| `threads` / `comments` | **`BIGINT` 連番のまま** | キーセットページネーションが素直に動いている。`comments` は 5 年で億単位になるため 8 → 16 バイトが効く。パーティションキー (`thread_id`) のハッシュ計算も重くなる |
| `users` | 内部 ID は `BIGINT`。**公開用に `public_id UUID` を別に持つ** | マイページの URL が連番だと全ユーザーを列挙できる |
| `images` | `UUID` | [ADR 0007](0007-image-storage.md)。キーが推測できると他人の画像を辿れる |
| `sessions` | ランダム | [ADR 0005](0005-authentication.md) |

掲示板でスレッド番号が連番なのはむしろ自然であり、
避けたいのは**ユーザーの列挙**だけなので、そこだけ分ける。

#### UUID v7 を選んだ根拠

RFC 9562 (2024 年) で標準化された版で、
**先頭 48 ビットが Unix ミリ秒のタイムスタンプ**、残りがランダムになっている。

| | UUID v4 | **UUID v7** | BIGINT 連番 |
| --- | --- | --- | --- |
| B-tree への挿入位置 | ランダム (ページ分割が多発) | **末尾に追記** | 末尾に追記 |
| キーセットの前提 (単調増加) | 満たさない | **満たす** | 満たす |
| サイズ | 16 バイト | 16 バイト | **8 バイト** |
| 総数の推測 | 不可 | **不可** | 可能 |
| 生成時刻の露出 | なし | **あり** (先頭が時刻) | なし |

v4 ではなく v7 を選ぶのは、**インデックスの挿入位置が末尾に寄る**ため。
v4 は完全ランダムなのでページ分割が多発する。

`public_id` はソートに使わないため単調増加である必要はないが、
インデックスの効率は v7 のほうが素直になる。

#### 公開用識別子はハンドル名ではなく UUID v7 にする

`/users/hoshino` のような可読な識別子は共有しやすいが、
**別の設計判断を一式呼び込む**。

- 変更を許すか (許すと URL が変わる)
- 一意性の判定 (大文字小文字、Unicode 正規化)
- 予約語の除外 (`admin`, `api`, `me` など)
- 紛らわしい名前によるなりすまし

まず `public_id UUID` (v7) で公開経路を作り、
**必要になってからハンドル名を足す**。
ハンドル名 → `public_id` の解決を追加するだけで済む。

逆順 (ハンドル名から始めて後で UUID を足す) にすると、
既に配布された URL の互換性が問題になる。

**PostgreSQL 17 には `uuidv7()` がない** (18 で追加) ため、
生成は Go 側 (`google/uuid` の `NewV7`) で行う。

### ✅ 16. セッションの解決を OIDC の設定から切り離すか

**切り離した。** 詳細は [ADR 0005](0005-authentication.md) 決定 4。

`Authenticate` は `sessions` を読んで期限を見るだけで Google を必要としない。
必要とするのはログイン (認可コードの交換) だけなので、
`SessionInteractor` と `LoginInteractor` に分けた。

**503 になるのはログインの 2 経路だけ**になり、
セッションの検証・`/me`・ログアウトは設定の有無にかかわらず動く。

切り離す前は、資格情報を置いていない CI で
**認証を要する経路が 1 件も検証されていなかった**。
しかもスモークは SKIP を失敗として数えないので、CI は緑のままだった。

実測 (資格情報なしでスモークを実行):

| | 切り離す前 | 切り離した後 |
| --- | --- | --- |
| CI で通る件数 | 74 | **89** |
| 冪等キー ([ADR 0015](0015-idempotency.md)) | 0 件 (全 SKIP) | **11 件** |
| `/me` の検査 | SKIP | **2 件** |
| ログアウト | (検査なし) | **2 件** |

手元 (資格情報あり) は 93 件。差の 4 件は、
ログインの開始を実際に 302 させる検査になる。

**「セッションを発行する手段が無いのにセッションを受け付ける」構成**は
承知のうえで選んでいる。生成と検証は別の関心事であり、
テストは `sessions` へ直接行を入れて作る (スモークが既にその形をとっていた)。

### ✅ 9. 定期処理をどのプロセスで動かすか

**API プロセス内で動かす。** (2026-08-13 決定)

`internal/scheduler` に置き、`cmd/api` が Job を渡す形にした。

| 処理 | 間隔 | 状態 |
| --- | --- | --- |
| 期限切れセッションの削除 | 1 時間 | **配線した** (実装済みで未配線だった) |
| 期限切れ冪等キーの削除 | 1 時間 | **配線した** (同上) |
| 画像の孤児回収 | 10 分 | Phase 6 後半で実装 + 配線 |
| 閲覧数のフラッシュ | — | Phase 7。**プロセス内でなければ動かない** |
| 問い合わせメールの送信 | 1 分 | **Phase 8 で配線した** (下記) |
| 送信元 IP の消し込み | 12 時間 | 同上。個人データの保持期間 ([ADR 0008](0008-contact-and-mail.md)) |

#### 決め手

**閲覧数のフラッシュがどうせプロセス内でしか動かない** ([ADR 0006](0006-view-count-and-popularity.md))。
バッファがそのプロセスのメモリにあるためで、
つまりスケジューラは API プロセスに必ず要る。
そこへ他を寄せればデプロイ単位が増えない
([ADR 0004](0004-modular-monolith.md) のモジュラモノリスとも揃う)。

#### 引き受けるコスト

**レプリカの数だけ同じ処理が同時に走る。**
そのため、登録する処理は次の 2 つを満たす必要がある。

1. 何度実行しても結果が変わらない (冪等)
2. 同じ行を 2 つのプロセスが掴まない
   (`SELECT ... FOR UPDATE SKIP LOCKED` または件数上限つきの `DELETE`)

画像の回収は 2 を行ロックで満たしている。
期限切れ削除は件数上限つきの `DELETE` なので、重複しても害がない。

**起動直後の実行時刻はばらつかせている。** 揃えると、デプロイのたびに
全レプリカが同じ瞬間へ負荷を集中させる。

**メール送信 ([ADR 0008](0008-contact-and-mail.md)) も同じスケジューラに載せた。**
外部への送信は「二重に走ると二重に届く」ので性質が違う、と保留していた点は
`UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED)` で確保してから
送る形で解いた —— 上の条件 2 をそのまま満たす。

**ただし exactly-once にはなっていない。** 送信の直後に status を書く前で
落ちると、リース切れの後にもう一度送られる。SMTP に冪等キーが無い以上
避けられないので、**重複を許して取りこぼしを許さない**側を選んでいる
(ADR 0008)。「二重に走ると二重に届く」を消したのではなく、
**起こる条件をクラッシュ時だけに狭めた**、というのが正確なところになる。

### 12. `comments` のパーティション数 (8) は足りるか

[ADR 0009](0009-scaling-strategy.md) の見積もり (登録 100 万ユーザー、
DAU 10〜30%) では、コメントは年間 3,650 万〜2 億件になる。
5 年で 1 パーティションあたり 2,000 万〜1.2 億行。

行数そのものは PostgreSQL が扱える範囲だが、
**ハッシュパーティションの数を後から変えるには全データの再配置が要る**
(モジュラスが変われば行の所属先が変わるため)。
新構成のテーブルへ移行するか、論理レプリケーションを使うことになる。

README に記載のとおり、パーティションは
「どの規模から効き始めるかを Phase 4 で実測する」ために入れたものなので、
判断材料は測定で得られる。ただし**変更コストが高い側の判断**である点は
認識しておく。

#### 実測後の決定 (Phase 4 / `make partition-probe`)

**8 のままにする。増やさない。**

2,000 万行まで測って、**分割が効き始める規模には届かなかった**
([ADR 0009](0009-scaling-strategy.md) の「実測」節)。
32 分割も測ったが、すべての項目で 8 分割より悪かった ——
計画時間が増え、除外が効かないクエリの走査先が増えるだけになる。

**問いの立て方が間違っていた。** 「8 で足りるか」は
「分割が読み取りを速くする」ことを前提にしているが、
その前提が測定で成立しなかった。除外は正しく効いている
(実行計画に `Subplans Removed: 7` が出る) のに速くならない ——
**2,000 万行を 8 分割しても B-tree の段数が変わらない**ためになる。

したがって 8 分割の価値は読み取り性能ではなく、保守の側にある
(区画ごとの `VACUUM`、索引の作り直し、古い区画の切り離し)。
その用途では 8 で足りており、増やす根拠が無い。

- [x] 実測後、8 のままにするか増やすか → **8 のまま**

### 14. テストの依存サービスをどこまで CI で立てるか

現在のテストは 2 層 (ユニット = フェイク、スモーク = 実 DB)。
今回の設計で、外部サービスへの依存が 3 つ増える。

| 依存 | ローカルでの代替 | 出典 |
| --- | --- | --- |
| オブジェクトストレージ | MinIO | [ADR 0007](0007-image-storage.md) |
| メール送信 | Mailpit | [ADR 0008](0008-contact-and-mail.md) |
| OpenID Connect プロバイダ | (フェイクを自作) | [ADR 0005](0005-authentication.md) |

ユニットテストはすべてフェイクで書けるが、
**スモークテスト (実 DB で HTTP 越し) をどこまで広げるかは決まっていない**。

- **広げる** — 画像アップロードとメール送信を実際に通す。
  CI で MinIO と Mailpit を起動する必要があり、CI 時間が伸びる
- **広げない** — 認証済みリクエストのテストはセッションを DB に直接入れて行い、
  画像とメールはユニットのフェイクに留める

Google の OIDC はどちらにせよ実際には叩かない
([ADR 0005](0005-authentication.md))。

#### ✅ オブジェクトストレージは**立てる** (2026-08-12 決定)

CI の `migration-ci` に MinIO を足した。判断の理由:

- **DB とストレージという 2 システム間の整合が主題**になる
  ([ADR 0007](0007-image-storage.md) 決定 3 の pending 行と孤児オブジェクト)。
  片方をフェイクにすると、検証したいものが残らない
- path-style の要否・`Content-Type` が保存されて配信時に返ること・
  存在しないキーの `DELETE` が成功すること、はいずれも
  **実物でしか確かめられない**
- **CI 時間の増加は実測で 26 秒** (Migration Check が 57 秒 → 83 秒)。
  MinIO の起動待ち・`mc` の取得・バケット作成・検証 5 件の合計になる。
  初版はここに「約 10 秒」と書いていたが、**手元の体感からの見積もりであり
  実測ではなかった**。CI で測った値に差し替えている

**メール送信 (Mailpit) はスモークに入れなかった。** 問い合わせで
実物でしか確かめられないのは「SKIP LOCKED が同じ行を配らないこと」で、
これは**実 DB があれば足り、SMTP サーバは要らない**
(`contact_repository_live_test.go`)。メッセージの組み立ては

### 15. デモ環境を置くか (3 か月後に判断)

[インフラ構成](../infrastructure.md) は理想構成であり、デプロイしない。
一方で「動くものを見せられない」という制約が残る。

AWS で最小構成を組むと **ALB と RDS が支配的で月 $40〜50** になり、
無料枠も 12 か月で切れる。

無料枠が効く構成なら、ほぼ費用をかけずに置ける。

| 役割 | 候補 |
| --- | --- |
| PostgreSQL | Neon (スケールトゥゼロ) |
| Go API | Cloud Run (スケールトゥゼロ) |
| Next.js | Vercel |
| 画像 | Cloudflare R2 (S3 互換・エグレス無料) |
| メール | Resend など |

**移行コストは低い。** ストレージ・メール送信・OIDC のいずれも
インターフェースの背後に置く設計になっているため
([ADR 0007](0007-image-storage.md) / [ADR 0008](0008-contact-and-mail.md) /
[ADR 0005](0005-authentication.md))、実装の差し替えで足りる。

**理想構成 (AWS) と実際のデモ構成が違うこと自体は、
「なぜ妥協したか」を説明できる材料になる**ため、
無理に AWS に寄せる必要はない。

判断に伴って決まること:

- CD (現在 CI のみで、デプロイのパイプラインがない)
- Google OAuth のリダイレクト URI を本番ドメインで登録する
- 公開する以上、利用規約とプライバシーポリシーが要る
  (メールアドレス・IP・画像を扱うため)
