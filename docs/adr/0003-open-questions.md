### ✅ 3. ESLint が実質的に動いていなかった

正式に導入した。

- `eslint` + `eslint-config-next` を devDependencies に追加
- フラット設定 `apps/next-app/eslint.config.mjs` を作成
- Next.js 16 で `next lint` は削除されたため、`eslint .` を直接呼ぶ形に変更
- 生成物 (`schema.d.ts`) は検査対象から除外
- `no-explicit-any` をエラーに引き上げ (型が生成されている以上 any は不要)

### ✅ 4. Next.js が 13.4.7 で止まっていた

以下に更新した。

| | 変更前 | 変更後 |
| --- | --- | --- |
| next | `latest` (実体 13.4.7) | `^16.2.12` |
| react / react-dom | `latest` (実体 18.2.0) | `^19.2.8` |

`jsx` が `react-jsx` (automatic runtime) になった。
これに伴い不要になった `import React` を削除している。

### ✅ 11. ID の型

**用途ごとに使い分ける。全部を統一しない。**

| テーブル | 決定 | 理由 |
| --- | --- | --- |
| `threads` / `comments` | **`BIGINT` 連番のまま** | キーセットページネーションが素直に動いている。`comments` は 5 年で億単位になるため 8 → 16 バイトが効く。パーティションキー (`thread_id`) のハッシュ計算も重くなる |
| `users` | 内部 ID は `BIGINT`。**公開用に `public_id UUID` を別に持つ** | マイページの URL が連番だと全ユーザーを列挙できる |
| `images` | `UUID` | [ADR 0007](0007-image-storage.md)。キーが推測できると他人の画像を辿れる |
| `sessions` | ランダム | [ADR 0005](0005-authentication.md) |

掲示板でスレッド番号が連番なのはむしろ自然であり、
避けたいのは**ユーザーの列挙**だけなので、そこだけ分ける。

#### UUID v7 を選んだ根拠

RFC 9562 (2024 年) で標準化された版で、
**先頭 48 ビットが Unix ミリ秒のタイムスタンプ**、残りがランダムになっている。

| | UUID v4 | **UUID v7** | BIGINT 連番 |
| --- | --- | --- | --- |
| B-tree への挿入位置 | ランダム (ページ分割が多発) | **末尾に追記** | 末尾に追記 |
| キーセットの前提 (単調増加) | 満たさない | **満たす** | 満たす |
| サイズ | 16 バイト | 16 バイト | **8 バイト** |
| 総数の推測 | 不可 | **不可** | 可能 |
| 生成時刻の露出 | なし | **あり** (先頭が時刻) | なし |

v4 ではなく v7 を選ぶのは、**インデックスの挿入位置が末尾に寄る**ため。
v4 は完全ランダムなのでページ分割が多発する。

`public_id` はソートに使わないため単調増加である必要はないが、
インデックスの効率は v7 のほうが素直になる。

#### 公開用識別子はハンドル名ではなく UUID v7 にする

`/users/hoshino` のような可読な識別子は共有しやすいが、
**別の設計判断を一式呼び込む**。

- 変更を許すか (許すと URL が変わる)
- 一意性の判定 (大文字小文字、Unicode 正規化)
- 予約語の除外 (`admin`, `api`, `me` など)
- 紛らわしい名前によるなりすまし

まず `public_id UUID` (v7) で公開経路を作り、
**必要になってからハンドル名を足す**。
ハンドル名 → `public_id` の解決を追加するだけで済む。

逆順 (ハンドル名から始めて後で UUID を足す) にすると、
既に配布された URL の互換性が問題になる。

**PostgreSQL 17 には `uuidv7()` がない** (18 で追加) ため、
生成は Go 側 (`google/uuid` の `NewV7`) で行う。

### ✅ 13. モジュール境界の検査ツール

**`go-arch-lint` に移し、`depguard` は外した。**
16 件のプローブで実測してから決めている。詳細は
[ADR 0017](0017-arch-lint-and-depguard.md)。

決め手は、この項目が当初想定していたものと**違っていた**。

| | 想定 | 実測 |
| --- | --- | --- |
| depguard の穴 | 拒否リストだから書き忘れが許可に倒れる | `list-mode: strict` で許可リストも書ける。**穴はどのルールにも一致しないファイルが無検査になること** |
| 分割方針 | depguard にレイヤとライブラリを残す | レイヤもライブラリも arch ファイルで書けたため、**depguard は 0 ルールにした** |

設定を更新せずに新モジュールを足すプローブ (M) は、
`depguard` では拒否リスト版・許可リスト版のどちらも素通りし、
`go-arch-lint` では落ちた。

`.golangci.yml` は 205 行から 79 行になった。

### 12. `comments` のパーティション数 (8) は足りるか

[ADR 0009](0009-scaling-strategy.md) の見積もり (登録 100 万ユーザー、
DAU 10〜30%) では、コメントは年間 3,650 万〜2 億件になる。
5 年で 1 パーティションあたり 2,000 万〜1.2 億行。

行数そのものは PostgreSQL が扱える範囲だが、
**ハッシュパーティションの数を後から変えるには全データの再配置が要る**
(モジュラスが変われば行の所属先が変わるため)。
新構成のテーブルへ移行するか、論理レプリケーションを使うことになる。

README に記載のとおり、パーティションは
「どの規模から効き始めるかを Phase 4 で実測する」ために入れたものなので、
判断材料は測定で得られる。ただし**変更コストが高い側の判断**である点は
認識しておく。

- [ ] 実測後、8 のままにするか増やすか

### 14. テストの依存サービスをどこまで CI で立てるか

現在のテストは 2 層 (ユニット = フェイク、スモーク = 実 DB)。
今回の設計で、外部サービスへの依存が 3 つ増える。

| 依存 | ローカルでの代替 | 出典 |
| --- | --- | --- |
| オブジェクトストレージ | MinIO | [ADR 0007](0007-image-storage.md) |
| メール送信 | Mailpit | [ADR 0008](0008-contact-and-mail.md) |
| OpenID Connect プロバイダ | (フェイクを自作) | [ADR 0005](0005-authentication.md) |

ユニットテストはすべてフェイクで書けるが、
**スモークテスト (実 DB で HTTP 越し) をどこまで広げるかは決まっていない**。

- **広げる** — 画像アップロードとメール送信を実際に通す。
  CI で MinIO と Mailpit を起動する必要があり、CI 時間が伸びる
- **広げない** — 認証済みリクエストのテストはセッションを DB に直接入れて行い、
  画像とメールはユニットのフェイクに留める

Google の OIDC はどちらにせよ実際には叩かない
([ADR 0005](0005-authentication.md))。

### 16. セッションの解決を OIDC の設定から切り離すか

**認証を要する経路が CI でまったく検証できていない。**

`resolveSession` は Google の資格情報が揃っていないと素通しする。
CI には資格情報を置いていないため、セッションが解決されず、
すべてのリクエストが匿名として扱われる。

結果として、スモークの以下が CI でスキップされる。

| 節 | 手元 | CI |
| --- | --- | --- |
| `/me` の検査 | 通る | **SKIP** |
| 認証セクション | 4 件 | **0 件** |
| 冪等キー ([ADR 0015](0015-idempotency.md)) | 9 件 | **0 件** |

冪等キーは**本番で実際に使われる経路**であり、
「壊しても CI が気づかない」状態が新しく増えたことになる。

`Authenticate` は `sessions` を読んで期限を見るだけで、
**Google を必要としない**。ログイン (認可コードの交換) だけが必要とする。
両者を分ければ、資格情報が無い環境でもセッションは解決できる。

- **切り離す** —— CI で認証済みの経路を検証できるようになる。
  [ADR 0005](0005-authentication.md) の
  「設定が無ければ認証エンドポイントだけが 503」という決定を、
  「ログインだけが 503。セッションの検証は常に動く」に読み替えることになる
- **切り離さない** —— 現状維持。認証まわりは手元でしか検証できない

判断の材料として、切り離した場合に
「セッションを発行する手段が無いのにセッションを受け付ける」構成になる点は
確認しておく必要がある (テストは DB へ直接行を入れて作る)。

- [ ] 切り離すかどうか

### 15. デモ環境を置くか (3 か月後に判断)

[インフラ構成](../infrastructure.md) は理想構成であり、デプロイしない。
一方で「動くものを見せられない」という制約が残る。

AWS で最小構成を組むと **ALB と RDS が支配的で月 $40〜50** になり、
無料枠も 12 か月で切れる。

無料枠が効く構成なら、ほぼ費用をかけずに置ける。

| 役割 | 候補 |
| --- | --- |
| PostgreSQL | Neon (スケールトゥゼロ) |
| Go API | Cloud Run (スケールトゥゼロ) |
| Next.js | Vercel |
| 画像 | Cloudflare R2 (S3 互換・エグレス無料) |
| メール | Resend など |

**移行コストは低い。** ストレージ・メール送信・OIDC のいずれも
インターフェースの背後に置く設計になっているため
([ADR 0007](0007-image-storage.md) / [ADR 0008](0008-contact-and-mail.md) /
[ADR 0005](0005-authentication.md))、実装の差し替えで足りる。

**理想構成 (AWS) と実際のデモ構成が違うこと自体は、
「なぜ妥協したか」を説明できる材料になる**ため、
無理に AWS に寄せる必要はない。

判断に伴って決まること:

- CD (現在 CI のみで、デプロイのパイプラインがない)
- Google OAuth のリダイレクト URI を本番ドメインで登録する
- 公開する以上、利用規約とプライバシーポリシーが要る
  (メールアドレス・IP・画像を扱うため)

- [ ] 全 Phase 完了後に判断する
