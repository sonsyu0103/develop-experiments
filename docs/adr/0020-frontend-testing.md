# ADR 0020: フロントの検査は「状態遷移」を対象にする

- ステータス: **採用・実装済み**
- 日付: 2026-08-16

## 背景

`apps/next-app` にある検査は `tsc --noEmit` / `eslint` / `next build` の 3 つだけで、
**振る舞いを見るものが 1 つも無かった。**

管理画面 ([ADR 0011](0011-moderation.md)) を入れた PR のレビューで、
これが具体的な形で出た。**指摘 6 件のうち 4 件**が次の領域だった。

| | 指摘 |
| --- | --- |
| ① | 絞り込みを変えた直後に、**遅れて届いた古い応答が新しい一覧へ追記される** |
| ② | `busy` が単一 ID なので、行をまたぐと**削除の二重送信が通る** |
| ③ | 一過性の取得失敗が「読み込み中」の表示で固定される |
| ④ | 取得失敗時に「通報はありません」がエラーと同時に出る |

**4 つとも型検査を通り、lint を通り、ビルドも通る。**
型が通ることは「呼べる」ことしか言わない。

同時に、[変異プローブ](../../.github/scripts/mutation-probe.py) が
**この領域を 1 件も測れなかった。** 「テストが通った」を信用しない、
というこのリポジトリの前提が、フロントにだけ適用されていなかったことになる。

## 決定 1: Playwright を入れる。ただし**実バックエンドは使わない**

応答は `page.route` で差し替える。

### なぜ実 API を使わないのか

**上の ①〜④ は、実 API では作れない。**

①②は「**A の応答が B より後に届く**」を必要とする。
③④は「500 を返す」「特定の 1 リクエストだけ落とす」を必要とする。
実 API を相手にこれを作るには、API 側に遅延や故障を注入する口を開けることになり、
**本番に存在しない経路が増える。**

ここで測りたいのは API の挙動ではなく、
**遅延・失敗・順序に対するクライアントの状態遷移**になる。

### 実 HTTP 越しの検査は既にある

API 側は `make smoke` が実 DB と実 MinIO に対して 207 件を回している。
**重ねない。** 重ねると、同じことを 2 か所で測りながら
どちらも中途半端になり、しかも遅くなる。

### 副産物: CI のジョブが増えない

Go API も Postgres も MinIO も要らないので、
既存の `Next.js Checks` にそのまま乗る。
compose を CI で立てる必要も、資格情報を用意する必要も無い。

## 決定 2: 本番ビルドに対して回す

`next dev` ではなく `next build && next start` を使う。

- `next dev` は Strict Mode で効果が 2 回走るなど**挙動が違う**
- **`/admin` が静的化されること**を確かめられるのは本番ビルドだけになる
  ([ADR 0005](0005-authentication.md) の 4 層キャッシュが 1 層になる根拠)

代償として、変異プローブは 1 変異ごとにビルドをやり直す。
**1 件あたり数十秒**かかり、Go の変異と同じ感覚では並べられない。
`next start` を使い回すと**壊す前のバンドルを検査してしまう**ので、
ここは短縮しない (`go test -count=1` と同じ理由)。

## 決定 3: 検査では API を**同一オリジン**に置く

`NEXT_PUBLIC_API_URL` を空にして、宛先を相対 URL (`/me`) にする。

別オリジンのままだと、`page.route` で差し替えた応答にもブラウザが
CORS を要求する。`credentials: 'include'` と併用するため
`Access-Control-Allow-Origin` にワイルドカードは使えず、
preflight の再現も要る —— **検査の設定ファイルで CORS を偽装することになる。**

CORS と preflight は
[ADR 0013](0013-http-defense.md) の `cors()` 単体検査とスモークが持つ領域で、
**そこを模造品で二重化しない。**

なお同一オリジン構成は実在する形になる
(フロントと API を 1 つのホストに置く場合。ADR 0013 の「実装して分かったこと 5」)。

## 決定 4: 再試行しない (`retries: 0`)

ここで測るのは状態遷移になる。
**再試行で緑になるなら、それは「たまたま順序が変わった」ことを意味する。**
隠すと、いま塞いだばかりの競合がそのまま戻る。

不安定な検査が出たら、再試行ではなく検査のほうを直す。

## 決定 5: 変異プローブを Playwright にも通す

`mutation-probe.py` に `runner:` を足した (`go` が既定、`playwright` を追加)。

**「テストが通った」を信用しない、という前提はフロントでも変わらない。**
これが無いと、①〜④ に対して「対応したという記録」だけが残る。

`-g` に一致しないとき Playwright は **終了コード 1 で終わる**ので、
「落ちた」と見分けが付かない。`No tests found` を見て `empty` に分けている
—— 分けないと、検査名を書き換えたときに
**「壊したら落ちた」と誤って数える。**

## 引き受けるコスト

- **CI が伸びる。** ブラウザは 100 MB 近くあるため、
  バージョンを鍵にしてキャッシュする。
  パッケージを上げたときに古いブラウザを引き当てると起動時に落ちるので、
  **鍵にバージョンを含めることが必須**になる
- **変異 1 件が数十秒。** 決定 2 の代償。件数を増やしにくい
- **Server Component を検査していない。** 現在の管理画面は取得を
  すべてブラウザに寄せているので届いているが、
  サーバ側で描画する画面が増えたら、この枠組みは同じようには効かない
- **実スタックとの結合は依然としてスモークだけ。**
  「ログインして管理画面から実際に削除する」経路は**通していない** ——
  Google の認可が要り、CI では資格情報が無い
  (スモークが moderator を作るのに `SQL_EXEC` でセッションを直接入れているのと
  同じ問題になる)。ここは埋まっていない
- **応答の形が手書きになる余地。** `schema.d.ts` の型で縛っているが、
  型が合っていても**実際の API が返さない組み合わせ**は作れる。
  仕様書が変わったときにテストだけが古い形のまま緑になる余地は残る

## やらなかったこと

### Vitest によるコンポーネント単体検査

①②は**複数のリクエストの順序**が対象になる。
コンポーネント単体で組むと、`fetch` のモックとタイマーの制御を
自前で書くことになり、**測りたいものより足場のほうが大きくなる。**

将来 `lib/` に純粋な関数が増えたら、そこには Vitest のほうが向く。
そのとき改めて判断する。

### 実スタックの E2E

上記のとおり、ログインの経路が CI で再現できない。
セッションを SQL で直接入れれば作れるが、
**その時点で「利用者がやること」を検査していない。**
入れるなら、認証を迂回する形と正面から向き合う必要がある。
